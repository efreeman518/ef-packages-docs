EF.LLMEval Operations

1. Budgets and ceilings

The ceiling is a hard limit, not a starting bid. The whole matrix is priced before a single call is sent, and a plan whose estimate exceeds the ceiling is refused with a full breakdown. The correct response to a refusal is almost always to cut a dimension, not to raise the number.

A matrix is cells times repeats, and cells are (workloads or episodes) times (candidates or assignments) times variants. Each factor multiplies:

Dimension What raising it buys What it costs
Candidates A wider field Linear in cells, and every non-incumbent cell is also two judge calls
Workloads or fixtures Evidence. Pooled comparisons grow, so the selection reaches its minimum sample count Linear
Variants A different question, with its own selection group Linear, and it does not help a group reach its sample minimum
Repeats Confidence against run-to-run variance, which matters because reasoning models generally reject temperature controls Linear

Dry-run first, always. A dry run walks the probe, the capability gate and the estimate, records every cell as skipped, and sends nothing. It is free and it is the only honest preview of a matrix's cost. The dashboard makes it mandatory before a live run for exactly this reason.

Declare expected output tokens. Without them, a workload is priced at its requested token ceiling, which it may never approach. That can overstate a sweep several-fold and refuse a run that would have been affordable. For an episode, declare them per role: a checker role that emits a short verdict priced at a full turn's ceiling distorts the whole plan.

The estimate is an upper bound, not a forecast. Actual spend is normally lower. Do not read the gap as the harness being wrong; read it as the ceiling having done its job.

Watch concurrency against the ceiling. Parallel cells can each clear the ceiling check before any of them has spent anything. Where cells share one ceiling, run them one at a time. That is why the dashboard's queue runs a single cell at a time and why a test project sharing a ceiling should turn off test parallelisation.

2. Judge cost, and the not-available case

The judge answers for every cell of the matrix, so on any sweep of size it is the bill:

  • Two judge calls per non-incumbent cell (the comparison is run in both orders).
  • Plus one per cell carrying a rubric score, including the incumbent's own cells.

Declare the judge's pricing so those calls are inside the estimate. Without it the sweep logs that the judging is outside the estimate, which is honest but leaves the ceiling protecting only half the spend.

The two paths

Path Billed Available
An API connection, selected with LLMEVAL_JUDGE_CONNECTION Yes, per call, to whoever owns the key Always
A file exchange drained by a Claude Code subagent No dollars. Subscription quota Only from the Claude Code harness, with a drainer online

Cost on the subscription path is reported as not available, never as zero. The spend field is null, the runner is named, and the judge calls are left out of the estimate with a logged note. Do not paper over that in a finding by writing zero: the judging was paid for, in quota, by whoever drained the queue.

There is no automatic fallback. With no drainer online (none started, or a heartbeat past the staleness bound) the sweep stops with No judge agent is draining {root} and names both ways out. A run that needs to proceed without a drainer selects an API judge explicitly and pays for it.

Operating the file-exchange path

  1. Start the drainer first, so a heartbeat exists before the first request is queued.
  2. Launch the sweep in the background. The exchange client blocks on its replies, so a foreground sweep and a drainer in the same session deadlock, each waiting for the other.
  3. Keep draining in a bounded loop until the run's summary file exists. Refresh the heartbeat on every pass, including empty ones, or the exchange will refuse to queue.

Draining is quota, not free. A long sweep is a long agent session.

Disagreeing with a verdict

Delete the one reply file and re-run: that question is asked again. Delete the whole done folder and everything is re-asked. Request files are never deleted, so the pending folder remains the record of what was actually asked.

Reproducibility

There is no model pin behind a subscription agent. A run is reproducible only in the sense that its reply files were kept, which is why they are kept. Record the judge and the date in every finding, and never compare win rates across runs whose judge was a different thing.

3. Pacing and 429s

Pacing comes first and is not retrying. Two caps apply: one per connection and one per model. A model that declares its own rate draws on its own bucket rather than the connection's, which matches the shape of most provider caps.

Cap the judge explicitly. It is one model on one account answering for the whole matrix, so it meets a per-model cap long before the rest of the field does. Set both a per-minute rate on the judge roster entry and a judge concurrency cap: the first bounds how many calls are sent per minute, the second how many are in flight. They are not substitutes, and a slow provider sits under a concurrency cap while exceeding a per-minute one.

The bucket is keyed on the connection and the wire model id, not the harness's roster id, so a judge entry and a candidate entry pointing at the same upstream model share one bucket exactly as they do at the provider. Where several entries declare a rate for one bucket, the strictest wins.

When a 429 arrives anyway, the client re-sends at most three times per call, on the SDK's own classification of transient faults. The schedule is flat: the provider's retry-after header where it is usable, a minute for a rate limit without one, ten seconds otherwise. A single wait is capped, and a provider asking for longer surfaces immediately as exhaustion of the bound with the duration named.

Beyond the bound:

  • A candidate cell is recorded as failed with its reason, and the sweep continues. That is a result about that model.
  • The judge stops the sweep, with a stop reason. Finished cells keep their results and a re-run replays them from cache.

Symptoms and what to do:

What you see What it means Do
A long pacing figure in the summary, low spend The run was slow, not expensive. Pacing waits are excluded from latency, so the latency column is still usable Nothing, or raise the declared rate if the provider actually allows more
Many retried calls with 429s The declared rate is above the real cap, or another process shares the account Lower the declared rate. More retries is the wrong lever
The sweep stopped with a judge stop reason The judge provider kept refusing Lower the judge rate and concurrency, then re-run. Finished cells replay free
One model takes minutes per cell and then fails A dead model id answering an error to everything: four sends and roughly half a minute per call Remove it from the roster
No pacing line in the report at all A decorating client provider is not forwarding the rate-limit counters Forward them. The member is a default interface implementation, so a decorator that ignores it returns nothing silently

4. Resuming, and what invalidates a cache

A stopped run needs no resume flag. Run the same command again. Candidate responses and judge replies are both cached on disk, so every cell that finished replays at no model cost and the run picks up where it left off. This is the intended response to an interruption, a judge outage, or a machine going to sleep.

What each cache is keyed on, and what therefore re-pays:

Cache Keyed on Invalidated by
Candidate responses The request, partitioned per model, and for an episode per assignment and the cast it names Editing a prompt, changing a model, or swapping a role's model inside an assignment that kept its name
Judge replies, API path The judge request, including the output cap Changing the rubric, the answers compared, or either output cap
Judge replies, file exchange A hash over the model, the messages and the options that change what a good answer looks like Deleting the reply file

Rules of thumb:

  • A scorer or report change re-pays nothing.
  • A prompt edit re-pays the affected candidate cells, and re-judges them.
  • A judge output-cap change re-pays most of the judging on a large matrix. That is deliberate: the cap is part of the cached request so a changed cap re-judges rather than replaying verdicts produced under a different one. Size the ceiling for the first run after such a change.
  • A timestamp or other varying value in a prompt makes every response a cache miss. If reruns are never free, look here first.

Turn caching off only to measure latency or run-to-run variance, both of which a cache falsifies. Remember that a cache-served cell reports no upstream route, because a cached response carries no fresh routing field, and that the summary carries a banner saying caching was on.

Retention. The storage root grows with every execution: the reporting store, the response cache, one report directory per execution name, and the judge exchange folders. Use a timestamped or build-numbered execution name for runs you want to compare over time, because runs sharing a name overwrite each other. Prune old executions deliberately; nothing prunes them for you. Keep the report half of anything a decision rested on, and keep the exchange reply files for any finding judged on the subscription path.

5. Secrets

Never in a repository, never in a report.

  • The roster file holds configuration key names, never key values. Keys come from user secrets and environment variables at load time.
  • A connection's string representation reports only whether a key or a credential is present, never either value, so a connection is safe to log.
  • A model under test carries no credential at all, and the eval host is never serialised. That is what makes a results file safe to commit.
  • The dashboard binds no credential to a component. Its pages show provider and connection names, model ids and upstream routes; the keys live inside the host's own client provider.
  • A connection with no resolvable key or credential is dropped at load time, along with every model and assignment naming it. A developer without one provider's key still gets a usable run.

Before publishing a report, a finding or a screenshot, the only check needed is that it came out of the package's own writers. If somebody has added their own logging around the provider, check that too.

For keyless auth, the credential chain is the caller's own dependency and its own decision. The package references only the core credential abstraction, never a credential-chain library, so there is no zero-configuration managed-identity path to be surprised by.

6. CI

Offline lane only. No live models in CI.

  • No provider secret should be available on a runner.
  • The opt-in environment variable should never be set on a runner, so the live lane stays inert by construction rather than by a filter somebody can delete.
  • If the offline lane should gate merges, add the project to an existing fast-test job with a filter that excludes the live test category. Otherwise leave the project out of CI entirely.

The offline lane is worth gating on. It proves the probe captures what the workload really sends, that a variant changes the request, that the ceiling parser is locale-safe, and that the deterministic evaluators accept clean input and reject bad input. All of that is exactly what breaks silently when the application's prompt assembly is refactored, and finding it during an expensive run is the expensive way to find it.

Two further rules:

  • Never take fixtures from real user data. Write synthetic fixtures, committed to the repository, shaped like production content but never lifted from it. That is what makes a fixture safe to run every day and to compare across models and months.
  • A sweep is not a merge gate. There is no pass condition for "which model is best", and a workflow that blocks on a measurement will either be disabled or will start spending on every pull request.

The skills install on build

Building a project that references EF.LLMEval copies the two packaged agent skills into the consuming repository, at <repository root>/.claude/skills/llmeval-harness and llmeval-run. That happens on a CI runner too, which is worth knowing for two reasons: a job that asserts a clean working tree after a build will see those folders unless they are committed or ignored, and a checkout with no .git entry installs nothing at all.

Lever Effect
<LLMEvalInstallSkills>false</LLMEvalInstallSkills> Opt out. Reasonable for a CI-only build that will never run an agent.
<LLMEvalSkillsRoot>path</LLMEvalSkillsRoot> Install into path/.claude/skills instead of the detected repository root.
tools/install-skills.ps1 / tools/install-skills.sh in the package Manual fallback for an opted-out build, a non-git checkout, or a machine that should not build first.

The copy only adds and overwrites its own two folders, never deletes anything else under .claude/skills, and warns rather than failing the build when the destination cannot be written. Commit the installed folders or add .claude/skills/llmeval-*/ to .gitignore; either is fine, and committing them is what makes the skills travel to everyone who clones.

7. Reading the dashboard

Point the dashboard at a storage root and it lists every execution under it. A directory directly under the root counts as an execution only when it holds a results file, which is what keeps the store and cache folders from being listed as runs.

Page Read it for
Executions When each run happened, its cells, its spend, its workloads. The first check after a run
Leaderboard Cost per passing generation, filtered by workload and variant. Per-role model and cost columns for an episode, the model and its upstream route for a scenario. The suggested adjustments from the results file follow
Cell One cell's transcript and response, every metric with its verdict and reason, the adjustment hints for that model and its vendor prompting note. Where to go when a model failed and it is not obvious why
Variants Two variants side by side, key by key
Proposals What the advisor proposed, with an accept action that records one into the execution's accepted set
Run Launch a sweep against a discovered host

Three things to know before trusting what you read:

  • The variant diff is override-only. A sweep records variant names, not variant text, so the diff cannot reconstruct a baseline column from a finished run. The page says so.
  • A judged run launched here is billed. The dashboard is not the Claude Code harness, so its judge is an API judge.
  • Accepted is not proposed. What the advisor suggested and what a person approved are kept in separate files deliberately, and an accepted variant wins over a host variant of the same name.

The run page's guardrails are all refusals with the same sentence the button's tooltip carries: live runs off by default, a ceiling the request cannot raise, a cell cap checked before planning, every assignment and variant named explicitly, and a mandatory dry run that is retired the moment any field changes. A plan refusal is shown verbatim, because its message carries the whole breakdown.
