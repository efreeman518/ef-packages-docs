EF.LLMEval Integration Guide

EF.LLMEval Integration Guide

Use this guide when you want to add a model-and-prompt evaluation harness to an existing .NET solution: a test project that runs the application's own code against a field of candidate models, prices every call, scores every result and ranks the field by cost per passing generation.

This guide is the procedure. It points at EF.LLMEval/README.md for every API detail rather than duplicating it, and at LLMEval-Design-Doc.md for why each mechanism is shaped the way it is. Day-to-day running is in LLMEval-Operations.md.

At a glance

Question Answer
What is added to the solution One test project (tests/Test.Eval), referencing EF.LLMEval and the production code it measures. Nothing in the application takes a dependency on the harness.
What runs the sweep A Claude Code session: the three skills the package installs on build, and a subagent draining the judge exchange. There is no other judge.
What it costs The candidate calls, capped by a spend ceiling priced before anything is sent, and the judge answers on top - outside that spend and charged to the harness subscription, about two per candidate cell, reported as a count beside the spend line and never as zero.
What comes out summary.md, results.json and the self-contained report.html, ranked by cost per passing generation.
What decides The Selection section: parity pick, upgrade pick, dominators, each with a pooled sample count, a per-comparison Wilson 95 percent interval and a cluster-level one with the scenario as the unit.
How long it takes to wire An afternoon for a single-shot workload over an existing composition root; longer where a chat client is newed inside a service and needs a seam first.

Every term of art in this guide has a one-line definition in the README glossary.

Getting started

Where this package joins an application that already uses LLMs

An application that registers its chat clients through EF.AI's AddEFChatClients has one keyed IChatClient per agent, under that agent's key in the EFAI:Agents block. That keyed registration is the seam. For every cell, EvalHost.CreateServices builds the application's own service collection, EvalCellServices.AddRoleClients removes the keyed client for each eval role and registers the candidate under test under the same key - wrapped in the recorder, the roster entry's setting variant, that role's production defaults and the capability stripper - and then the workload calls the application's own entry point, the service or handler a request calls. The real prompts, tools, multi-agent sequencing, persistence and gates all run; only the model behind each role is swapped.

What that buys: nothing is re-implemented in the harness, so a prompt or an orchestration change in production is measured by the next run without anybody editing the eval, and the incumbent is what actually ships.

What it requires: the EF.AI registration exists first; the agent keys are stable, because a role binds to a key and a renamed key is a cell talking to the live endpoint; request settings live in the agent's Defaults block so the seam can vary them per cell; and each workload is a call to the production entry point, with doubles only for infrastructure a cell cannot have. See design doc section 3.5 for why it is shaped that way, and Step 3 below for the code.

Before you start

  1. Register the application's chat clients through EF.AI first - AddEFChatClients over an EFAI:Connections and EFAI:Agents block, one keyed IChatClient per agent, secrets in user secrets or the environment. The harness binds each eval role to an agent key and reads that agent's Defaults, so this is not optional.
  2. Keep request settings out of the call sites, in the agent's Defaults block, or every cell that measures one is recorded as setting overridden: ... (pinned by the application).
  3. Put the package feed in NuGet.config and the credential in the user-level config, never in the repository.
  4. For a Foundry or Azure-backed connection, az account get-access-token has to succeed first: such a connection runs as whoever is signed in locally.
  5. Know what the judge costs. It is a Claude Code subagent draining the file exchange: outside the eval's dollar spend, and charged to the harness subscription at about two judge answers per candidate cell - times SweepOptions.JudgeReplicates when it is raised - plus a proposal request per scenario and a hints request per vendor family. A 1000-cell round is roughly two thousand judge answers.
  6. Plan for the samples rule. A selection needs SelectionOptions.MinSamples (6) judged comparisons per candidate: fixtures x repeats for single-shot scenarios, repeats alone for a single-fixture episode. Plan 6 repeats or two fixtures, and pass every fixture to one call.
  7. Pass an ILogger to SweepRunner. The packed template does. Without it the plan line, the pacing, the dropped settings and every limitation the runner reports are discarded.

Step 1. Inventory the model call sites

Do this before writing any code. A harness built without the inventory measures whatever was easiest to reach, which is rarely the call that costs the money.

Search the solution for every place a model is actually called, and for every place a prompt is built. The useful signals are chat-client injections and resolutions, keyed service lookups, prompt or system-message constants and templates, structured-output schemas, tool definitions and reasoning effort settings.

For each hit, write down five things:

Field Why it matters
The entry point a request reaches This is the thing a scenario or workload calls.
Which chat client it resolves, and under what key The key becomes a role binding in step 3.
Whether it is one call or a conversation Decides scenario versus episode, step 2.
What the request asks for: structured output, tools, reasoning effort Decides what gets removed from the request for a candidate whose catalog entry refuses it. No candidate is excluded over one.
Roughly how often it runs in production, and how long its output is Decides which call site is worth measuring first, and what to declare as expected output tokens.

Group the hits into workloads: one workload per thing a decision might be made about separately. An interpretation prompt that turns a structured input into prose and a classifier that tags the same input are two workloads, because they can reasonably run on different models.

Then find the composition root the harness will reuse: the method or class that registers the application's services, including its chat clients. If there is no such method (registration is inline in a program file), extracting one is usually the only application change this integration needs, and it is worth making.

Write the inventory down, in the test project's README or a scratch file. It is the argument for what the harness covers and what it does not.

Keep request settings out of the call site. While inventorying, grep for values the application fixes itself - ReasoningEffort, Temperature =, TopP =, MaxOutputTokens =, ResponseFormat =, provider-specific AdditionalProperties[...], which is worth recording even though the OpenAI-wire clients drop it - and record each as pinned setting: <file>:<line> <setting>=<value> used by <role>. Each one is a setting this harness can only measure by overriding it: the cell runs, but it is recorded as setting overridden: ... (pinned by the application), the incumbent is measured at the pinned value because that is what ships, and adopting the variant means changing the application first. Configure them per agent instead, in the Defaults block on the agent's EFAI:Agents entry (EF.AI 1.2.107 or later): ReasoningEffort, Temperature, TopP, MaxOutputTokens, FrequencyPenalty, PresencePenalty, Seed, StopSequences, ResponseFormatJson, with an agent's keys overriding its connection's and a caller-set ChatOptions member always winning - so an eval override still takes effect. Production sets its defaults once and the eval's setting variants override per cell.

Wire the configured defaults into the harness so the incumbent stays measured on what ships. Build one provider from the host's own CreateServices() and hand it to each role binding:

using var application = CreateServices().BuildServiceProvider();

var roles = new[]
{
    new EvalRoleBinding("main", "chat-synthesis").WithApplicationDefaults(application),
    new EvalRoleBinding("judge", "chat-judge").WithApplicationDefaults(application),
};

WithApplicationDefaults reads the merged connection-and-agent Defaults EF.AI registered as named options under that agent key - the same object the application's own client is built from - and returns the binding unchanged when that Defaults block sets nothing. A key the application registers no client under is refused by name instead, because reading it would report an agent that configures nothing and measure the whole field at the provider's own default. Add the section name (WithApplicationDefaults(application, "MyAI")) when the agents are not under EFAI, so the report points at the key a reader would actually edit.

A single-shot scenario harness has no role binding - the sweep hands the scenario a client and its own code decides what to do with it - so it carries the resolved defaults on the scenario:

using var application = CreateServices().BuildServiceProvider();

var scenario = new EvalScenario("summarise", RunSummarise)
{
    RequestDefaults = RoleRequestDefaults.ForAgent(application, role: "main", serviceKey: "chat-summarise"),
};

role is only what the reports call it. Everything else is identical to the episode path.

The sweep then applies them below the roster entry's requestSettings and above the capability stripper, prices the completed request in the spend estimate, and prints one line per role in summary.md, report.html and results.json. Never wrap the bound client on the application side instead: that wrapper sits above the sweep's own settings layer, so every setting-variant cell would be reported as overriding a value pinned by the application and the recorder would claim the application asked for the defaults.

Step 2. Decide scenario or episode

Choose When
Scenario The workload is one model call, or a short deterministic chain around one call. Example: an interpretation prompt that turns a structured record into a paragraph of prose.
Episode The workload converses, or more than one model participates. Example: a three-agent tutoring session where one model explains, a second checks the explanation, and a simulated student replies.

Signals that an apparent scenario is really an episode: the code loops until a condition, one call's output is another model's input, or a person is expected to reply in the middle.

If it is an episode, decide three more things now:

  • The roles. Name them for what they do (main, checker, student). The first declared role is primary: the turn cap counts its turns and the leaderboard ranks on it.
  • The turn budget. A cap, not a target. An episode that hits it is recorded as having hit it, not as a failure. It counts turns, not calls: a tool round trip made by the application's own agent continues its turn. A tool-using workload must declare ToolRoundTripsPerTurn: it sets the call ceiling the spend ceiling reserves, MaxTurns * (1 + 2 * ToolRoundTripsPerTurn), and at 0 the ceiling is MaxTurns calls, so a round trip uses up a turn. An episode that catches the cap (context.TurnCapReached) and returns what it had keeps its transcript and artifact.
  • The human. A scripted human is the default and the right one: it sends nothing, costs nothing and says the same thing every run, which is what makes two candidates comparable. Reach for a model-backed persona only when a script genuinely cannot carry the variation, and know that it is priced under its own role.

A workload that declares a human turn, or more than one role, with no human configured anywhere is refused rather than run. See design doc section 3.4.

Step 3. Add the test project and the eval host

Create a test project (tests/Test.Eval or the repository's own convention) that references EF.LLMEval and project-references the production code the workload calls. Never copy a prompt or an agent class into the test project: the value of the sweep is that it measures what production runs, and a copy drifts the first time somebody edits the original.

If live cells share one spend ceiling, turn assembly and class parallelisation off in the test project. Parallel test classes each reserve against the same ceiling and can overshoot it together.

The host over the real composition root

The host builds the application's own service collection per cell and swaps in the clients under test. Two callbacks, and the split between them is the thing to get right:

var host = new EvalHost
{
    Name = "interpretation",

    // Everything that does not look at IChatClient while registering.
    CreateServices = () =>
    {
        var services = new ServiceCollection();
        services.AddApplicationServices(configuration);
        return services;
    },

    ConfigureCell = (services, cell) =>
    {
        cell.AddRoleClients(services);                       // first: the clients under test
        services.AddAiServices(configuration);               // then anything that inspects them
        services.AddDbContext<AppDbContext>(o => o.UseInMemoryDatabase($"cell-{Guid.NewGuid()}"));
        services.AddSingleton<IClock>(new FixedClock(FixedInstant));
    },
};
Registration Where it goes
Adds an IChatClient Either side. The cell registration removes it.
Inspects the collection for an IChatClient while registering (an "add AI services" method that picks a live path when one is present) ConfigureCell, after AddRoleClients, so it sees the clients under test and takes the offline branch.
TryAddKeyedSingleton for a chat client Moves with the code above. Safe on either side.
A plain AddKeyedSingleton for a chat client Never after AddRoleClients. It wins, and the cell talks to the live endpoint.
Everything the harness cannot supply: storage, request or tenant context, configuration, clocks, outbound integrations ConfigureCell. A workload that reaches a real dependency is measuring that dependency's availability alongside the model.

Storage doubles

The harness replaces chat clients and nothing else. Give each cell its own storage, because one container is built per cell and a shared store would make a repeat a second pass over warm state:

  • An in-memory provider with a per-cell database name, as above, is the usual answer for EF Core.
  • An in-memory or fake implementation of the repository interface is better where the workload only reads a fixture.
  • A fixed identity and a fixed clock keep audit fields and any time-dependent prompt stable across cells, which matters more than it sounds: a timestamp in a prompt makes every cached response a miss.

The workload

var workload = new EvalWorkload(
    "explain",
    [new EvalRoleBinding("main", "chat-main"), new EvalRoleBinding("checker", "chat-checker")],
    (provider, variant, ct) =>
        provider.GetRequiredService<InterpretationService>().ExplainAsync(fixture, variant, ct));

The service key in each binding is the key the application resolves its client under. The role name is what a role assignment names a model for.

Discovery

Implement the one-member host source so a tool that never compiled against the application can find the host.

Step 4. Roster and connections

Keep the roster in a JSON file copied to the output directory, not in code: a roster is data that changes when a vendor ships a model, and a code change to add a candidate is friction that stops the field being refreshed.

The file holds connections and the candidate list (or the role assignments for an episode). There is no judge entry: the judge is a file exchange the runner builds from two options, not a connection. The file holds no secret values, only the configuration keys that hold them. Keys come from user secrets and environment variables at load time.

The candidate list is a research output, not a list typed from memory. Read what each connection actually offers, search for what shipped recently in every main family, annotate each entry with its capabilities rather than filtering on them - no candidate is ever excluded over a capability, the unsupported setting is stripped at call time and recorded - and exclude a frontier-priced model only as an explicit price decision written into the roster. Commit a provenance table beside the file with prices, flags, sources and the date each was read; the provenance field on each entry is printed into the report's roster table. The llmeval-harness skill has the procedure.

{
  "connections": {
    "aggregator": {
      "provider": "OpenRouter",
      "auth": "ApiKey",
      "apiKeySecret": "Aggregator:ApiKey",
      "catalog": "openrouter"
    },
    "first-party": {
      "provider": "Foundry",
      "endpointSecret": "FirstParty:Endpoint",
      "auth": "TokenCredential",
      "catalog": "azure-retail"
    }
  },
  "models": [
    { "id": "agg/alpha", "modelId": "vendor-a/alpha-3", "connection": "aggregator",
      "upstreamTag": "vendor-a", "family": "vendor-a", "tags": ["baseline"] },
    { "id": "agg/beta",  "modelId": "vendor-b/beta-2",  "connection": "aggregator",
      "upstreamTag": "vendor-b", "family": "vendor-b", "tags": ["challenger"] },
    { "id": "fp/alpha",  "modelId": "alpha-3-deployment", "connection": "first-party",
      "catalogMatch": "alpha 3", "family": "vendor-a",
      "provenance": "the deployment production runs today" }

}

A setting is a candidate too. The same wire model at reasoning effort low and at high has two prices, two latencies and often two quality levels, so where the research says a setting matters the roster carries the same model more than once:

{
  "models": [
    { "id": "agg/beta", "modelId": "vendor-b/beta-2", "connection": "aggregator",
      "upstreamTag": "vendor-b", "tags": ["challenger", "reasoning-field"] },
    { "id": "agg/beta@effort-low", "modelId": "vendor-b/beta-2", "connection": "aggregator",
      "upstreamTag": "vendor-b", "baseModelId": "agg/beta",
      "requestSettings": { "reasoningEffort": "low" },
      "provenance": "the vendor's guide says low is enough for extraction-shaped work, at a third of the price",
      "tags": ["challenger", "reasoning-field"] },
    { "id": "agg/frontier", "modelId": "vendor-c/frontier", "connection": "aggregator",
      "shortlisted": false,
      "provenance": "cut 2026-09-17: frontier priced at $60/1M output, 30x the incumbent at this call volume" }
  ],
  "settingVariants": [
    { "name": "reasoning-efforts", "tags": ["reasoning-field"],
      "reason": "effort is the cheapest lever on this workload before the model is changed at all",
      "source": "vendor prompting guide, read 2026-09-17",
      "variants": [
        { "label": "effort-low",  "settings": { "reasoningEffort": "low" } },
        { "label": "effort-high", "settings": { "reasoningEffort": "high" } }
      ] }
  ]
}

An entry with requestSettings and baseModelId is a candidate in its own right - its own cells, price line, chart point and table row, grouped under its base model in the report - and must be the same wire model on the same connection as its base, because the two share a client and a rate-limit bucket. settingVariants rules generate the same entries at load from a tag, with their reason and source recorded in each generated entry's provenance. "shortlisted": false keeps an entry in the file without running it, which is how a narrowing round stays reversible. Never put settings on the incumbent: what the application sends today is what it is measured on. See the README's Setting variants for the whole shape.

Five fields earn their place and are easy to leave out by accident:

  • upstreamTag on every aggregator candidate meant to measure one specific upstream. Without it, the same model id is routed across upstreams whose prices differ and the run measures a blend.
  • catalogMatch on every first-party candidate priced from a retail meter list.
  • family on any deployment-name or gateway-alias id. An unplaced family silently disables the same-family warning in the selection report, and it is also the unit researched prompt hints are asked for.
  • requestsPerMinute on any candidate a provider caps tighter than the route, and ProviderConnection.RequestsPerMinute for a whole route.
  • provenance on every entry: why it is in the roster and where its facts came from. It is printed verbatim into the report, so it never carries a key or an endpoint value.

The connection block is written in EF.AI's shape (provider, endpoint / endpointSecret, apiKeySecret, auth, networkTimeout as hh:mm:ss, defaultHeaders, useResponsesApi), so an application registering its production clients from an EFAI:Connections block and this roster describe the same endpoints once.

Keyless and keyed auth

Two shapes, and the loader should support both because a team usually has both:

// Keyed: a secret resolved from user secrets or the environment.
var keyed = new ProviderConnection
{
    Name = "aggregator",
    Provider = EvalProvider.OpenRouter,
    ApiKey = configuration["Aggregator:ApiKey"],
    CatalogName = OpenRouterModelCatalog.DefaultName,
};

// Keyless: whoever is signed in locally. Azure.Identity is the caller's own dependency.
var keyless = new ProviderConnection
{
    Name = "first-party",
    Provider = EvalProvider.Foundry,
    Endpoint = configuration["FirstParty:Endpoint"],
    Auth = EvalAuth.TokenCredential,
    Credential = new DefaultAzureCredential(),
};

Drop, do not fail. A connection with no resolvable key or credential should be dropped at load time, and with it every model and assignment that names it. A developer without one provider's key still gets a usable run over the rest of the field, which is what keeps the harness something people actually run.

Step 5. Catalogs

Wire a catalog per connection, plus a static fallback for anything neither live catalog prices, and enrich the roster before the first sweep. Without a catalog every request goes out exactly as your code built it and every model is priced as unknown.

Enrichment is asynchronous and belongs in the host's prepare step rather than in a constructor: the host runs it at most once per instance, before anything is estimated or sent, dry runs included. Without it, a dry run prices an unenriched roster at nothing.

An unresolvable price stays unknown. The model still runs and is simply left out of the cost ranking. If a model you expect to be priced is not, read its pricing diagnostics: they carry the meter names or upstream tags that were actually on offer.

Step 6. The spend-gated live lane

Split the test project in two.

The offline lane runs in an ordinary local test pass, costs nothing, and proves the harness itself is sound:

  • The probe captures the request options the workload really sends.
  • A prompt variant actually changes what is sent.
  • The spend-ceiling parser is locale-safe (a comma-decimal culture must not turn a 5 into a 5000).
  • The deterministic evaluator both accepts clean input and rejects bad input.
  • The per-cell container builds.

A harness whose own correctness is only established during an expensive run is a harness nobody checks.

The live lane is opt-in, gated on an environment variable with a project-specific prefix (never a bare EVAL, so two harnesses on one machine cannot collide):

internal static class EvalGate
{
    public const string RunVariable      = "MYAPP_RUN_EVAL";
    public const string RequireVariable  = "MYAPP_REQUIRE_EVAL";
    public const string MaxSpendVariable = "MYAPP_EVAL_MAX_SPEND";

    public static void RequireLiveRun()
    {
        if (IsSet(RunVariable)) return;
        if (IsSet(RequireVariable)) Assert.Fail($"{RequireVariable} is set but {RunVariable} is not.");
        Assert.Inconclusive($"Live model evaluation is opt-in. Set {RunVariable}=1 to run it.");
    }
}

Three rules make the gate trustworthy:

  • A live test that finds nothing runnable (no configured key, no model matching a filter) is inconclusive by default and fails when the require variable is set. A missing prerequisite must never read as a passing run.
  • A sweep test itself ends inconclusive with a one-line summary and a pointer to the report. A sweep is a measurement, not an assertion; there is no pass condition for "which model is best".
  • The ceiling is a hard limit, not a starting bid. Set it from the environment variable, keep the default small, and treat a plan refusal as a signal to cut a dimension rather than to raise the number. The refusal message carries the whole breakdown.

Add a cheap single-call smoke test to the live lane as well, ahead of the sweep: it proves the wire mapping (reasoning effort, structured output, tools) actually reaches the provider the way the harness assumes, for a few cents rather than for the cost of a matrix.

Step 7. Evaluators and a rubric as data

At minimum, one deterministic evaluator that checks the property the workload actually cares about. Never rely on a judge alone for the metric a decision rests on.

internal sealed class RequiredSectionsEvaluator : IEvaluator
{
    public const string MetricName = "Required sections";
    public IReadOnlyCollection<string> EvaluationMetricNames => [MetricName];

    public ValueTask<EvaluationResult> EvaluateAsync(
        IEnumerable<ChatMessage> messages, ChatResponse modelResponse,
        ChatConfiguration? chatConfiguration = null,
        IEnumerable<EvaluationContext>? additionalContext = null,
        CancellationToken cancellationToken = default)
    {
        var context = EvalCallContext.Find(additionalContext);   // model plus the recorded call
        // ... inspect modelResponse.Text, return a BooleanMetric with a reason ...
    }
}

For an episode, read the episode context instead: it carries the role assignment, every role's calls and the episode result, including the final artifact your delegate produced. Where an evaluator needs to know what "correct" means for a given input, attach that as evaluation context rather than inferring it from the prompt.

Layer the package's built-ins on top: cost and latency, response completeness (which catches a reasoning model spending its whole allowance on hidden tokens and returning nothing visible), structured-output validity with the required fields named, and output language where it matters.

Keep the rubric as data. It is the sentence that defines "better" for the judge, it is stored with the numbers it produced, and it should be editable without a code change:

"rubric": "Answers the question asked, stays inside the supplied facts, names its uncertainty, and never pads."

A rubric that lives in a string literal is a rubric nobody revises, and a selection report read six months later cannot be checked against the rubric that was actually in force.

Step 8. Baseline and judge

First, ask whether there is an incumbent at all. "Is the model the application currently uses a realistic production candidate?" A harness is usually built over initial plumbing, and making that the incumbent ranks the field by how well it imitates a placeholder. If the answer is no, leave SweepOptions.Baseline and BaselineAssignment null: the sweep attaches RubricScoreEvaluator itself, scores every generation 1 to 5 against SweepOptions.Rubric, and the selection ranks on the mean with a Student t 95% interval, picking the cheapest candidate inside the best candidate's interval. results.json records which instrument was used as selection.basis, and RoundPlanner.PromotedBaseline hands the best of that round to the next one as its incumbent. See Running without a baseline. Record the developer's answer in the roster provenance either way.

The baseline is the incumbent: the model production runs today, or the one you would keep if nothing wins. Name it in the sweep options (for an episode, the incumbent assignment). Its cells run first as one batch, and every other cell is judged against its answer to the same workload, variant and iteration.

The judge is the harness subagent, and nothing configures it beyond where its exchange lives: its model is whichever model the drainer names in its heartbeat - the latest Opus, on Claude Code's opus alias - unless JudgeModelId pins one. What is worth a moment is the incumbent: a candidate from the judge's own vendor family is flagged in the selection report, and that flag is placed from the judge's model. Attach the pairwise evaluator with the rubric and leave the judging out of the budget - it is quota, not money.

var options = new SweepOptions
{
    StorageRootPath = root,
    MaxSpend = ceiling,
    Baseline = incumbent,
    Rubric = rubric,
    JudgeExchangeRoot = "judge-queue",  // default: under StorageRootPath
    Repeats = 3,
    Selection = new SelectionOptions { MinSamples = 6 },
};

Who judges, and who pays

The judge is the Claude Code harness subagent, draining the file exchange, and there is nothing else to select: no API judge, no connection entry, no judge price. Judging is reported as outside the eval's spend, charged to the harness subscription, never as zero and never as free: it consumes that subscription's tokens, and both reports print the judge-answer count beside the spend line. With no drainer online the sweep stops with a reason rather than finding a paid endpoint to use instead. See design doc section 8.

Budget the drainer's time and that subscription's allowance before running: two judge calls per non-incumbent cell, plus one per cell if a rubric score is attached - both times SweepOptions.JudgeReplicates, and the dry run's Judge answers planned line adds them up - plus one per persona turn when the simulated human goes through the same exchange, plus a proposal request per scenario and a hints request per vendor family when those are on. On any matrix of size, the judging is the bulk of the queue: a thousand-cell round is roughly two thousand judge answers.

Step 9. Run it

From Claude Code, with the skills

Three agent skills travel inside the EF.LLMEval package, and building a project that references the package installs them into the consuming repository:

<repository root>/.claude/skills/llmeval-harness
<repository root>/.claude/skills/llmeval-run
<repository root>/.claude/skills/llmeval-focus

Claude Code discovers them there with no further step. Restore alone does not install anything, so the first dotnet build after adding the reference is what does the copy. The package's targets are packed for transitive use as well, so a test project that picks EF.LLMEval up through another project reference installs them too. The repository root is the nearest ancestor holding a .git entry; a checkout that is not a git repository installs nothing unless it is told where to put them.

Property Effect
<LLMEvalInstallSkills>false</LLMEvalInstallSkills> Opt out. The install step is skipped entirely.
<LLMEvalSkillsRoot>path</LLMEvalSkillsRoot> Install into path/.claude/skills instead of the detected repository root. Also the way to install from a checkout with no .git.

The copy only adds and overwrites its own three folders and never deletes anything else under .claude/skills. A destination it cannot write warns and carries on rather than failing the build.

Manual install, as a fallback for an opted-out build, a non-git checkout, or a machine that should not build first: the package ships tools/install-skills.ps1 and tools/install-skills.sh. Each takes the skills from the package it sits in, or the newest ef.llmeval in the NuGet cache, installs into the repository root it finds or into an explicit destination, prints what it did, and exits non-zero on failure.

~/.nuget/packages/ef.llmeval/<version>/tools/install-skills.sh --destination /path/to/repo

Whether to commit the installed .claude/skills/llmeval-* folders or add them to .gitignore is the repository's choice: committing makes them travel to everyone who clones, at the cost of a diff whenever the package version moves. Nothing in the package depends on which you pick.

Skill Use it to
llmeval-harness Build the harness this guide describes, with templates for every file and a verification checklist. It also ships the file a draining subagent is handed.
llmeval-run Run the broad first round of an existing harness: start the drainer, launch the sweep in the background, wait for the summary, read the selection and the HTML report, keep the report and write the findings.
llmeval-focus Run round N+1 seeded from a previous run's results.json: the shortlist per role, the prompt variants that round earned, and the joint casts for a multi-role workflow.

llmeval-run opens with a discussion rather than a launch, and that is deliberate: it prices the matrix with a dry run (SweepOptions.DryRun, over the template's __PREFIX___EVAL_DRY_RUN), which plans and prices every cell and sends nothing - a zero ceiling is not the same thing, since it refuses only an estimate above zero and an unpriced roster would run for real - then states the field as roster, candidates, setting variants and set-aside entries separately ("48 in the roster file: 20 candidates, 14 models plus 6 setting variants, 28 already set aside") and offers the full field, a researched shortlist of the top 10 or 20 per role, or a different ceiling. Nothing runs until that is answered. A shortlist cut is recorded per entry and reversible, and the harness passes EvalConfiguration.SetAside to LeaderboardWriter.WriteAsync so the report prints those entries under roster provenance; see Narrowing the field.

The ordering constraint is not optional. The exchange client blocks on its replies, so a foreground sweep and a drainer in the same session deadlock:

  1. Discuss the field and the ceiling with the developer, and wait for the answer.
  2. Start the drainer first, so a heartbeat naming its model exists before the sweep settles its judge.
  3. Launch the sweep in the background, keeping its log.
  4. Keep draining in a bounded loop until the run's summary file exists.

From a plain test run

Set the opt-in variable, optionally the ceiling and a model filter, and run the live test category. Nothing else is needed: a stopped or interrupted run resumes by being run again, because finished cells replay from cache.

Step 10. Read the report

LeaderboardWriter writes three files into the output directory: summary.md, results.json and report.html, the self-contained HTML report a person reads to choose a model. The report embeds every prompt and every response verbatim, so read the transcripts before committing a copy of it.

summary.md is the one to read first:

Section What to take from it
The leaderboard, one table per workload and variant Ranked by cost per passing generation. A model with zero passes is listed without a cost figure rather than sorted to the bottom by an invented number.
The pacing line How many calls waited on rate limits and for how long, and how many were retried. A large number here means the run was slower than it was expensive.
Banners The run stopped on its ceiling, response caching was on (so latency and the upstream route are not trustworthy for cached cells), or the judging was outside the estimate.
Suggested adjustments One subsection per model that failed something: the deterministic hints and any matching vendor prompting note.
Selection The parity pick, the upgrade pick, dominators, each with pooled sample count, win rate, a per-comparison Wilson interval and a cluster-level interval with its parity flag, plus the judge, the rubric and the thresholds.

Read the selection section with its sample count in view. Below the minimum it reports insufficient samples and names nobody, which is the correct answer and not a bug. With enough samples and nothing over the line it says none qualifies rather than promoting the least-bad candidate.

results.json carries the full report, the same adjustments, and the selection, so a consumer does not have to recompute any of it. Commit a results file when a decision rests on it: it carries no credential and it is the evidence for the choice.

For transcripts, render the underlying reporting store as HTML with the evaluation library's own report tool. The two are meant to be read together: the leaderboard narrows the field, the transcript report explains why.

Step 11. The next round

One broad round ranks a field; it rarely separates the top of it. The second round narrows and deepens, and it is one option plus one number:

SeedFrom = "<the previous run's results.json>",   // null is round 1
TopK = 3,                                         // per role, on top of the incumbent

With SeedFrom set the runner keeps the top TopK per role by cost per pass among the candidates that reached the parity win rate over at least the minimum samples, keeps the incumbent whether or not it made the cut, carries in every admitted proposal and every prompt hint concrete enough to run as a variant bound to the model or family it was learned from, and for a multi-role run builds joint casts capped by MaxJointAssignments instead of a model list. A seed it cannot use - missing, unparseable, nothing judged, narrowing to no model, or measured in the other shape - stops the sweep before anything is sent rather than running the whole roster and calling it a shortlist.

Raise the repeats as the field narrows. That is the point of narrowing: three candidates at six repeats over three fixtures pool eighteen comparisons each, where twelve candidates on the same budget pool four, and four comparisons separate nobody. Every round's provenance is chained into results.json and printed in the HTML report, so a report still reading round 1 means the seed never arrived.

Troubleshooting

Symptom Cause Fix
A plan exception before anything runs The estimated spend exceeds the ceiling Read the breakdown in the message. Narrow the matrix, declare expected output tokens for a role priced at its full ceiling, or raise the ceiling deliberately.
A row says it ran without part of the request The model's catalog entry refuses a member of the probed options, so it was removed before the call Read the record's dropped options. Either the catalog is right and the model cannot take it, or the catalog entry is wrong. The score is real; it is a score for the request as sent.
Price is unknown on a model that should be priced No catalog match or upstream tag, or the meter could not be classified Read the pricing diagnostics for the meter names or upstream tags that were on offer, then correct the match string or the model id.
The sweep hangs on its first cell A foreground sweep deadlocking with a drainer in the same session Start the drainer first, then launch the sweep in the background. With no drainer at all the sweep fails fast instead; if it hangs, check that the heartbeat file is being written.
"No judge agent is draining" Nobody is draining the exchange, or the heartbeat is stale Start the drainer. There is no other judge to fall back to, by design.
Selection says insufficient samples Fewer pooled comparisons than the minimum Add repeats or add fixtures. Adding a variant does not help: it is a different question and gets its own group.
Every cell returns an unreadable judge verdict The drainer is answering with prose, a code fence or a summary Re-read judge-queue.md with it: a verdict is bare JSON in exactly the shape the prompt asks for, and anything else is recorded as unmeasurable.
Latency looks impossibly good Response caching served the cells Caching is on by default. Turn it off for any run that measures latency or run-to-run variance.
The pacing line is missing from the report A decorating client provider did not forward the rate-limit counters Forward them. The member is a default interface implementation, so a decorator that ignores it silently returns nothing.
A cell talked to the live endpoint A plain keyed chat-client registration ran after the cell's clients were registered Move it before, or make it a try-add. See step 3.
An episode completed in one turn and looks suspiciously clean No human simulator, so the conversation ended after its opening turn Configure one. A workload that genuinely never converses says so with an empty script.
A keyless Azure connection fails auth, or its models vanish from the roster The credential chain has nothing to hand it Test the CLI session first (az account get-access-token). A dropped connection takes its models with it, so a short roster is the symptom rather than an error.
The report says round 1 when a round was seeded The seed path never reached SweepOptions.SeedFrom The whole roster ran. Check the gate variable, and do not report the result as a shortlist.
Restoring the package fails The package feed is not configured Add the GitHub Packages feed for the repository, or project-reference during development.

Suggested order

  1. Inventory the call sites and write it down.
  2. Add the test project with the offline lane only, and a scenario or episode over one workload.
  3. Add the host over the real composition root, with storage doubles, and prove the probe captures what you expected.
  4. Add the roster file and the catalogs. Run a dry run: it should price the matrix and send nothing.
  5. Add the spend-gated live lane and a cheap smoke test. Run it.
  6. Add evaluators and the rubric. Run a small sweep with no judge.
  7. Add the baseline and the rubric, start the drainer, and run the real sweep.

Each step leaves something that works, and only steps 5, 7 and beyond spend anything.
