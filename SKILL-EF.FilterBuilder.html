SKILL-EF.FilterBuilder

SKILL: EF.FilterBuilder

What this skill is

This skill teaches you how to construct, reason about, and generate correct FilterSet definitions for EF.FilterBuilder — a C# 14 / .NET 10 library that compiles serializable filter definitions into Expression<Func<T, bool>> predicates targeting IQueryable<T> (EF Core → SQL) and IEnumerable<T> (in-memory).

When a user asks you to build a filter, query, or rule using EF.FilterBuilder, use this skill to generate correct, idiomatic code and JSON. All examples in this skill are verified against the implementation.

Core mental model

FilterSet (serializable JSON)
    │
    ├── Operator: AND | OR
    ├── Filters: [ Filter, Filter, ... ]      ← leaf conditions
    └── FilterSets: [ FilterSet, FilterSet ]  ← nested logical groups (not both)

Filter (single leaf condition)
    ├── PropertyPath   "A.B.C"     dot-delimited navigation path
    ├── Operation      "eq"        comparison operator
    ├── TestValue      object?     right-hand side (when FilterType = Default)
    ├── FilterType     enum        controls where TestValue comes from
    └── FilterSet      FilterSet?  child group — CONTROLS COLLECTION SCOPE

The output is always Expression<Func<T, bool>> — passable directly to .Where() on IQueryable<T> or compiled to a delegate for IEnumerable<T>.

Data model — complete property reference

FilterSet

Property Type Required Notes
Operator Operator (AND|OR) Yes Combines all children at this level
Filters IList<Filter>? One of Leaf conditions. Mutually exclusive with FilterSets at same level
FilterSets IList<FilterSet>? One of Nested logical groups
Sequence int No Sort order for FindFirstMatch. Lower = evaluated first
Name string? No Identifier returned when this FilterSet wins FindFirstMatch
ReferenceValue string? No Supplementary payload (tier code, routing target, etc.)

Rule: A FilterSet must have either Filters OR FilterSets — not both, not neither.

Filter

Property Type Required Notes
PropertyPath string Yes Navigation path to target property. e.g. "Customer.Address.City"
Delimiter string? No Path separator. Defaults to ".". Can be "/", "->", "::", any string
Operation string Yes See operator table below
FilterType FilterType No Defaults to Default (static TestValue)
TestValue object? Conditional RHS value when FilterType = Default. Accepts arrays for in/nin
FilterSet FilterSet? No Controls collection scope (see critical rule below)
ParamKey string? Conditional Key into params1 dict for dynamic RHS strategies
Query string? Conditional Property name (FilterExpression) or JSONPath expr (Json)
TestValueExpression string? No C# expression applied to resolved value. e.g. "Math.Abs(TestValue - 90)"
CaseSensitive bool No Defaults to true. Set false for case-insensitive string matching — both sides lowercased
Normalize bool No Defaults to false. When true, trims whitespace from both sides before comparison

Operators

Comparison — any comparable type

Code Meaning
eq Equal (==)
ne Not equal (!=)
gt Greater than (>)
ge Greater than or equal (>=)
lt Less than (<)
le Less than or equal (<=)

String — string properties only; automatically null-safe

Code Meaning
bw Begins with (StartsWith)
bn Does not begin with (!StartsWith)
ew Ends with (EndsWith)
en Does not end with (!EndsWith)
cn Contains (Contains)
nc Does not contain (!Contains)

String operators respect CaseSensitive and Normalize flags on the Filter.

Membership — TestValue must be an array

Code Meaning Compiled form
in Value is in list new[] { v1, v2 }.Contains(property) → SQL IN (...)
nin Value is NOT in list !new[] { v1, v2 }.Contains(property) → SQL NOT IN (...)

TestValue accepts object[], string[], int[], JSON arrays, or any IEnumerable. Type coercion is applied per element.

Null checks — no TestValue required; do NOT set TestValue for these

Code Meaning SQL
isnull Property IS NULL IS NULL
isnotnull Property IS NOT NULL IS NOT NULL

For non-nullable value types, isnull compiles to false constant and isnotnull to true constant at expression-build time — no runtime check.

Date/time components — DateTime or DateTimeOffset properties only; nullable types are null-guarded automatically

Code Meaning TestValue
year-eq Year component equals integer e.g. 2024
month-eq Month equals (1–12) integer e.g. 3
day-eq Day of month equals (1–31) integer e.g. 15
hour-eq Hour equals (0–23) integer e.g. 9
dow-eq Day of week equals string "Monday"…"Sunday" OR integer 0=Sunday…6=Saturday

EF Core translates each to the native SQL date function (YEAR(), MONTH(), DAY(), DATEPART()).

String length — string properties only; null strings evaluate to false

Code Meaning
len-eq string.Length == value
len-ne string.Length != value
len-gt string.Length > value
len-ge string.Length >= value
len-lt string.Length < value
len-le string.Length <= value

EF Core translates string.Length to LEN() / LENGTH() in SQL.

FilterType enum — dynamic RHS strategies

Value TestValue source SQL output When to use
Default Filter.TestValue literal Constant in WHERE Static value known at authoring time
TestValueParam params1[ParamKey] at call time Constant in WHERE Value varies per request
TestValueFilterExpression Child FilterSet → first match → extract named property Scalar constant in WHERE Single value derived from another collection
TestValueFilterExpressionMulti Child FilterSet → all matches → extract named property from each → typed array WHERE col IN (v1,v2,...) Membership set derived from another collection
TestValueJson JSONPath against JsonDocument in params1 Constant in WHERE Value in JSON config or sensor data

All strategies resolve at expression-build time. EF Core receives a standard Expression<Func<T,bool>> for all of them.

TestValueFilterExpressionMulti constraint: Operation must be "in" or "nin". Using any other operator throws InvalidOperationException at expression-build time.

Large arrays: If the dataset query matches thousands of records, the SQL IN (...) clause grows proportionally. Query plan generation degrades above ~1,000 values. Pre-filter the dataset in params1.

Do not cache expressions built with TestValueFilterExpressionMulti if the underlying dataset changes between calls — the array is a snapshot.

All four strategies converge on a single testValue object before building the expression constant. If TestValueExpression is set, it is evaluated as a C# expression with variable TestValue bound to the resolved value, and the result replaces testValue.

FilterSetType enum — build-time branching

Value Behaviour SQL output
Standard (default) Compiled directly to a predicate Normal WHERE
Branch Evaluates ConditionFilterSet against params1[ConditionParamKey]; compiles BranchIfMatch or BranchIfNoMatch Normal WHERE from selected branch — no conditional in SQL
Switch Evaluates ConditionFilterSet, extracts SwitchValueProperty from first match, compiles first SwitchCase whose WhenValue matches Normal WHERE from selected case — no conditional in SQL

Key constraint: Branch and Switch resolve entirely at expression-build time. EF Core receives a flat Expression<Func<T,bool>>. No Expression.Condition or runtime branching appears in the compiled output.

Condition datasets must be pre-materialized. Pass List<T> in params1. Never pass IQueryable<T> — it bypasses EF Core translation and iterates all rows into memory.

BranchIfNoMatch = null and SwitchDefault = null both compile to Expression.Constant(true) — matches every entity.

Branch and Switch are fully serializable — all properties round-trip through JSON. Branch logic stored in a database changes at data-edit time with zero code changes.

Nesting: Branch and Switch may be nested arbitrarily. A BranchIfMatch can be a Switch; a SwitchCase.Then can be another Branch. The compiler recurses through the same entry point.

FilterSet branching properties

Property Type Used by Notes
FilterSetType FilterSetType All Defaults to Standard
ConditionFilterSet FilterSet? Branch, Switch Condition evaluated against dataset
ConditionParamKey string? Branch, Switch Key to pre-materialized List<T> in params1
BranchIfMatch FilterSet? Branch Compiled when condition matches any element
BranchIfNoMatch FilterSet? Branch Compiled when condition matches nothing. null = match all
SwitchValueProperty string? Switch Property extracted from first condition match
SwitchCases List<FilterSetCase>? Switch Ordered { WhenValue, Then } pairs. First match wins
SwitchDefault FilterSet? Switch Compiled when no case matches. null = match all

Rule 1: Collection scope is determined by child FilterSet presence

When a PropertyPath segment resolves to an IEnumerable<T> property (and is not string):

Child FilterSet PRESENT on the Filter targeting the collection → SAME-OBJECT scope

  • All conditions in the child FilterSet must be satisfied by the same collection element
  • Compiled as a single Any(e => condition1 && condition2 && ...)

Child FilterSet ABSENT → ANY-OBJECT scope

  • Each filter gets its own independent Any() call
  • Different elements can satisfy different conditions
  • Use dot-notation paths like "Tags.Key" to traverse past the collection

This distinction is determined entirely by structure — no flag, no operator, no annotation. Getting this wrong produces silent logic errors where different semantics apply.

// SAME-OBJECT: "a Tag with Key='color' AND Value='red' on the SAME Tag"
new Filter {
    PropertyPath = "Tags",
    Operation    = "eq",
    FilterSet    = new FilterSet {           // child FilterSet present = same-object
        Operator = Operator.AND,
        Filters  = [
            new Filter { PropertyPath = "Key",   Operation = "eq", TestValue = "color" },
            new Filter { PropertyPath = "Value", Operation = "eq", TestValue = "red"   },
        ]
    }
}
// → orders.Where(o => o.Tags.Any(t => t.Key == "color" && t.Value == "red"))

// ANY-OBJECT: "a Tag with Key='color' AND separately a Tag with Value='red' (may differ)"
new FilterSet {
    Operator = Operator.AND,
    Filters  = [
        new Filter { PropertyPath = "Tags.Key",   Operation = "eq", TestValue = "color" },
        new Filter { PropertyPath = "Tags.Value", Operation = "eq", TestValue = "red"   },
    ]
}
// → orders.Where(o => o.Tags.Any(t => t.Key == "color") && o.Tags.Any(t => t.Value == "red"))

Rule 2: Filters and FilterSets are mutually exclusive at each level

A FilterSet node contains either:

  • Filters (leaf conditions) — making it a leaf group
  • FilterSets (nested groups) — making it a branch group

Never both. Use nested FilterSets to build AND/OR trees of arbitrary depth.

// CORRECT — (A AND B) OR (C AND D)
new FilterSet {
    Operator    = Operator.OR,
    FilterSets  = [
        new FilterSet { Operator = Operator.AND, Filters = [ A, B ] },
        new FilterSet { Operator = Operator.AND, Filters = [ C, D ] },
    ]
}

// WRONG — mixing Filters and FilterSets at same level
new FilterSet {
    Operator    = Operator.AND,
    Filters     = [ A ],        // ← do not do this
    FilterSets  = [ ... ],      // ← at the same level
}

Rule 3: Null-safety is automatic

Multi-segment paths are null-checked at every navigation level automatically. "A.B.C.Name" generates null-guards at A, B, and C. No annotation required. Pass enableNullChecks: true (the default) and it just works.

Rule 4: Delimiter is per-Filter, not per-FilterSet

Each Filter independently specifies its delimiter. Different filters in the same FilterSet can use different delimiters. When absent, defaults to ".".

Rule 5: Type coercion is automatic

TestValue is typed as object?. The compiler coerces it to the target property type at build time:

  • Enums: by name string ("Active") or integer value
  • Guid: from string
  • Nullable types: unwrapped automatically
  • Other primitives: via Convert.ChangeType

You do not need to cast TestValue — pass the natural JSON-representable value and the library handles it.

Rule 6: CaseSensitive and Normalize apply only to string properties

CaseSensitive = false lowercases both sides before any string comparison. Normalize = true trims both sides. When both are set, Normalize runs first, then CaseSensitive — so " Smith " → trim → "Smith" → lowercase → "smith". Both flags are silently ignored on non-string properties.

Rule 7: isnull / isnotnull require no TestValue — never set one

Do not set TestValue, FilterType, or any other field when using isnull or isnotnull. The compiler dispatches these before TestValue resolution. Setting TestValue has no effect but may cause type coercion errors on some inputs.

// CORRECT
new Filter { PropertyPath = "DeletedAt", Operation = "isnull" }

// WRONG — TestValue is ignored and may cause confusion
new Filter { PropertyPath = "DeletedAt", Operation = "isnull", TestValue = null }

Rule 8: in / nin TestValue must be an enumerable — never a scalar

If you pass a scalar (e.g. TestValue = "Active"), the compiler throws at build time. Always pass an array or list.

// CORRECT
new Filter { PropertyPath = "Status", Operation = "in", TestValue = new[] { "Active", "Pending" } }

// WRONG — scalar value for in/nin
new Filter { PropertyPath = "Status", Operation = "in", TestValue = "Active" }

Rule 9: Date/time operators only work on DateTime and DateTimeOffset

Applying year-eq, month-eq, day-eq, hour-eq, or dow-eq to a non-date property throws a descriptive InvalidOperationException at expression-build time.

Rule 10: String length operators only work on string properties

Applying len-* operators to a non-string property throws InvalidOperationException at expression-build time. Null string properties evaluate to false for all length comparisons — they do not throw.

Rule 11: Branch and Switch output is always a flat predicate — never conditional

The compiled output of FilterSetType.Branch and FilterSetType.Switch is a normal Expression<Func<T,bool>> with no Expression.Condition at the outermost level. If a proposed implementation produces runtime conditional logic in the expression tree, it is wrong. The branching must be fully resolved before the predicate is constructed.

Rule 12: Condition datasets in params1 must be pre-materialized

For Branch, Switch, TestValueFilterExpression, and TestValueFilterExpressionMulti, any dataset passed in params1 must be a List<T>, array, or other in-memory collection. Never pass IQueryable<T>. The compiler iterates condition datasets as IEnumerable<T> — passing an IQueryable<T> bypasses EF Core query execution and loads all rows into memory.

Rule 13: TestValueFilterExpressionMulti requires Operation = "in" or "nin"

This strategy builds an array and feeds it to the membership operator pipeline. Using any other operator (e.g. "eq", "gt") throws InvalidOperationException at expression-build time with a descriptive message.

Rule 14: Do not cache expressions built with TestValueFilterExpressionMulti if the dataset changes

The array is a snapshot of the dataset state at expression-build time. A cached expression reflects the dataset as it was when the expression was first built. If the underlying dataset changes between calls, rebuild the expression rather than reusing the cache.

Rule 15: SwitchCase.WhenValue comparison is case-insensitive

Switch case matching uses StringComparison.OrdinalIgnoreCase. "VIP", "vip", and "Vip" all match a WhenValue of "VIP". This is intentional — switch values often originate from databases with inconsistent casing.

FilterBuilder<T> (primary public API)

// Compile FilterSet to typed predicate expression
Expression<Func<T, bool>> FilterBuilder<T>.ProcessFilterSet(
    FilterSet filterset,
    bool enableNullChecks = true,
    Dictionary<string, object?>? params1 = null)

// First-match priority evaluation
FilterSet? FilterBuilder<T>.FindFirstMatch(
    ICollection<T> items,
    List<FilterSet> filterSets)   // sorted by Sequence internally

// Example-based FilterSet generation
FilterSet FilterBuilder<T>.BuildFilterSetItem(T example)

IQueryable<T> extension

IQueryable<T> source.ApplyFilters(
    FilterSet? filterSet = null,
    T? filterItem = null,                       // triggers BuildFilterSetItem internally
    bool enableNullChecks = true,
    Dictionary<string, object?>? params1 = null)

JSON serialization format

FilterSet serializes to idiomatic JSON. Property names follow C# PascalCase by default (configure with JsonSerializerOptions as needed). FilterType serializes as the enum name string.

{
  "operator": "AND",
  "filters": [
    {
      "propertyPath": "Status",
      "operation": "eq",
      "testValue": "Active"
    },
    {
      "propertyPath": "Score",
      "operation": "ge",
      "testValue": 80
    }
  ]
}

Complex example with collection scope, dynamic param, and nested logic:

{
  "operator": "AND",
  "filters": [
    {
      "propertyPath": "Tags",
      "operation": "eq",
      "filterSet": {
        "operator": "AND",
        "filters": [
          { "propertyPath": "Key",   "operation": "eq", "testValue": "priority" },
          { "propertyPath": "Value", "operation": "eq", "testValue": "high"     }
        ]
      }
    },
    {
      "propertyPath": "Score",
      "operation":    "ge",
      "filterType":   "TestValueParam",
      "paramKey":     "minScore"
    }
  ]
}

Usage patterns — complete examples

Pattern 1: Simple flat filter

var filter = new FilterSet
{
    Operator = Operator.AND,
    Filters  =
    [
        new Filter { PropertyPath = "IsActive", Operation = "eq", TestValue = true      },
        new Filter { PropertyPath = "Score",    Operation = "ge", TestValue = 75         },
        new Filter { PropertyPath = "Name",     Operation = "cn", TestValue = "Smith"   },
    ]
};

var results = dbContext.Users.ApplyFilters(filter);

Pattern 2: Deep navigation path (auto null-safe)

var filter = new FilterSet
{
    Operator = Operator.AND,
    Filters  =
    [
        new Filter { PropertyPath = "Customer.Address.City",    Operation = "eq", TestValue = "Richmond" },
        new Filter { PropertyPath = "Customer.Address.ZipCode", Operation = "bw", TestValue = "232"      },
    ]
};

Pattern 3: Nested AND/OR

// (Status = 'Active' AND Score >= 80) OR (Status = 'VIP')
var filter = new FilterSet
{
    Operator   = Operator.OR,
    FilterSets =
    [
        new FilterSet
        {
            Operator = Operator.AND,
            Filters  =
            [
                new Filter { PropertyPath = "Status", Operation = "eq", TestValue = "Active" },
                new Filter { PropertyPath = "Score",  Operation = "ge", TestValue = 80       },
            ]
        },
        new FilterSet
        {
            Operator = Operator.AND,
            Filters  = [ new Filter { PropertyPath = "Status", Operation = "eq", TestValue = "VIP" } ]
        }
    ]
};

Pattern 4: Collection filtering — same-object

Use when ALL conditions must match the SAME element in the collection.

// Order must have a Tag where Key = 'color' AND Value = 'red' on THE SAME TAG
var filter = new FilterSet
{
    Operator = Operator.AND,
    Filters  =
    [
        new Filter
        {
            PropertyPath = "Tags",
            Operation    = "eq",
            FilterSet    = new FilterSet          // child FilterSet → same-object scope
            {
                Operator = Operator.AND,
                Filters  =
                [
                    new Filter { PropertyPath = "Key",   Operation = "eq", TestValue = "color" },
                    new Filter { PropertyPath = "Value", Operation = "eq", TestValue = "red"   },
                ]
            }
        }
    ]
};

Pattern 5: Collection filtering — any-object

Use when conditions can be satisfied by DIFFERENT elements in the collection.

// Order has a tag with Key='color' AND (separately) a tag with Value='red' — may be different tags
var filter = new FilterSet
{
    Operator = Operator.AND,
    Filters  =
    [
        new Filter { PropertyPath = "Tags.Key",   Operation = "eq", TestValue = "color" },
        new Filter { PropertyPath = "Tags.Value", Operation = "eq", TestValue = "red"   },
    ]
};

Pattern 6: Runtime parameter

// Strategy: the filter definition carries no hardcoded comparison value.
// The threshold is supplied at call time via params1. The FilterSet itself can
// be stored in a database and reused across requests with different values.
var filter = new FilterSet
{
    Operator = Operator.AND,
    Filters  = [ new Filter {
        PropertyPath = "Price",
        Operation    = "le",
        FilterType   = FilterType.TestValueParam,
        ParamKey     = "maxPrice"   // matches the key in params1 below
    }]
};

var runtimeParams = new Dictionary<string, object?>
{
    ["maxPrice"] = 49.99m
};

var results = dbContext.Products.ApplyFilters(filter, params1: runtimeParams);

Pattern 7: Cross-type dataset query

RHS value is derived by querying a separate typed dataset at expression-build time. The dataset type is completely independent from the entity being filtered. Query names the property to extract from the first matching element.

// PricingRule is an entirely separate type from Product. MaxPrice is the property
// that Query = "MaxPrice" extracts from the first matching rule.
public class PricingRule
{
    public string  Category { get; set; } = "";
    public decimal MaxPrice { get; set; }
}

// Pre-fetch the rules before building the filter. Must be a List<T>, not IQueryable<T>.
var pricingRules = new List<PricingRule>
{
    new() { Category = "Electronics", MaxPrice = 999.00m },
    new() { Category = "Accessories",  MaxPrice = 149.00m },
};

// Strategy: filter products by a price ceiling that comes from a PricingRule, not a
// hardcoded value. At expression-build time, FilterBuilder will:
//   1. Run the child FilterSet against pricingRules → find the rule where Category = 'Electronics'
//   2. Extract MaxPrice from that rule → 999.00m
//   3. Use 999.00m as a constant in the WHERE clause
// EF Core SQL: WHERE Price <= 999.00
var filter = new FilterSet
{
    Operator = Operator.AND,
    Filters  = [ new Filter {
        PropertyPath = "Price",
        Operation    = "le",
        FilterType   = FilterType.TestValueFilterExpression,
        ParamKey     = "rules",        // key into params1 for the dataset
        Query        = "MaxPrice",     // property to extract from the matched PricingRule
        FilterSet    = new FilterSet   // defines which PricingRule to match
        {
            Operator = Operator.AND,
            Filters  = [ new Filter {
                PropertyPath = "Category",
                Operation    = "eq",
                TestValue    = "Electronics"
            }]
        }
    }]
};

var runtimeParams = new Dictionary<string, object?>
{
    ["rules"] = pricingRules   // List<PricingRule> — a completely different type to Product
};

var results = dbContext.Products.ApplyFilters(filter, params1: runtimeParams);

Pattern 8: JSONPath with math transform

// Strategy: comparison value comes from a JSON document field, then a math
// expression is applied before the constant is built. Here the filter matches
// sensors whose reading is within 5 degrees of a target angle from config.
var filter = new FilterSet
{
    Operator = Operator.AND,
    Filters  = [ new Filter {
        PropertyPath        = "Reading",
        Operation           = "le",
        FilterType          = FilterType.TestValueJson,
        ParamKey            = "config",
        Query               = "$.sensor.target",
        TestValueExpression = "Math.Abs(TestValue - 90)"
    }]
};

// jsonDoc is a JsonDocument or JSON string loaded from config, a DB column, etc.
var runtimeParams = new Dictionary<string, object?>
{
    ["config"] = jsonDoc
};

var results = sensors.AsQueryable().ApplyFilters(filter, params1: runtimeParams);

Pattern 9: First-match priority rules

var rules = new List<FilterSet>
{
    new FilterSet {
        Sequence       = 1,
        Name           = "VIP",
        ReferenceValue = "tier-vip",
        Operator       = Operator.AND,
        Filters        = [ new Filter { PropertyPath = "TotalSpend", Operation = "ge", TestValue = 10000m } ]
    },
    new FilterSet {
        Sequence       = 2,
        Name           = "Gold",
        ReferenceValue = "tier-gold",
        Operator       = Operator.AND,
        Filters        = [ new Filter { PropertyPath = "TotalSpend", Operation = "ge", TestValue = 2500m } ]
    },
};

// Rules are sorted by Sequence internally — insertion order does not matter
FilterSet? matched = FilterBuilder<Customer>.FindFirstMatch(customers, rules);
string tier = matched?.ReferenceValue ?? "standard";

Pattern 10: Example-based generation

// Generates a FilterSet from an example object's non-default property values
var example = new Product { Category = "Electronics", IsActive = true };
// Price = 0m → excluded (default), Name = null → excluded (default)

FilterSet filter = FilterBuilder<Product>.BuildFilterSetItem(example);
// Equivalent to: WHERE Category = 'Electronics' AND IsActive = true

var results = dbContext.Products.ApplyFilters(filter);

Pattern 11: Custom delimiter

// All three are semantically identical to "Customer.Address.City"
new Filter { PropertyPath = "Customer/Address/City",   Delimiter = "/",   Operation = "eq", TestValue = "Richmond" }
new Filter { PropertyPath = "Customer->Address->City", Delimiter = "->",  Operation = "eq", TestValue = "Richmond" }
new Filter { PropertyPath = "Customer::Address::City", Delimiter = "::",  Operation = "eq", TestValue = "Richmond" }

// Mixed delimiters in the same FilterSet — each Filter is independent
new FilterSet {
    Operator = Operator.AND,
    Filters  =
    [
        new Filter { PropertyPath = "A/B/Name",   Delimiter = "/",  Operation = "eq", TestValue = "foo" },
        new Filter { PropertyPath = "X::Y::Score", Delimiter = "::", Operation = "gt", TestValue = 0     },
    ]
}

Common mistakes to avoid

Mistake Correct approach
Using both Filters and FilterSets on the same node Choose one. Use FilterSets to compose groups, Filters for leaves
Expecting same-object collection semantics without a child FilterSet Add a child FilterSet to the Filter targeting the collection property
Putting conditions directly on the collection-targeting Filter Conditions targeting collection element properties go inside the child FilterSet
Casting TestValue to the target type Don't — pass the natural value. Type coercion is automatic
Setting ParamKey without setting FilterType FilterType must be TestValueParam, TestValueFilterExpression, TestValueFilterExpressionMulti, or TestValueJson
Using FindFirstMatch and expecting insertion-order evaluation Evaluation order is determined by Sequence value, not list order
Using string method operators on non-string properties String operators only work on string properties
Passing a scalar to in / nin TestValue must be an array — new[] { "Active", "Pending" }
Setting TestValue on isnull / isnotnull No TestValue needed — omit it entirely
Using year-eq / etc. on a non-DateTime property Date component operators only work on DateTime / DateTimeOffset
Using len-* on a non-string property String length operators only work on string properties
Using TestValueFilterExpressionMulti with Operation = "eq" Must use "in" or "nin" — multi-result produces an array
Passing IQueryable<T> as a condition dataset in params1 Must be pre-materialized List<T> — IQueryable<T> bypasses EF Core translation
Caching an expression built with TestValueFilterExpressionMulti when the dataset changes Array is a snapshot — rebuild the expression if the underlying dataset changes
Expecting Branch/Switch to produce conditional SQL Branch and Switch resolve at build time; EF Core receives a flat predicate with no conditional logic
Expecting BranchIfNoMatch = null to throw null is valid — produces Expression.Constant(true) (match everything)

Decision guide — which operator / FilterType to use?

What are you testing?
    ├── Equality / comparison on any type               → eq, ne, gt, ge, lt, le
    ├── String content                                  → bw, bn, ew, en, cn, nc
    │       └── Case-insensitive?                       → add CaseSensitive = false
    │       └── Trim user input first?                  → add Normalize = true
    ├── Membership in a known list                      → in / nin   (TestValue = array)
    ├── Membership in a dynamically-computed set
    │       └── All matches from another collection     → TestValueFilterExpressionMulti + in/nin
    ├── Null / not-null                                 → isnull / isnotnull  (no TestValue)
    ├── Date/time component
    │       ├── Year                                    → year-eq
    │       ├── Month (1–12)                            → month-eq
    │       ├── Day of month (1–31)                     → day-eq
    │       ├── Hour (0–23)                             → hour-eq
    │       └── Day of week                             → dow-eq
    └── String character count                          → len-eq / len-ne / len-gt / len-ge / len-lt / len-le

What is the RHS value source?
    ├── Known at authoring time                         → FilterType.Default
    ├── Supplied per request                            → FilterType.TestValueParam
    ├── First match from another collection             → FilterType.TestValueFilterExpression
    ├── All matches from another collection (array)     → FilterType.TestValueFilterExpressionMulti
    └── JSON document field                             → FilterType.TestValueJson

Does the filter itself need to branch based on context?
    ├── Binary if/else based on whether a condition matches  → FilterSetType.Branch
    ├── Multi-way selection based on an extracted value      → FilterSetType.Switch
    └── No branching                                         → FilterSetType.Standard (default)

Can this be inside FilterBuilder or must it be external?
    ├── Expressible as an EF Core-translatable expression tree  → inside FilterBuilder
    ├── Geo/spatial distance (Haversine)                        → compose externally
    └── Full-text search (CONTAINS, MATCH AGAINST)              → compose externally

Decision guide — same-object vs any-object collection scope?

Do ALL conditions need to match the SAME collection element?
    YES → Put all conditions inside a child FilterSet on the collection-targeting Filter
    NO  → Use dot-notation paths through the collection (no child FilterSet)

Generating FilterSets from natural language

Natural language FilterSet structure
"where X equals Y" Filter { PropertyPath="X", Operation="eq", TestValue=Y }
"where X is greater than Y" Filter { PropertyPath="X", Operation="gt", TestValue=Y }
"where X contains Y" Filter { PropertyPath="X", Operation="cn", TestValue=Y }
"where X contains Y (case-insensitive)" Same + CaseSensitive=false
"where X is one of [A, B, C]" Filter { Operation="in", TestValue=new[]{A,B,C} }
"where X is in the set of [active/matching] values from another collection" FilterType.TestValueFilterExpressionMulti + Operation="in"
"where X is not A, B, or C" Filter { Operation="nin", TestValue=new[]{A,B,C} }
"where X is null / not set" Filter { Operation="isnull" } — no TestValue
"where X is not null / is set" Filter { Operation="isnotnull" } — no TestValue
"where X is non-empty" Filter { Operation="len-gt", TestValue=0 }
"where X has exactly N characters" Filter { Operation="len-eq", TestValue=N }
"records from year Y" Filter { Operation="year-eq", TestValue=Y }
"records from month M" Filter { Operation="month-eq", TestValue=M }
"records on Mondays" Filter { Operation="dow-eq", TestValue="Monday" }
"where A and B" FilterSet { Operator=AND, Filters=[A, B] }
"where A or B" FilterSet { Operator=OR, Filters=[A, B] }
"(A and B) or (C and D)" FilterSet { Operator=OR, FilterSets=[{AND,[A,B]},{AND,[C,D]}] }
"if customer is VIP apply X filter, otherwise apply Y" FilterSetType.Branch
"select filter based on customer tier" FilterSetType.Switch with SwitchValueProperty
"where any Tag has Key='x' and Value='y'" Collection filter with child FilterSet (same-object)
"where there exists a Tag with Key='x' and also a Tag with Value='y'" Any-object scope — two dot-path filters
"ignore case / case-insensitive" Add CaseSensitive=false to any string Filter
"trim whitespace / ignore spaces" Add Normalize=true
"not deleted / active only" Filter { PropertyPath="DeletedAt", Operation="isnull" }
"within X miles / km of location" Cannot be inside FilterBuilder — compose geo predicate externally
"full-text search / contains words" Cannot be inside FilterBuilder — compose via raw SQL

Pattern 12: List membership — in / nin

// Status must be one of the provided values
new Filter { PropertyPath = "Status", Operation = "in",
             TestValue = new[] { "Active", "Pending", "Review" } }

// Exclude specific values
new Filter { PropertyPath = "Status", Operation = "nin",
             TestValue = new[] { "Deleted", "Archived" } }

// JSON representation
// { "propertyPath": "Status", "operation": "in", "testValue": ["Active","Pending","Review"] }

Pattern 13: Null checks

// Soft-delete: only non-deleted records
new Filter { PropertyPath = "DeletedAt", Operation = "isnull" }

// Only records with a linked navigation property
new Filter { PropertyPath = "Customer.Address", Operation = "isnotnull" }

// Compose with other conditions
new FilterSet {
    Operator = Operator.AND,
    Filters  = [
        new Filter { PropertyPath = "DeletedAt", Operation = "isnull" },
        new Filter { PropertyPath = "Status",    Operation = "eq", TestValue = "Active" },
    ]
}

Pattern 14: Date/time component filters

// Orders placed in March of any year
new Filter { PropertyPath = "CreatedAt", Operation = "month-eq", TestValue = 3 }

// Events on Mondays — string name or integer both accepted
new Filter { PropertyPath = "EventDate", Operation = "dow-eq",   TestValue = "Monday" }
new Filter { PropertyPath = "EventDate", Operation = "dow-eq",   TestValue = 1 }

// Records from 2024, in Q1 (AND composition)
new FilterSet {
    Operator = Operator.AND,
    Filters  = [
        new Filter { PropertyPath = "CreatedAt", Operation = "year-eq",  TestValue = 2024 },
        new Filter { PropertyPath = "CreatedAt", Operation = "month-eq", TestValue = 3    },
    ]
}

Pattern 15: String length filters

// Non-empty (null-safe — null string → false, no exception)
new Filter { PropertyPath = "Description", Operation = "len-gt", TestValue = 0 }

// Postal code is exactly 5 characters
new Filter { PropertyPath = "PostalCode", Operation = "len-eq", TestValue = 5 }

// Within a column limit
new Filter { PropertyPath = "Name", Operation = "len-le", TestValue = 100 }

Pattern 16: Case-insensitive and normalised string matching

// Case-insensitive contains
new Filter { PropertyPath = "Name",  Operation = "cn",
             TestValue = "smith", CaseSensitive = false }

// Trim + lowercase — handles messy user input
new Filter { PropertyPath = "Email", Operation = "eq",
             TestValue = "someone@somecompany.com",
             Normalize = true, CaseSensitive = false }

// Non-blank after trimming
new Filter { PropertyPath = "Name", Operation = "len-gt",
             TestValue = 0, Normalize = true }

Pattern 17: Soft-delete base filter (serializable)

// Option A — chain .Where() before ApplyFilters
dbContext.Orders.Where(o => o.DeletedAt == null).ApplyFilters(userFilterSet);

// Option B — compose as nested FilterSet (fully serializable, storable in DB)
var notDeleted = new FilterSet {
    Operator = Operator.AND,
    Filters  = [ new Filter { PropertyPath = "DeletedAt", Operation = "isnull" } ]
};
var combined = new FilterSet {
    Operator   = Operator.AND,
    FilterSets = [ notDeleted, userFilterSet ]
};
dbContext.Orders.ApplyFilters(combined);

Pattern 18: Geo-distance — external composition

FilterBuilder does not include a spatial operator (Haversine cannot be translated to SQL without a spatial database extension). Compose externally:

Expression<Func<Property, bool>> dataFilter =
    FilterBuilder<Property>.ProcessFilterSet(filterSet);

Expression<Func<Property, bool>> geoFilter =
    p => GeoHelper.DistanceKm(p.Latitude, p.Longitude, 37.540, -77.434) <= 32.2;

// Compose with LinqKit — use AsExpandable() on IQueryable
var combined = dataFilter.And(geoFilter);
var results  = dbContext.Properties.AsExpandable().Where(combined).ToList();

// With NetTopologySuite + EF Core spatial extension (SQL Server / PostGIS):
var target = new Point(targetLng, targetLat) { SRID = 4326 };
Expression<Func<Property, bool>> geoFilter =
    p => p.Location != null && p.Location.Distance(target) <= radiusMetres;

Pattern 19: Storing FilterSets in the database

public class FilterRule
{
    public int    Id            { get; set; }
    public string TenantId      { get; set; } = "";
    public int    Sequence      { get; set; }
    public string FilterSetJson { get; set; } = "{}"; // nvarchar(max) / jsonb

    [NotMapped]
    public FilterSet FilterSet
    {
        get => JsonSerializer.Deserialize<FilterSet>(FilterSetJson)!;
        set => FilterSetJson = JsonSerializer.Serialize(value);
    }
}

// Retrieve and apply
var rules = await db.FilterRules
    .Where(r => r.TenantId == tenantId).OrderBy(r => r.Sequence)
    .AsNoTracking().ToListAsync();

FilterSet? matched = FilterBuilder<Customer>
    .FindFirstMatch(customers, rules.Select(r => r.FilterSet).ToList());

Pattern 20: ASP.NET Core — receive FilterSet as request body

app.MapPost("/api/orders/search", async (
    [FromBody] FilterSearchRequest req,
    [FromServices] AppDbContext db, CancellationToken ct) =>
{
    var filtered = db.Orders.ApplyFilters(req.Filter, params1: req.Params);
    var items    = await filtered.Skip((req.Page-1)*req.PageSize).Take(req.PageSize).ToListAsync(ct);
    var total    = await filtered.CountAsync(ct);
    return Results.Ok(new { items, total });
});

Pattern 21: Multi-result dataset query

// Promotion is a separate type tracking which product categories are discounted.
public class Promotion
{
    public int  CategoryId { get; set; }
    public bool IsActive   { get; set; }
}

var promotionList = new List<Promotion>
{
    new() { CategoryId = 1, IsActive = true  },
    new() { CategoryId = 4, IsActive = true  },
    new() { CategoryId = 9, IsActive = false },
    new() { CategoryId = 7, IsActive = true  },
};

// Strategy: filter products to only those in categories with an active promotion.
// At expression-build time, FilterBuilder will:
//   1. Run child FilterSet against promotionList → collect ALL where IsActive = true
//   2. Extract CategoryId from each match → int[] { 1, 4, 7 }
//   3. Compile a membership test against that array
// EF Core SQL: WHERE CategoryId IN (1, 4, 7)
var filter = new FilterSet
{
    Operator = Operator.AND,
    Filters  = [ new Filter {
        PropertyPath = "CategoryId",
        Operation    = "in",                        // must be "in" or "nin"
        FilterType   = FilterType.TestValueFilterExpressionMulti,
        ParamKey     = "promotions",                // key into params1 for the dataset
        Query        = "CategoryId",                // property to extract from each match
        FilterSet    = new FilterSet {
            Operator = Operator.AND,
            Filters  = [ new Filter { PropertyPath = "IsActive",
                                      Operation = "eq", TestValue = true }]
        }
    }]
};

var runtimeParams = new Dictionary<string, object?>
{
    ["promotions"] = promotionList
};

var results = dbContext.Products.ApplyFilters(filter, params1: runtimeParams);

Pattern 22: Branch — binary conditional filter selection

// VipRecord is a simple lookup type. vipList is pre-fetched before the filter runs.
public class VipRecord { public Guid CustomerId { get; set; } }

var vipList = await dbContext.VipRecords.AsNoTracking().ToListAsync();
Guid currentCustomerId = ...; // from session, auth token, etc.

// Strategy: at expression-build time, check whether the current customer appears in
// the vipList. If yes, compile the VIP filter; if no, compile the standard filter.
// EF Core receives a single flat predicate either way — no conditional logic in SQL.
var filter = new FilterSet
{
    FilterSetType      = FilterSetType.Branch,
    ConditionParamKey  = "vipList",              // key into params1 for the lookup dataset
    ConditionFilterSet = new FilterSet {
        Operator = Operator.AND,
        Filters  = [ new Filter {
            PropertyPath = "CustomerId",
            Operation    = "eq",
            FilterType   = FilterType.TestValueParam,
            ParamKey     = "customerId"
        }]
    },
    BranchIfMatch = new FilterSet {              // compiled when customer IS in vipList
        Operator = Operator.AND,
        Filters  = [
            new Filter { PropertyPath = "IsVipEligible", Operation = "eq", TestValue = true },
            new Filter { PropertyPath = "Stock",         Operation = "gt", TestValue = 0    },
        ]
    },
    BranchIfNoMatch = new FilterSet {            // compiled when customer is NOT in vipList
        Operator = Operator.AND,
        Filters  = [ new Filter { PropertyPath = "IsPublic",
                                  Operation = "eq", TestValue = true } ]
    }
};
// EF Core SQL (VIP):      WHERE IsVipEligible = 1 AND Stock > 0
// EF Core SQL (standard): WHERE IsPublic = 1
// Branch decided at build time — no conditional logic in SQL

var runtimeParams = new Dictionary<string, object?>
{
    ["vipList"]    = vipList,           // List<VipRecord> — the lookup dataset
    ["customerId"] = currentCustomerId  // scalar compared against VipRecord.CustomerId
};

var results = dbContext.Products.ApplyFilters(filter, params1: runtimeParams);

Pattern 23: Switch — multi-case filter selection by extracted value

// TierRule maps a customer to a named tier. tierRuleList is pre-fetched before the filter runs.
public class TierRule
{
    public Guid   CustomerId { get; set; }
    public string TierName   { get; set; } = "";  // e.g. "VIP", "Gold", "Standard"
}

var tierRuleList = await dbContext.TierRules.AsNoTracking().ToListAsync();
Guid currentCustomerId = ...; // from session, auth token, etc.

// Strategy: at expression-build time, look up the customer's TierName from tierRuleList,
// then select the matching filter case. EF Core receives a single flat predicate —
// no CASE WHEN in the generated SQL.
var filter = new FilterSet
{
    FilterSetType       = FilterSetType.Switch,
    ConditionParamKey   = "tierRules",           // key into params1 for the lookup dataset
    ConditionFilterSet  = new FilterSet {
        Operator = Operator.AND,
        Filters  = [ new Filter {
            PropertyPath = "CustomerId",
            Operation    = "eq",
            FilterType   = FilterType.TestValueParam,
            ParamKey     = "customerId"
        }]
    },
    SwitchValueProperty = "TierName",            // property to extract from the matched TierRule
    SwitchCases         =
    [
        new FilterSetCase {
            WhenValue = "VIP",       // case-insensitive match
            Then      = new FilterSet {
                Operator = Operator.AND,
                Filters  = [ new Filter { PropertyPath = "IsVipEligible",
                                          Operation = "eq", TestValue = true } ]
            }
        },
        new FilterSetCase {
            WhenValue = "Gold",
            Then      = new FilterSet {
                Operator = Operator.AND,
                Filters  = [ new Filter { PropertyPath = "MinimumOrderValue",
                                          Operation = "le", TestValue = 500m } ]
            }
        },
        new FilterSetCase {
            WhenValue = "Standard",
            Then      = new FilterSet {
                Operator = Operator.AND,
                Filters  = [ new Filter { PropertyPath = "IsPublic",
                                          Operation = "eq", TestValue = true } ]
            }
        },
    ],
    SwitchDefault = new FilterSet {              // no matching tier → return nothing
        Operator = Operator.AND,
        Filters  = [ new Filter { PropertyPath = "Id",
                                  Operation = "eq", TestValue = Guid.Empty } ]
    }
};
// EF Core SQL: flat WHERE from selected case — no CASE WHEN in SQL

var runtimeParams = new Dictionary<string, object?>
{
    ["tierRules"]  = tierRuleList,
    ["customerId"] = currentCustomerId
};

var results = dbContext.Products.ApplyFilters(filter, params1: runtimeParams);

Pattern 24: Nested Branch inside Switch

// Switch selects tier; VIP case itself branches on a feature flag
var vipCase = new FilterSet
{
    FilterSetType      = FilterSetType.Branch,
    ConditionParamKey  = "featureFlags",
    ConditionFilterSet = new FilterSet {
        Operator = Operator.AND,
        Filters  = [ new Filter { PropertyPath = "Flag",
                                  Operation = "eq", TestValue = "PremiumCatalog" }]
    },
    BranchIfMatch   = new FilterSet {  // premium catalog on
        Operator = Operator.AND,
        Filters  = [ new Filter { PropertyPath = "IsPremium",
                                  Operation = "eq", TestValue = true } ]
    },
    BranchIfNoMatch = new FilterSet {  // premium catalog off
        Operator = Operator.AND,
        Filters  = [ new Filter { PropertyPath = "IsVipEligible",
                                  Operation = "eq", TestValue = true } ]
    }
};

var filter = new FilterSet
{
    FilterSetType       = FilterSetType.Switch,
    ConditionParamKey   = "tierRules",
    ConditionFilterSet  = new FilterSet { /* find customer tier */ },
    SwitchValueProperty = "TierName",
    SwitchCases         =
    [
        new FilterSetCase { WhenValue = "VIP",      Then = vipCase            },
        new FilterSetCase { WhenValue = "Standard", Then = new FilterSet { /* ... */ } },
    ]
};
// Compiler recurses through the same ProcessFilterSet entry point for each nested level.
// Final output: a single flat Expression<Func<T,bool>> — EF Core generates normal SQL.
