Cross-node cancel: design note

Cross-node cancel: design note

Status: proposal, not implemented. Decide before coding.

Problem

CancelAsync stops an execution of the instance only when it runs in the calling process. There it flags the execution, which then discards its own outcome. The cancel then adopts the execution's lease and writes Cancelled.

An execution on another node is not reached:

  1. The cancel cannot take the lease that node holds. It writes Cancelled without the lease, through SaveWithRetryAsync.
  2. The other node keeps running nodes, with their side effects, until its next save.
  3. Its final save can overwrite Cancelled. Optimistic concurrency makes that save fail and reload. Whether the reload keeps Cancelled depends on the terminal-status guard in the retry path, not on any cancel protocol.

Options

  1. Cancel marker checked before each save. CancelAsync sets CancelRequestedAt on the record (a new field) when it cannot take the lease. The loop reloads, or reads the marker from the concurrency-failure reload, before each node and each save. On seeing it, the loop stops and writes Cancelled itself.
    • Cost: one field per store schema, and one read per node (or piggyback on existing saves).
    • The holder stays the only writer of the outcome.
    • Latency is bounded by the longest node.
  2. The lease holder is the only writer. Without the lease, CancelAsync writes only the marker and returns a "cancel requested" result. The holder, or the sweep after the lease expires, finishes the cancel.
    • This is option 1 with a stricter contract.
    • CancelAsync can no longer promise a Cancelled snapshot on return, which is a breaking API change.
  3. Broadcast to nodes (pub/sub per instance, for example over the existing intake queue or Redis).
    • Fastest stop.
    • Adds a transport dependency to every deployment.
    • Still needs option 1 for a node that misses the message.

Recommendation

Option 1. Add CancelRequestedAt. Check it:

  • in the loop before each node, using the record the loop already holds plus a cheap re-read when the lease is renewed;
  • in SaveWithRetryAsync's reload: never overwrite a record whose marker is set or whose status is terminal.

CancelAsync keeps writing Cancelled itself when it holds the lease, as it does locally today.

Tests to write with it

  • Two engines sharing one store and lock provider. Cancel on engine A while engine B runs a gated node. B must not run its next node, and the record must end Cancelled.
  • B's final save after the cancel must not overwrite Cancelled.
  • The sweep resuming an instance whose marker is set finishes the cancel and does not run it.
