Cross-node cancel

Cross-node cancel

Status: implemented (the Cancelled record is the stop signal, read by the lease renewal service).

Problem

CancelAsync stops an execution of the instance directly only when it runs in the calling process. There it flags the execution, which then discards its own outcome. The cancel then adopts the execution's lease and writes Cancelled.

An execution on another node holds the lease, so the cancel cannot take it. The cancel writes Cancelled without the lease, through SaveWithRetryAsync. The other node's later saves cannot overwrite it: a save that conflicts reloads the record and adopts a terminal status instead of writing over it. But the other node does not save after every node unless PersistAfterEveryNode is set, so it could keep running nodes, with their side effects, until it suspended or finished.

Design

The Cancelled status written by the cancel is the stop signal; there is no separate marker field.

  • Each pass, LeaseRenewalService renews the leases in parallel, then reads the status and version of every execution whose lease held in one call (IExecutionStateStore.GetStatusesAsync). When a status is terminal, it loads that record, records it on the execution (LocalExecution.FinalizedRecord) and cancels the execution's token, as it does when the lease is lost.
  • The engine loop, stopped that way, saves nothing. It reports the stored outcome to its caller and releases its lease.
  • Child instances are cancelled by the cancel's cascade, each through its own record, so each running child stops the same way on whichever node runs it.

Stop latency: about one LeaseRenewalInterval (13 s by default), sooner when the running node observes its cancellation token. The pass renews up to 16 leases at a time and reads all statuses in one call, so it stays short with many executions. A node that ignores the token finishes its own work, but the loop does not start another node.

Only a final record at a version other than the one the execution last loaded or saved counts: the in-memory store hands the execution its own working object, whose status the loop sets before saving it. For the same reason CancelAsync writes into a copy of the record it loads, so a cancel never lands in an execution's working object (where that execution's next save would persist it as its own, at a version the check then treats as its own).

Cost: one batched status read per renewal interval. SQL, Cosmos, Redis and Azure Table read only status and version (one query, one projected query per 256 ids, one MGET, and two-column point reads); the File store and custom stores without their own implementation load each record. A full record is loaded only for a finalized instance.

Options considered

  1. A CancelRequestedAt field checked before each node. A schema change in every store and a read per node, to stop marginally sooner than the renewal check, which also interrupts the running node.
  2. The lease holder is the only writer. CancelAsync would return "cancel requested" instead of a Cancelled snapshot: a breaking API change.
  3. Broadcast to nodes (pub/sub). A transport dependency for every deployment, and still needs a record check for a node that misses the message.

Tests

CrossNodeCancelTests: two engines share one store, lock provider and registry. A cancel on engine A while engine B runs a gated node; with the node observing its token and with it ignoring the token, B does not run the next node, the record stays Cancelled, and B releases its lease.
