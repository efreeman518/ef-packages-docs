01 What is EF.FilterBuilder?

EF.FilterBuilder is a runtime predicate expression engine. You define filter logic as plain serializable data — a FilterSet object that can be stored as JSON — and the library compiles it into a strongly-typed Expression<Func<T, bool>> at runtime. That expression can be passed directly to IQueryable<T>.Where() for server-side SQL execution, or evaluated in-memory against any IEnumerable<T>.

The key insight is that filter definitions live in data, not code. Adding a new filter rule, changing a comparison value, or reprioritizing rules requires zero code changes and zero redeployment.

Primary use cases: user-configurable search/filter UIs, rule engines driven from a database, multi-tenant filter logic that differs per tenant, A/B testing of filtering strategies, and any scenario where filtering requirements change faster than deployment cycles.

Key capabilities at a glance

02 Architecture

The pipeline has four stages: a serializable definition flows into the compiler, which emits a typed expression tree, which is handed to a query target.

FIG 1 — System architecture pipeline

The public entry point is FilterBuilder<T>, a thin generic wrapper that delegates to the non-generic FilterExpressionBuilder static class. All recursive work — path decomposition, collection detection, RHS resolution — happens in the non-generic core so that runtime types propagate cleanly without MakeGenericMethod overhead.

05 Null-safe Path Decomposition

When PropertyPath contains a delimiter, the compiler splits it into segments and builds a chain of MemberExpression nodes. At each step it asks: is this property nullable? If yes — and null checks are enabled — it wraps the accumulated expression in:

// Conceptually, for each navigation step:
Expression.Condition(
    Expression.Equal(navigationProp, Expression.Constant(null)),
    Expression.Constant(false),   // short-circuit: return false if null
    accumulatedChildExpression
)

This repeats independently at every recursive decomposition level, so a path like "A.B.C.Name" gets null-guarded at A, B, and C — not just the top.

What triggers a null-guard? Either (a) the resolved TestValue is null (navigation-level node, not a leaf comparison), or (b) the operator is a string-method operator (bw, cn, ew, etc.) whose invocation on null would throw.

Null-check injection fires automatically with no developer annotation. The configurable Delimiter property means paths can use any separator — "/", "->", "::" — and per-filter overrides allow different filters in the same FilterSet to use different delimiters.

06 Collection Scope Disambiguation

When path decomposition hits a property that is IEnumerable (and not string), two different semantics are possible. The choice is determined entirely by structure, not by any flag or operator.

FIG 4 — Collection scope disambiguation by structure

This distinction matters a lot. Given a collection of Tag objects with Key and Value properties: same-object scope means "find an item that has a Tag where Key='color' AND Value='red' on the same Tag object." Any-object scope means "find an item that has a Tag with Key='color' AND separately has a Tag with Value='red' — which could be two different Tag objects."

07 Runtime Type-Parameterized Compiler

The non-generic core compiler, FilterExpressionBuilder, accepts Type entityType as a runtime parameter. This means:

  • No compile-time generic constraint at the compiler entry point or any recursive call
  • Collection element types are extracted via GetGenericArguments()[0] and passed through recursion — no MakeGenericMethod
  • The output LambdaExpression is typed at runtime via typeof(Func<,>).MakeGenericType(entityType, typeof(bool))
  • Dataset element types for TestValueFilterExpression strategy flow the same way — the same compiler handles primary and secondary dataset compilation uniformly

The public FilterBuilder<T> class is a thin generic wrapper that casts the output for call-site type safety. All heavy lifting is in the non-generic core.

// Public API — type-safe wrapper
public static class FilterBuilder<T>
{
    public static Expression<Func<T, bool>> ProcessFilterSet(
        FilterSet filterset,
        bool enableNullChecks = true,
        Dictionary<string, object?>? params1 = null)
    {
        // Delegates to non-generic core, casts result
        var lambda = FilterExpressionBuilder.ProcessFilterSet(
            typeof(T), filterset, enableNullChecks, params1 ?? []);
        return (Expression<Func<T, bool>>)lambda;
    }
}

08 Usage — Basic Filtering

The simplest case: filter a list of objects on a flat property.

// Define a filter — this can come from JSON, a database, anywhere
var filterSet = new FilterSet
{
    Operator = Operator.AND,
    Filters =
    [
        new Filter { PropertyPath = "Status",  Operation = "eq", TestValue = "Active" },
        new Filter { PropertyPath = "Score",   Operation = "ge", TestValue = 80 },
    ]
};

// Apply to IQueryable — EF Core translates to SQL
IQueryable<User> results = dbContext.Users.ApplyFilters(filterSet);

// Or apply to an in-memory list
List<User> results = users.AsQueryable().ApplyFilters(filterSet).ToList();

// Or build the expression yourself and use it directly
Expression<Func<User, bool>> predicate =
    FilterBuilder<User>.ProcessFilterSet(filterSet);
List<User> results = users.Where(predicate.Compile()).ToList();

09 Usage — Deep Navigation Paths

Navigation paths are automatically null-safe. Use any delimiter.

// Dot notation (default) — null-checked at Customer, Address, and City
var filter = new Filter
{
    PropertyPath = "Customer.Address.City",
    Operation    = "eq",
    TestValue    = "Richmond"
};

// Arrow delimiter — useful when property names might contain dots
var filter = new Filter
{
    PropertyPath = "Customer->Address->City",
    Delimiter    = "->",
    Operation    = "cn",
    TestValue    = "Rich"
};

// Mixed delimiters in one FilterSet — each Filter is independent
var filterSet = new FilterSet
{
    Operator = Operator.AND,
    Filters  =
    [
        new Filter { PropertyPath = "A/B/C",   Delimiter = "/",  Operation = "eq", TestValue = 1 },
        new Filter { PropertyPath = "X::Y::Z", Delimiter = "::", Operation = "gt", TestValue = 0 },
    ]
};

10 Usage — Collection Filtering

Given an Order with a List<Tag> Tags property, where Tag has Key and Value strings:

// ── Same-object scope ──────────────────────────────────────────────────────
// "Find orders that have a Tag where BOTH Key='color' AND Value='red'
//  on the SAME Tag object."
// Uses child FilterSet → compiled as a single Any(tag => tag.Key == "color" && tag.Value == "red")

var sameObject = new FilterSet
{
    Operator = Operator.AND,
    Filters  =
    [
        new Filter
        {
            PropertyPath = "Tags",
            Operation   = "eq",
            FilterSet   = new FilterSet   // ← child FilterSet = same-object scope
            {
                Operator = Operator.AND,
                Filters  =
                [
                    new Filter { PropertyPath = "Key",   Operation = "eq", TestValue = "color" },
                    new Filter { PropertyPath = "Value", Operation = "eq", TestValue = "red"   },
                ]
            }
        }
    ]
};

// ── Any-object scope ───────────────────────────────────────────────────────
// "Find orders that have a Tag with Key='color' (any tag)
//  AND separately have a Tag with Value='red' (possibly a different tag)."
// No child FilterSet → each Filter gets its own Any()

var anyObject = new FilterSet
{
    Operator = Operator.AND,
    Filters  =
    [
        new Filter { PropertyPath = "Tags.Key",   Operation = "eq", TestValue = "color" },
        new Filter { PropertyPath = "Tags.Value", Operation = "eq", TestValue = "red"   },
    ]
};
The difference is entirely structural. If the child FilterSet is present on the Tags filter, you get correlated same-object semantics. If it's absent and you use dot-notation paths like "Tags.Key", you get independent any-object semantics. No flag, no operator change.

11 Usage — Dynamic RHS Values

// ── Runtime parameter ──────────────────────────────────────────────────────
// Comparison value is supplied at query time, not baked into the filter definition.
var filter = new FilterSet
{
    Operator = Operator.AND,
    Filters  = [ new Filter {
        PropertyPath = "Price", Operation = "le",
        FilterType   = FilterType.TestValueParam,
        ParamKey     = "maxPrice"
    }]
};

var results = dbContext.Products.ApplyFilters(filter, params1: new()
{
    ["maxPrice"] = 49.99m
});

// ── Dataset FilterSet query (cross-type value resolution) ──────────────────
// The right-hand side value comes from querying a DIFFERENT dataset
// using a nested FilterSet compiled and executed at expression-build time.
var filter = new FilterSet
{
    Operator = Operator.AND,
    Filters  = [ new Filter {
        PropertyPath = "Price", Operation = "le",
        FilterType   = FilterType.TestValueFilterExpression,
        ParamKey     = "pricingRules",   // key to the List<PricingRule> dataset
        Query        = "MaxPrice",        // property to extract from matched element
        FilterSet    = new FilterSet       // query to run against pricingRules
        {
            Operator = Operator.AND,
            Filters  = [ new Filter {
                PropertyPath = "Category",
                Operation   = "eq",
                TestValue   = "Electronics"
            }]
        }
    }]
};

var results = products.ApplyFilters(filter, params1: new()
{
    ["pricingRules"] = pricingRulesList   // List<PricingRule> — different type entirely
});

12 Usage — First-Match Priority Rules

The FindFirstMatch method evaluates a list of FilterSets in ascending Sequence order and returns the first one whose predicate any collection item satisfies. This is useful for tiered rule engines: VIP pricing, customer segment assignment, routing logic, etc.

var rules = new List<FilterSet>
{
    new FilterSet
    {
        Sequence = 1, Name = "VIP", ReferenceValue = "tier-vip",
        Operator = Operator.AND,
        Filters  = [ new Filter {
            PropertyPath = "TotalSpend", Operation = "ge", TestValue = 10000m
        }]
    },
    new FilterSet
    {
        Sequence = 2, Name = "Gold", ReferenceValue = "tier-gold",
        Operator = Operator.AND,
        Filters  = [ new Filter {
            PropertyPath = "TotalSpend", Operation = "ge", TestValue = 2500m
        }]
    },
    new FilterSet
    {
        Sequence = 3, Name = "Standard", ReferenceValue = "tier-standard",
        Operator = Operator.AND,
        Filters  = [ new Filter {
            PropertyPath = "TotalSpend", Operation = "ge", TestValue = 0m
        }]
    },
};

// Rules are sorted by Sequence regardless of list order.
// The FIRST rule whose predicate matches any customer wins.
FilterSet? matched = FilterBuilder<Customer>.FindFirstMatch(customers, rules);

if (matched is not null)
{
    Console.WriteLine($"Tier: {matched.Name}, Code: {matched.ReferenceValue}");
    // → "Tier: VIP, Code: tier-vip"  (if any customer has TotalSpend >= 10000)
}

// To reprioritize: update Sequence values in the database.
// No code change, no redeployment.

Example-based FilterSet generation

Pass a typed example object to generate a matching FilterSet automatically. Useful for search-by-example UIs.

var example = new Product { Category = "Electronics", IsActive = true };

// Generates: WHERE Category = 'Electronics' AND IsActive = true
// (all non-default properties become Filter conditions)
var filterSet = FilterBuilder<Product>.BuildFilterSetItem(example);
var results = products.ApplyFilters(filterSet).
Default values are excluded automatically. null reference types, 0 integers, false booleans, and other type defaults are skipped — only properties you've explicitly set on the example become filter conditions.

17 In / Nin — List Membership

Test whether a property value is (or is not) a member of a provided list. TestValue accepts any array type or JSON array. EF Core translates to SQL IN (...).

// Status must be one of the provided values
new Filter { PropertyPath = "Status", Operation = "in",
             TestValue = new[] { "Active", "Pending", "Review" } }

// Exclude specific values
new Filter { PropertyPath = "Status", Operation = "nin",
             TestValue = new[] { "Deleted", "Archived" } }

// Works with integers, GUIDs, or any comparable type
new Filter { PropertyPath = "CategoryId", Operation = "in",
             TestValue = new[] { 1, 4, 7, 12 } }
JSON: "testValue": ["Active","Pending","Review"] — a standard JSON array. Round-trips through serialization without any special handling.

18 IsNull / IsNotNull

Explicit null checks. No TestValue required. EF Core translates to IS NULL / IS NOT NULL. For non-nullable value types the compiler returns a compile-time constant — no runtime check is generated.

// Soft-delete: exclude records with a DeletedAt timestamp
new Filter { PropertyPath = "DeletedAt",        Operation = "isnull"    }

// Only records that have a linked address navigation property
new Filter { PropertyPath = "Customer.Address", Operation = "isnotnull" }

// Combine with other conditions
new FilterSet {
    Operator = Operator.AND,
    Filters  = [
        new Filter { PropertyPath = "DeletedAt", Operation = "isnull"    },
        new Filter { PropertyPath = "Status",    Operation = "eq", TestValue = "Active" },
    ]
}

19 Date/Time Component Operators

Filter on a single component of a DateTime or DateTimeOffset property. EF Core translates each to the native SQL date function (YEAR(), MONTH(), DATEPART() etc.).

new Filter { PropertyPath = "CreatedAt", Operation = "month-eq", TestValue = 3 }

// Records from 2024
new Filter { PropertyPath = "Timestamp", Operation = "year-eq",  TestValue = 2024 }

// Events on Mondays — name or integer both accepted
new Filter { PropertyPath = "EventDate", Operation = "dow-eq",   TestValue = "Monday" }
Nullable DateTime? properties are automatically null-guarded — a null value evaluates to false rather than throwing.

20 String Length Operators

Filter based on the character length of a string property. EF Core translates string.Length to LEN() on SQL Server and LENGTH() on Postgres/SQLite/MySQL. Null strings evaluate to false for all length operators.

// Non-empty description (null-safe)
new Filter { PropertyPath = "Description", Operation = "len-gt", TestValue = 0   }

// Postal code is exactly 5 characters
new Filter { PropertyPath = "PostalCode",  Operation = "len-eq", TestValue = 5   }

// Name within column limit
new Filter { PropertyPath = "Name",        Operation = "len-le", TestValue = 100 }

Available: len-eq, len-ne, len-gt, len-ge, len-lt, len-le.

21 CaseSensitive & Normalize Flags

Two boolean flags on Filter control how string values are prepared before comparison.

CaseSensitive (default: true)

When false, both the property value and TestValue are lowercased before comparison — portable across all databases regardless of collation.

new Filter { PropertyPath = "Email", Operation = "eq",
             TestValue = "[email protected]", CaseSensitive = false }

new Filter { PropertyPath = "Name",  Operation = "cn",
             TestValue = "freeman",         CaseSensitive = false }

Normalize (default: false)

When true, leading and trailing whitespace is trimmed from both sides before comparison. When combined with CaseSensitive = false, trim is applied first then lowercase — so " Freeman " correctly matches "freeman".

new Filter { PropertyPath = "Email", Operation = "eq",
             TestValue    = "[email protected]",
             Normalize    = true,
             CaseSensitive = false }

// Ensure field is non-blank after trimming
new Filter { PropertyPath = "Name", Operation = "len-gt",
             TestValue = 0, Normalize = true }
CaseSensitive defaults to true and Normalize defaults to false. Both fields are optional in serialized JSON.

13 Multi-Result Dataset Query

FilterType.TestValueFilterExpressionMulti extends the cross-type dataset query strategy from single-match scalar extraction to collecting all matching elements and building a typed array for in / nin membership testing. EF Core translates the output to WHERE col IN (...).

IQueryable compatible. The array is built at expression-build time; EF Core receives a standard Enumerable.Contains expression and generates IN (...) SQL. The condition dataset in params1 must be a pre-materialized List<T> — never an IQueryable<T>.
new Filter {
    PropertyPath = "CategoryId",
    Operation    = "in",          // must be "in" or "nin"
    FilterType   = FilterType.TestValueFilterExpressionMulti,
    ParamKey     = "promotions",   // pre-materialized List<Promotion>
    Query        = "CategoryId",   // property extracted from each match
    FilterSet    = new FilterSet {
        Operator = Operator.AND,
        Filters  = [ new Filter {
            PropertyPath = "IsActive", Operation = "eq", TestValue = true
        }]
    }
}

// Build time: run FilterSet against promotions → collect ALL matches
//             → extract CategoryId from each → int[] { 1, 4, 7 }
// EF Core SQL: WHERE CategoryId IN (1, 4, 7)

var results = dbContext.Products.ApplyFilters(filter, params1: new()
{
    ["promotions"] = promotionList   // List<Promotion> — must be pre-materialized
});
Large result sets: The array is a snapshot built at expression-build time. If the dataset query matches thousands of records the IN (...) clause grows proportionally — SQL query plan generation degrades above ~1,000 values. Pre-filter the dataset in params1 if needed. Do not cache the compiled expression if the underlying dataset changes between calls.

14 Build-Time Branching — Branch (if/else)

FilterSetType.Branch evaluates a ConditionFilterSet against a dataset in params1 at expression-build time and compiles either BranchIfMatch or BranchIfNoMatch. EF Core receives a completely flat Expression<Func<T,bool>> — no runtime conditional logic appears in the generated SQL.

IQueryable compatible. Branch selection happens before the expression tree is built. The selected branch compiles to a normal WHERE predicate. The condition dataset must be a pre-materialized List<T> in params1.
var filter = new FilterSet
{
    FilterSetType      = FilterSetType.Branch,
    ConditionParamKey  = "vipList",         // pre-materialized List<VipRecord>
    ConditionFilterSet = new FilterSet {    // does customer appear in vipList?
        Operator = Operator.AND,
        Filters  = [ new Filter {
            PropertyPath = "CustomerId", Operation = "eq",
            FilterType   = FilterType.TestValueParam, ParamKey = "customerId"
        }]
    },
    BranchIfMatch = new FilterSet {         // compiled when VIP found
        Operator = Operator.AND,
        Filters  = [
            new Filter { PropertyPath = "IsVipEligible", Operation = "eq", TestValue = true },
            new Filter { PropertyPath = "Stock",         Operation = "gt", TestValue = 0    },
        ]
    },
    BranchIfNoMatch = new FilterSet {      // compiled when not VIP
        Operator = Operator.AND,
        Filters  = [ new Filter { PropertyPath = "IsPublic",
                                    Operation = "eq", TestValue = true } ]
    }
};

// EF Core SQL (VIP path): WHERE IsVipEligible = 1 AND Stock > 0
// EF Core SQL (standard):  WHERE IsPublic = 1
// Branch decided at build time — SQL has no conditional logic

var results = dbContext.Products.ApplyFilters(filter, params1: new()
{
    ["vipList"]    = vipList,
    ["customerId"] = currentCustomerId
});
BranchIfNoMatch = null produces Expression.Constant(true) — the predicate matches every entity. Use when "no filter" is the correct result when the condition is not met.

15 Build-Time Branching — Switch (multi-case)

FilterSetType.Switch evaluates a ConditionFilterSet, extracts SwitchValueProperty from the first match, and compiles the first SwitchCase whose WhenValue matches. If no case matches, SwitchDefault is compiled. Case comparison is case-insensitive.

IQueryable compatible. Same guarantee as Branch — the selected case compiles to a flat predicate. Condition dataset must be pre-materialized.
var filter = new FilterSet
{
    FilterSetType       = FilterSetType.Switch,
    ConditionParamKey   = "tierRules",        // pre-materialized List<TierRule>
    ConditionFilterSet  = new FilterSet {
        Operator = Operator.AND,
        Filters  = [ new Filter {
            PropertyPath = "CustomerId", Operation = "eq",
            FilterType   = FilterType.TestValueParam, ParamKey = "customerId"
        }]
    },
    SwitchValueProperty = "TierName",         // extract from first match
    SwitchCases         =
    [
        new FilterSetCase { WhenValue = "VIP",
            Then = new FilterSet { Operator = Operator.AND, Filters = [
                new Filter { PropertyPath = "IsVipEligible",
                             Operation = "eq", TestValue = true }] } },
        new FilterSetCase { WhenValue = "Gold",
            Then = new FilterSet { Operator = Operator.AND, Filters = [
                new Filter { PropertyPath = "MinimumOrderValue",
                             Operation = "le", TestValue = 500m }] } },
        new FilterSetCase { WhenValue = "Standard",
            Then = new FilterSet { Operator = Operator.AND, Filters = [
                new Filter { PropertyPath = "IsPublic",
                             Operation = "eq", TestValue = true }] } },
    ],
    SwitchDefault = new FilterSet {             // no tier found — show nothing
        Operator = Operator.AND,
        Filters  = [ new Filter { PropertyPath = "Id",
                                    Operation = "eq", TestValue = Guid.Empty } ]
    }
};
SwitchDefault = null produces Expression.Constant(true) when no case matches — use when "no filter" is correct for an unrecognised value.

16 Build-Time Branching — Nested

Branch and Switch FilterSets may be nested arbitrarily. A BranchIfMatch can be a Switch; a SwitchCase.Then can be another Branch. The compiler recurses through the same entry point — no depth limit. The final compiled output is always a single flat predicate.

var filter = new FilterSet
{
    FilterSetType      = FilterSetType.Branch,
    ConditionParamKey  = "featureFlags",
    ConditionFilterSet = new FilterSet { /* is tiered pricing enabled? */ },
    BranchIfMatch      = new FilterSet    // tiered pricing on → use Switch
    {
        FilterSetType       = FilterSetType.Switch,
        ConditionParamKey   = "tierRules",
        ConditionFilterSet  = new FilterSet { /* find customer tier */ },
        SwitchValueProperty = "TierName",
        SwitchCases         = [ /* VIP, Gold, Standard cases */ ]
    },
    BranchIfNoMatch = new FilterSet {     // tiered pricing off → flat filter
        Operator = Operator.AND,
        Filters  = [ new Filter { PropertyPath = "IsPublic",
                                    Operation = "eq", TestValue = true } ]
    }
};
// Result: a single flat Expression<Func<T,bool>> — EF Core generates normal SQL
Condition datasets must always be pre-materialized. Pass List<T> in params1. Never pass IQueryable<T> as a condition dataset — it bypasses EF Core query translation and iterates all rows into memory.

26 Pattern — Geo-Distance Filtering

FilterBuilder does not include a spatial operator because a Haversine predicate cannot be translated to SQL without a spatial database extension, and the same FilterSet should execute identically on both targets. The correct approach is to compose predicates externally:

// FilterBuilder handles all serializable data-driven conditions
Expression<Func<Property, bool>> dataFilter =
    FilterBuilder<Property>.ProcessFilterSet(filterSet);

// Spatial predicate lives in typed code — developer controls translation strategy
double targetLat = 37.540, targetLng = -77.434, radiusKm = 32.2;

Expression<Func<Property, bool>> geoFilter =
    p => GeoHelper.DistanceKm(p.Latitude, p.Longitude, targetLat, targetLng) <= radiusKm;

// Compose with LinqKit
var combined = dataFilter.And(geoFilter);
var results  = dbContext.Properties.AsExpandable().Where(combined).ToList();

For SQL Server or PostgreSQL/PostGIS with NetTopologySuite, use a Point-typed property — EF Core translates .Distance() to the native spatial SQL function automatically.

var target = new Point(targetLng, targetLat) { SRID = 4326 };

Expression<Func<Property, bool>> geoFilter =
    p => p.Location != null && p.Location.Distance(target) <= radiusMetres;

27 Pattern — Pagination & Sorting

ApplyFilters returns IQueryable<T>, so chaining with OrderBy and paging is natural. Reuse the same filter expression for the count query to avoid round-tripping the full dataset.

var page = 2; var size = 25;

var filtered = dbContext.Orders.ApplyFilters(filterSet, params1: runtimeParams);

var results = await filtered
    .OrderByDescending(o => o.CreatedAt)
    .Skip((page - 1) * size)
    .Take(size)
    .ToListAsync();

var total = await filtered.CountAsync();

28 Pattern — Soft-Delete & Global Base Filters

Apply a mandatory base filter before or alongside the user-supplied FilterSet. The new isnull operator makes this serializable:

// Option A — chain .Where() before ApplyFilters
var results = dbContext.Orders
    .Where(o => o.DeletedAt == null)
    .ApplyFilters(userFilterSet);

// Option B — compose as a nested FilterSet (fully serializable)
var notDeleted = new FilterSet {
    Operator = Operator.AND,
    Filters  = [ new Filter { PropertyPath = "DeletedAt", Operation = "isnull" } ]
};
var combined = new FilterSet {
    Operator   = Operator.AND,
    FilterSets = [ notDeleted, userFilterSet ]
};
var results = dbContext.Orders.ApplyFilters(combined);

29 Pattern — Caching Compiled Expressions

For high-throughput in-memory evaluation, compile the predicate once and cache it by the serialized FilterSet. For IQueryable, cache the Expression<Func<T,bool>> itself — never compile it to a delegate or EF Core cannot translate to SQL.

// In-memory cache — cache the compiled delegate
private static readonly ConcurrentDictionary<string, Func<Order, bool>> _cache = new();

public IEnumerable<Order> Filter(IEnumerable<Order> orders, FilterSet fs)
{
    var key  = JsonSerializer.Serialize(fs);
    var pred = _cache.GetOrAdd(key, _ => FilterBuilder<Order>
                                            .ProcessFilterSet(fs).Compile());
    return orders.Where(pred);
}

// IQueryable cache — cache the expression tree
private static readonly ConcurrentDictionary<string, Expression<Func<Order, bool>>> _exprCache = new();

public IQueryable<Order> Query(IQueryable<Order> source, FilterSet fs)
{
    var key  = JsonSerializer.Serialize(fs);
    var expr = _exprCache.GetOrAdd(key, _ => FilterBuilder<Order>.ProcessFilterSet(fs));
    return source.Where(expr);
}

26 Pattern — Storing FilterSets in a Database

Store serialized FilterSets in a JSON column. EF Core maps this cleanly with a [NotMapped] computed property for deserialization.

public class FilterRule
{
    public int    Id            { get; set; }
    public string TenantId      { get; set; } = "";
    public int    Sequence      { get; set; }
    public string FilterSetJson { get; set; } = "{}"; // nvarchar(max)

    [NotMapped]
    public FilterSet FilterSet
    {
        get => JsonSerializer.Deserialize<FilterSet>(FilterSetJson)!;
        set => FilterSetJson = JsonSerializer.Serialize(value);
    }
}

// Retrieve and apply
var rules = await db.FilterRules
    .Where(r => r.TenantId == tenantId)
    .OrderBy(r => r.Sequence)
    .AsNoTracking().ToListAsync();

FilterSet? matched = FilterBuilder<Customer>
    .FindFirstMatch(customers, rules.Select(r => r.FilterSet).ToList());
On PostgreSQL, use .HasColumnType("jsonb") on the FilterSetJson property for native JSON indexing and querying.

27 Pattern — Multi-Tenancy

Per-tenant filter definitions retrieved at request time, cached in memory, and applied to a scoped DbContext. This is one of FilterBuilder's primary production use cases.

public class FilterService(AppDbContext db)
{
    private readonly ConcurrentDictionary<string, List<FilterSet>> _cache = new();

    public List<FilterSet> GetRules(string tenantId) =>
        _cache.GetOrAdd(tenantId, _ => db.FilterRules
            .Where(r => r.TenantId == tenantId)
            .OrderBy(r => r.Sequence).AsNoTracking().ToList()
            .Select(r => r.FilterSet).ToList());

    public IQueryable<T> Apply<T>(
        IQueryable<T> source, string tenantId, FilterSet? extra = null)
    {
        var rules = GetRules(tenantId);
        var combined = new FilterSet {
            Operator   = Operator.AND,
            FilterSets = extra is null ? rules : [..rules, extra]
        };
        return source.ApplyFilters(combined);
    }
}

28 Pattern — ASP.NET Core Integration

Receive a FilterSet as a JSON request body in a minimal API endpoint. System.Text.Json deserializes the FilterSet directly — no custom converter needed.

app.MapPost("/api/orders/search", async (

    [FromServices] AppDbContext db,
    CancellationToken ct) =>
{

    var items = await filtered
        .Skip((req.Page - 1) * req.PageSize).Take(req.PageSize)

29 Pattern — Testing FilterSets

Unit test filter logic using in-memory evaluation against a fixed dataset. A helper that runs the same FilterSet against both IQueryable and IEnumerable targets catches translation regressions early.

private static readonly List<Customer> _data =

];

[Fact]
public void In_ReturnsOnlyMatchingStatuses()
{

                     TestValue = new[] { "Active" } }
    ]};

}

// Helper: verify IQueryable and IEnumerable produce identical results

    var fromL = list.AsQueryable().ApplyFilters(fs).ToList();
    Assert.Equal(fromQ.Count, fromL.Count);
