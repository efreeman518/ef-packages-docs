FlowEngine-SKILL

SKILL: FlowEngine Workflow Builder

What this skill is

This skill teaches you how to design, construct, validate, and explain FlowEngine workflow definitions — either through natural language conversation with a business user or by generating workflow JSON directly.

FlowEngine is a declarative, serializable workflow engine where:

  • Every workflow is a directed graph of typed nodes connected by conditional edges
  • Every node produces a DecisionOutcome (Match, NoMatch, Unknown, Error, Default)
  • Every edge specifies which outcomes it handles and an optional When predicate
  • The entire workflow definition serializes to JSON and can be stored, versioned, and modified without code changes
  • FilterBuilder is the filter language used inside filter nodes — use the FilterBuilder SKILL in parallel when constructing filter conditions

When a user asks you to design, build, explain, or modify a workflow, use this skill.

Two modes of operation

Mode 1 — Business design conversation

Used when a business user describes what they want in plain language. Your job is to ask the right questions, map answers to node types, draft the workflow JSON, and explain it back in business terms.

Questions to ask before drafting:

  1. What triggers this workflow? (API call, form submission, event, scheduled job)
  2. What data does it start with? (the primary entity)
  3. What decisions does it make, and based on what data?
  4. Who needs to approve or act on things, and when?
  5. What external systems does it call?
  6. What are the failure and rejection paths?
  7. Is there any rework or retry logic? How many times?
  8. What does a successful completion look like?

Do not draft until you have enough answers to cover at least the happy path. Identify gaps and ask about them after presenting the initial draft.

Mode 2 — Technical construction

Used when a developer or agent constructs workflow JSON directly. Use the complete reference below to generate correct, validated JSON. Always write intent fields on every node and the workflow definition itself.

Core mental model

WorkflowDefinition
  ├── entryNodeId         → where all instances start
  ├── nodes               → keyed dictionary of NodeDefinition
  │     each node:
  │       type                → which executor handles it
  │       config              → type-specific settings (JSON)
  │       edges               → ordered list of EdgeDefinition
  │       storeAs             → optional context key for node output
  │       outputSchema        → optional JSON Schema validated against output before storeAs write
  │       contextRequirements → optional map of required context keys (with optional per-key schemas)
  │       intent              → plain-language explanation (required)
  │       maxVisits           → cycle guard (default 100)
  │
  └── edges
        on              → [Match|NoMatch|Unknown|Error|Default] (null = catch-all)
        when            → optional C# predicate expression (see below)
        nextNodeId      → any node in the graph (including backward edges)
        label           → human-readable branch name

Execution context namespaces (JSONPath) — used in `storeAs`, `config` paths, `target`, `valuePath`:
  $.entity            read-only primary entity passed at invocation
  $.entity.Field      nested field access (e.g. $.entity.Order.Total)
  $.params.x          read-only invocation parameters (supports nested: $.params.order.id)
  $.context.x         mutable — written by nodes via storeAs (supports nested: $.context.crmResponse.data.id)
  $.engine.visits.{nodeId}   visit count for a node (read-only)
  $.engine.visits._total     total node executions so far (read-only)
  $.engine.instanceId / workflowId / workflowVersion / status / currentNodeId / createdAt / parentInstanceId / correlationId

when predicate syntax

Edge when predicates are C# expressions evaluated by Roslyn scripting. The following globals are in scope:

Global Type Content
Context IReadOnlyDictionary<string,object?> All $.context.* values
Entity IReadOnlyDictionary<string,object?> $.entity deserialized as object dict
Params IReadOnlyDictionary<string,object?> All $.params.* values
Engine IReadOnlyDictionary<string,object?> instanceId, workflowId, currentNodeId, status, visits dict, totalVisits

Note: createdAt, workflowVersion, parentInstanceId, and correlationId are available via ctx.Resolve("$.engine.createdAt") etc. inside custom node executors, but are not injected into the Engine global for when predicates. Only the keys listed above are accessible as Engine["..."] in edge expressions.

// Equality check on a context value
Context["riskTier"]?.ToString() == "low"

// Numeric comparison
(double)Context["orderTotal"] > 5000

// Null-safe access
Context.ContainsKey("approver") && Context["approver"] != null

// Nested value via string path (context stores deserialized objects)
((System.Text.Json.JsonElement)Context["address"]).GetProperty("country").GetString() == "US"

// Human task response (after quorum)
((System.Text.Json.JsonElement)Context["_humanTaskResponse"]).GetProperty("decision").GetString() == "approved"

// Visit count guard
(int)((Dictionary<string,int>)Engine["visits"])["n-review"] >= 3

Important: when expressions must be valid C# — not JSONPath. Use Context["key"] not $.context.key.

Workflow-level configuration

These fields are declared at the WorkflowDefinition root level, not inside individual nodes.

Field Type Default Purpose
id string required Stable identifier across versions
version string "1.0" SemVer or arbitrary string — combined with id as registry key
label string (id) Human-readable display name
description string? — Prose description of the workflow's purpose
intent string? — AI-routing hint — written same style as node intent
status Draft|Active Draft Only Active workflows can be started; Draft ↔︎ Active transitions allowed
entryNodeId string required First node to execute
paramsSchema string? — JSON Schema (draft-07 subset) validating StartRequest.Params
globalOnFailureNodeId string? — Reroutes any unhandled Error instead of faulting the instance
globalOnDeadlineNodeId string? — Reroutes when the instance-level deadline is exceeded
defaultRetryPolicy RetryPolicy? — Retry policy applied to every node that doesn't declare its own
defaultLeaseDuration TimeSpan? engine default Distributed lock lease duration for this workflow's instances
defaultTags Dictionary<string,string> — Key/value tags automatically merged into every instance
enableCompensation bool false Enable saga rollback — see Saga Compensation section
persistAfterEveryNode bool false Save state after every node, not just at async boundaries — enables crash recovery from last completed node; one extra store write per node

paramsSchema — input validation

paramsSchema holds a JSON Schema string (full draft-07) that validates the params argument on StartRequest before any node executes. Backed by NJsonSchema. Supported keywords include: required, properties, type, enum, minimum, maximum, anyOf, oneOf, $ref (internal), pattern, minLength, maxLength, minItems, maxItems.

When to use: whenever the workflow relies on specific named parameters from the caller and you want fail-fast validation with clear error messages rather than a null-path fault inside a node.

{
  "id": "loan-application",
  "version": "1.0.0",
  "paramsSchema": "{\"required\":[\"applicantId\",\"requestedAmount\"],\"properties\":{\"applicantId\":{\"type\":\"string\"},\"requestedAmount\":{\"type\":\"number\",\"minimum\":1000,\"maximum\":500000}}}",
  "entryNodeId": "n-start",
  "nodes": { "...": "..." }
}

Once validated, params are available in nodes as $.params.applicantId, $.params.requestedAmount, etc.

Designing paramsSchema in conversation mode: when a user describes the workflow inputs (e.g. "the workflow needs an applicant ID and the loan amount"), map those to required properties. Add minimum/maximum for numeric ranges the user describes. Add enum when the user says "it must be one of X, Y, Z".

Retry policy

Set defaultRetryPolicy on the workflow definition to retry failing nodes automatically. Override with retryPolicy on individual nodes; nodes with neither have no automatic retry.

{
  "defaultRetryPolicy": {
    "maxAttempts": 3,
    "backoff": "ExponentialWithJitter",
    "initialDelay": "00:00:01",
    "maxDelay": "00:05:00"
  }
}

Key decisions for workflow authors:

  • backoff: use ExponentialWithJitter for distributed HTTP calls (prevents thundering-herd), Fixed for polling loops with a known cadence.
  • retryOn: defaults to ["Error"]. Add "NoMatch" only if the external service intermittently returns empty results that are genuinely transient.
  • retryOnHttpStatus: defaults to [429, 500, 502, 503, 504]. Narrow this list if the service uses non-standard codes for permanent failures.
  • retryPolicy is in-process and fast (milliseconds to seconds). For durable waits that survive a server restart — e.g. retrying after 10 minutes — model the retry explicitly with a timer node looping back on the error edge instead.

Full field reference and backoff formula details: FlowEngine Design Doc → Retry Policy

DecisionOutcome vocabulary

Every node emits exactly one outcome. Edges match on these:

Outcome Meaning Typical source
Match Condition satisfied / operation succeeded filter (found results), integration (2xx), human (response received)
NoMatch Condition explicitly not satisfied filter (no results), integration (404), decision (value is explicit null)
Unknown Could not determine — missing or null data filter (null/missing target), compute (null result), decision (path not found), transform (missing path)
Error Exception or external failure integration (5xx/timeout), compute (threw), wait (timed out)
Default Catch-all — no other edge matched Any node, last edge with no on

Unknown vs NoMatch: Unknown means the path could not be resolved (key missing from context). NoMatch means the path resolved but the value was null. Always handle Unknown explicitly rather than relying on a Default catch-all — it often means a required upstream step was skipped.

An edge with on: null or no on field matches any outcome — use for unconditional transitions.

Node type reference

filter — FilterBuilder condition check

{
  "type": "filter",
  "intent": "Check whether the order total exceeds the manager approval threshold",
  "config": {
    "target": "$.entity",
    "filterSet": { "operator": "AND", "filters": [
      { "propertyPath": "Total", "operation": "ge", "testValue": 5000 }
    ]}
  },
  "edges": [
    { "label": "Over threshold", "on": ["Match"],   "nextNodeId": "n-manager-approval" },
    { "label": "Under threshold","on": ["NoMatch"],  "nextNodeId": "n-auto-approve"     },
    { "label": "Unknown total",  "on": ["Unknown"],  "nextNodeId": "n-error-handler"    }
  ]
}

Target options:

  • "$.entity" — filter the primary entity (default)
  • "$.context.someObject" — filter a stored context value
  • "$.engine" — filter engine metadata (e.g. visit counts)

For visit-count-based limits (rework, retry):

{
  "target": "$.engine",
  "filterSet": { "operator": "AND", "filters": [
    { "propertyPath": "visits.n-review", "operation": "ge", "testValue": 3 }
  ]}
}

Outcomes: Match, NoMatch, Unknown (null target), Error

Use the FilterBuilder SKILL for constructing FilterSet config.

decision — resolve a context value, branch via When predicates

{
  "type": "decision",
  "intent": "Route based on the risk tier calculated in the previous step",
  "config": { "valuePath": "$.context.riskTier" },
  "edges": [
    { "label": "Low risk",    "on": ["Match"], "when": "Context[\"riskTier\"]?.ToString() == \"low\"",    "nextNodeId": "n-auto-approve"   },
    { "label": "Medium risk", "on": ["Match"], "when": "Context[\"riskTier\"]?.ToString() == \"medium\"", "nextNodeId": "n-underwriter"    },
    { "label": "High risk",   "on": ["Match"], "when": "Context[\"riskTier\"]?.ToString() == \"high\"",   "nextNodeId": "n-committee"      },
    { "label": "Unknown",     "on": ["Unknown", "Default"],                                                "nextNodeId": "n-manual-review"  }
  ]
}

Outcomes: Match (value resolved and non-null — branching done by edge when predicates), NoMatch (value is explicit null), Unknown (path not found in context), Error

store — write a value to context

{
  "type": "store",
  "intent": "Record that this application has been escalated",
  "config": {
    "key":   "escalated",
    "value": "true"
  }
}

value starting with "$." is a JSONPath expression; otherwise a literal string. For computed values use compute instead.

Outcomes: Match (always), Error

compute — Roslyn C# expression

{
  "type": "compute",
  "intent": "Calculate order total including tax and shipping",
  "storeAs": "orderTotal",
  "config": {
    "expression": "(decimal)Context[\"subtotal\"] + (decimal)Context[\"taxAmount\"] + (decimal)Context[\"shippingCost\"]"
  }
}

Two variables in scope:

  • Context — IReadOnlyDictionary<string, object?> of $.context.* values
  • Engine — IReadOnlyDictionary<string, object?> with keys: instanceId, workflowId, currentNodeId, status, visits (dict), totalVisits

Common patterns:

// Increment a counter
(Context.ContainsKey("reworkCount") ? (int)Context["reworkCount"] : 0) + 1

// Sum a collection
((IEnumerable<decimal>)Context["lineAmounts"]).Sum()

// Date arithmetic
DateTime.Parse(Context["applicationDate"].ToString()).AddDays(30)

// Access visit count
(int)((Dictionary<string,int>)Engine["visits"])["n-review"]

Outcomes: Match (non-null result), Unknown (null result), Error

transform — reshape context data

{
  "type": "transform",
  "intent": "Extract the fields needed from the CRM response for downstream nodes",
  "storeAs": "customer",
  "config": {
    "mapping": {
      "customerId":  "$.context.crmResponse.data.id",
      "totalSpend":  "$.context.crmResponse.data.lifetimeValue",
      "tier":        "$.context.crmResponse.data.segment",
      "joinDate":    "$.context.crmResponse.data.createdAt"
    }
  }
}

Unmapped source fields are discarded. Missing source paths produce Unknown.

Outcomes: Match, Unknown (any source path missing), Error

integration — typed external API call

{
  "type": "integration",
  "intent": "Get the current product details including stock level",
  "storeAs": "product",
  "config": {
    "clientRef":   "product-api",
    "integration": "product-details-api",
    "request": {
      "productId": "$.entity.ProductId"
    },
    "responseMapping": {
      "productName":  "$.name",
      "stockLevel":   "$.inventory.available",
      "price":        "$.pricing.basePrice"
    },
    "idempotencyKey": "$.entity.OrderId + '-product-fetch'"
  },
  "edges": [
    { "label": "Got product",    "on": ["Match"],   "nextNodeId": "n-next"  },
    { "label": "Not found",      "on": ["NoMatch"],  "nextNodeId": "n-error" },
    { "label": "API unavailable","on": ["Error"],    "nextNodeId": "n-retry" }
  ]
}

Key rules:

  • clientRef names the registered IRequestResponseClient (required)
  • integration optionally names an IntegrationDefinition overlay for schema validation and outcome mapping
  • request maps context values → integration request fields (JSONPath or literals)
  • responseMapping maps response fields → context keys (JSONPath into response)
  • idempotencyKey prevents duplicate side effects on retry — always set for writes
  • Use integration over fetch whenever a typed client definition exists

fetch — low-level HTTP (use integration when possible)

{
  "type": "fetch",
  "intent": "Call the legacy reporting webhook with the completed order data",
  "config": {
    "method": "POST",
    "url":    "https://legacy.internal.company.com/webhook/order-complete",
    "body":   "{\"orderId\": \"{{$.entity.OrderId}}\", \"total\": {{$.context.orderTotal}}}",
    "headers": { "Content-Type": "application/json" },
    "credentialRef": "legacy-webhook-key",
    "timeoutMs": 5000
  }
}

Outcomes: Match (2xx), NoMatch (404), Error (other 4xx/5xx/timeout)

loop — iterate over a collection

{
  "type": "loop",
  "intent": "Check stock availability for each line item, separating available from backordered",
  "config": {
    "over":          "$.entity.LineItems",
    "itemAs":        "currentItem",
    "indexAs":       "currentIndex",
    "subWorkflowId": "check-line-item-stock",
    "mode":          "Parallel",
    "maxConcurrency": 10,
    "aggregate": {
      "reservedItems":    { "strategy": "collect" },
      "orderSubtotal":    { "strategy": "sum", "sourcePath": "$.output.lineTotal" }
    },
    "errorBehavior": "ContinueOnError"
  },
  "edges": [
    { "label": "All checked", "on": ["Match"], "nextNodeId": "n-next" },
    { "label": "Loop error",  "on": ["Error"], "nextNodeId": "n-error" }
  ]
}

Modes: Sequential (order matters) or Parallel (independent) Aggregation strategies: collect (array — default), sum (numeric), count, first, last Error behavior: StopOnError or ContinueOnError

What storeAs receives: the aggregated result object as specified in the aggregate config. Each key in aggregate becomes a key on the stored object. If no aggregate is configured, storeAs receives an array of each iteration's raw output.

Outcomes: Match (all iterations complete per errorBehavior), Error

workflow — invoke a sub-workflow (local or cross-engine)

{
  "type": "workflow",
  "intent": "Run the standard contract execution sub-workflow now that legal has approved",
  "storeAs": "contractResult",
  "config": {
    "workflowId":   "contract-execution",
    "entityPath":   "$.entity",
    "params": {
      "approvedBy": "$.context.legalReviewer",
      "approvedAt": "$.context.approvalTimestamp"
    },
    "fireAndForget": false
  },
  "edges": [
    { "label": "Executed",              "on": ["Match"], "nextNodeId": "n-notify" },
    { "label": "Sub-workflow faulted",  "on": ["Error"], "nextNodeId": "n-error"  }
  ]
}

fireAndForget: true — parent advances immediately, child runs independently. fireAndForget: false (default) — parent suspends until child reaches terminal state.

What storeAs receives: when the child completes, storeAs is written with the child's outputMapping object. If the child's output node has no outputMapping, the entire child $.context is stored instead. With fireAndForget: true, storeAs is always null — the parent never sees the child's output.

Cross-engine invocation — add clientRef to dispatch to a remote FlowEngine instance:

{
  "type": "workflow",
  "storeAs": "riskResult",
  "config": {
    "clientRef":    "risk-engine",
    "workflowId":   "credit-risk-assessment",
    "entityPath":   "$.entity",
    "params":       { "requestedAmount": "$.entity.LoanAmount" },
    "fireAndForget": false
  }
}

clientRef absent → local engine. clientRef set → dispatched to the named IFlowEngineClient (different deployment, service, or version).

parallel — run multiple sub-workflows concurrently

{
  "type": "parallel",
  "intent": "Run credit, fraud, and inventory checks simultaneously to reduce total latency",
  "config": {
    "branches":       ["credit-check", "fraud-check", "inventory-check"],
    "joinStrategy":   "All",
    "errorBehavior":  "StopAll",
    "branchParams": {
      "credit-check":    { "applicantId": "$.entity.ApplicantId" },
      "fraud-check":     { "applicantId": "$.entity.ApplicantId", "amount": "$.entity.RequestedAmount" },
      "inventory-check": { "productId":   "$.entity.ProductId" }
    }
  },
  "edges": [
    { "label": "All passed", "on": ["Match"], "nextNodeId": "n-evaluate" },
    { "label": "Any failed", "on": ["Error"], "nextNodeId": "n-decline"  }
  ]
}

Join strategies: All (wait for all), FirstOf (resume when any one completes), Threshold (resume when N complete — set joinThreshold)

branchParams collision warning. Keys in branchParams are merged into the parent execution context when branches are joined. If any branchParams key matches an existing $.context.* key, the branch value silently overwrites the existing context value. Use branch-scoped key prefixes (e.g. "creditCheck_applicantId" rather than "applicantId") to avoid collisions when branch params share names with workflow-level context keys.

human — human approval or input task

{
  "type": "human",
  "intent": "Get manager approval for expenses over the auto-approval threshold",
  "config": {
    "title":       "Approve expense report {{$.entity.ReportId}} — ${{$.context.total}}",
    "assignedTo":  "$.context.managerEmail",
    "channel":     "Internal",
    "formSchema":  "{ \"required\": [\"decision\"], \"properties\": { \"decision\": { \"type\": \"string\", \"enum\": [\"approved\", \"rejected\", \"needs-info\"] }, \"notes\": { \"type\": \"string\" } } }",
    "visibleContext": ["$.entity.ReportId", "$.context.lineItems", "$.context.total"],
    "quorum":      1,
    "dueIn":       "P2D"
  },
  "edges": [
    { "label": "Approved",    "on": ["Match"], "when": "((System.Text.Json.JsonElement)Context[\"_humanTaskResponse\"]).GetProperty(\"decision\").GetString() == \"approved\"",   "nextNodeId": "n-process-payment" },
    { "label": "Rejected",    "on": ["Match"], "when": "((System.Text.Json.JsonElement)Context[\"_humanTaskResponse\"]).GetProperty(\"decision\").GetString() == \"rejected\"",   "nextNodeId": "n-notify-rejected" },
    { "label": "Needs info",  "on": ["Match"], "when": "((System.Text.Json.JsonElement)Context[\"_humanTaskResponse\"]).GetProperty(\"decision\").GetString() == \"needs-info\"", "nextNodeId": "n-request-info"    }
  ]
}

Key fields:

  • title — supports {{$.context.key}} and {{$.entity.field}} template interpolation
  • assignedTo — one of:
    • Direct JSONPath: "$.context.reviewerEmail" (resolved to string value)
    • Role reference: "role:managers" or "user:alice@co.com"
    • Template: "role:{{$.context.tier}}-counsel" (interpolated)
  • channel — Internal (task queue) or External (notification with response link)
  • formSchema — JSON Schema string. Required fields are validated on submission. Response available at $.context._humanTaskResponse
  • visibleContext — list of plain keys ("total") or JSONPath expressions ("$.entity.ReportId", "$.context.lineItems") — all resolved into the context snapshot sent to the form
  • quorum — number of responses needed before resuming (default 1)
  • dueIn — ISO 8601 duration, e.g. "P2D" (2 days), "PT4H" (4 hours)
  • onTimeoutNodeId — node to route to if deadline elapses before quorum. When omitted, instance transitions to TimedOut.
  • escalation — { "after": "PT8H", "reassignTo": "role:senior-managers" }

Response context keys written on resume:

Key When Content
$.context._humanTaskResponse Always First/only respondent's form values (JSON object)
$.context._humanTaskResponses quorum > 1 Array of all respondents' form values
$.context._humanTaskConsensus quorum > 1 "unanimous" / "majority" / "any-denied" / "split"

Outcomes: always Match when quorum reached; Error on timeout (if onTimeoutNodeId not set, instance transitions to TimedOut instead).

Quorum = 1 edge pattern (standard):

{ "label": "Approved", "on": ["Match"], "when": "((System.Text.Json.JsonElement)Context[\"_humanTaskResponse\"]).GetProperty(\"decision\").GetString() == \"approved\"", "nextNodeId": "n-next" }

Quorum > 1 edge pattern (committee voting):

{ "label": "All approved", "on": ["Match"], "when": "Context[\"_humanTaskConsensus\"]?.ToString() == \"unanimous\"",  "nextNodeId": "n-approve"  },
{ "label": "Any denied",   "on": ["Match"], "when": "Context[\"_humanTaskConsensus\"]?.ToString() == \"any-denied\"", "nextNodeId": "n-deny"     },
{ "label": "Split",        "on": ["Match"], "when": "Context[\"_humanTaskConsensus\"]?.ToString() == \"split\"",      "nextNodeId": "n-escalate" }

wait — suspend until an external signal

{
  "type": "wait",
  "intent": "Pause until the customer confirms their email address",
  "config": {
    "eventName":          "email.confirmed",
    "correlationKeyPath": "$.entity.CustomerId",
    "timeout":            "P7D",
    "minSignalCount":     1
  },
  "edges": [
    { "label": "Confirmed",  "on": ["Match"], "nextNodeId": "n-activate-account" },
    { "label": "Timed out",  "on": ["Error"], "nextNodeId": "n-send-reminder"    }
  ]
}

Correlation key fields (one required):

  • correlationKeyPath — JSONPath resolved at suspend time: "$.entity.OrderId" → "ORD-1234"
  • correlationKeyExpression — Roslyn expression for computed keys: "Entity[\"EmployeeId\"] + \"-\" + Context[\"currentItem\"][\"CourseId\"]" Use when the correlation key cannot be expressed as a simple field lookup.

Signal delivery: POST /instances/{id}/signal with { "eventName": "...", "correlationKey": "..." } minSignalCount > 1 — accumulate N signals before resuming (e.g. N lab readings, committee votes)

Signal payload available after resume:

  • $.context._signal — most recent payload
  • $.context._signals — array of all accumulated payloads (when minSignalCount > 1)

Outcomes: Match (signal received), Error (timed out)

query — FilterBuilder query against a named data source

{
  "id":    "n-fetch-open-disputes",
  "type":  "query",
  "label": "Fetch open disputes for this customer",
  "intent": "Check CRM for open disputes. More than 2 routes to manual review regardless of credit score.",
  "storeAs": "openDisputes",
  "config": {
    "clientRef":  "crm-db",
    "entityType": "Dispute",
    "resultMode": "all",
    "filterSet": {
      "operator": "AND",
      "filters": [
        { "propertyPath": "CustomerId", "operation": "eq",
          "filterType": "TestValueParam", "paramKey": "customerId" },
        { "propertyPath": "Status", "operation": "in",
          "testValue": ["Open", "UnderReview"] }
      ]
    },
    "params": { "customerId": "$.entity.CustomerId" },
    "orderBy": [{ "property": "CreatedAt", "direction": "desc" }],
    "take": 100
  },
  "edges": [
    { "label": "Got results", "on": ["Match"], "nextNodeId": "n-check-count" },
    { "label": "Query failed","on": ["Error"], "nextNodeId": "n-error" }
  ]
}

resultMode options:

Mode Returns Outcome emitted Use case
all Array of entities Match (always) Get collection for downstream filter/loop
first Single entity or null Match (found), NoMatch (not found) Look up specific record
count Integer Match (always) How many? Use compute/filter on stored count
any Boolean Match (found), NoMatch (none) Does any exist? Most efficient — uses EXISTS
page { items, totalCount, hasMore } Match Large datasets with pagination

Key rule: query fetches data. filter evaluates it. They compose:

query (resultMode: all → storeAs: disputes) → filter (target: $.context.disputes) → branch

For yes/no checks, use resultMode: any to skip the filter node entirely.

Use FilterBuilder SKILL to construct the filterSet inside a query node.

agent — call an AI agent, LLM, or agent workflow

{
  "id":    "n-extract-contract-terms",
  "type":  "agent",
  "label": "Extract contract terms",
  "intent": "Use GPT-4o via Microsoft Foundry to extract structured terms from the uploaded contract. Output is validated against schema before storing.",
  "storeAs": "contractTerms",
  "config": {
    "clientRef":      "gpt4o",
    "promptTemplate": "Extract the key terms from this contract and return valid JSON matching the output schema. Contract: {{contractText}}",
    "input": {
      "contractText": "$.context.contractDocument.text",
      "contractType": "$.entity.ContractType"
    },
    "outputSchema": "{ \"parties\": { \"type\": \"array\" }, \"effectiveDate\": { \"type\": \"string\" }, \"value\": { \"type\": \"number\" } }",
    "timeoutMs": 45000
  },
  "edges": [
    { "label": "Extracted",        "on": ["Match"], "nextNodeId": "n-validate-terms" },
    { "label": "Agent failed",     "on": ["Error"], "nextNodeId": "n-manual-extract" }
  ]
}

Key design: the agent node doesn't know about models, temperature, or providers. Those are configured on the registered IAgentClient by the developer. The workflow only specifies what to ask (promptTemplate) and what to do with the answer (storeAs).

Two layers of output schema for agent nodes:

  • config.outputSchema (inside AgentNodeConfig) — forwarded to the IAgentClient to guide the LLM toward structured output (model-side enforcement)
  • outputSchema (on the NodeDefinition) — validated by the engine before writing to context (engine-side enforcement)

Set both to the same schema string when you want the LLM to produce the right shape and the engine to reject it if it doesn't.

Additional AgentNodeConfig fields:

Field Type Purpose

contentFilterPolicy string? Name of a registered IContentFilter — runs pre-call (FilterInputAsync) and post-call (FilterOutputAsync). Returns Error if blocked.
promptVersion string? Label stored in NodeExecutionRecord.Metadata["promptVersion"] for A/B tracking

No external signal, no harness code. The sweep service resumes the instance automatically when the delay elapses.

When to use timer vs wait:

Need Use
Wait a fixed time then continue timer — no harness code
Wait for an external event to arrive wait — harness calls ResumeAsync
Wait up to X time for an event, then error wait with timeout
Delay between loop iterations timer inside sub-workflow

checkpoint — force mid-chain state persistence

{
  "id":    "n-checkpoint-1",
  "type":  "checkpoint",
  "label": "Persist before payment chain",
  "intent": "Force a state store write here. Credit scoring above is expensive — crash recovery resumes from this point rather than re-running scoring.",
  "edges": [
    { "on": ["Match"], "nextNodeId": "n-charge-card" }
  ]
}

No config. Always returns Match. The engine saves full execution state immediately after this node, then continues without releasing the claim.

When to use:

  • Before a chain of write operations (charge → allocate → ship) — even with idempotency keys, re-running an entire chain is wasteful and error-prone
  • After expensive compute (scoring, ML inference, agent calls) you don't want to repeat on crash recovery
  • Before loop or parallel nodes that spawn many child instances

When NOT to use:

  • Between every node — every checkpoint is a state store round-trip; use at meaningful boundaries only
  • As a substitute for idempotency keys — always implement idempotency on write nodes regardless

Alternative — workflow-level persistAfterEveryNode: instead of scattering checkpoint nodes, set persistAfterEveryNode: true on the WorkflowDefinition. The engine then saves after every node automatically. Nodes that already emit ForceCheckpoint are not double-saved. Recommended only for workflows with low node counts or where state store write cost is acceptable; checkpoint placement is still preferred for high-throughput workflows.

Outcomes: Match (always).

  "type": "human",
  "intent": "Underwriter reviews the application and either approves, rejects, or requests rework",
  "maxVisits": 10,

Saga compensation pattern

Use when the workflow executes a chain of side-effecting steps (reserve inventory, charge payment, book shipping) that all need to roll back if any one fails — the classic distributed saga.

Business conversation guide:

User says What to ask / design
"If payment fails, we need to release the inventory reservation" Each forward step needs a compensationNodeId pointing to its undo node
"Rollback in reverse order if anything fails" Set enableCompensation: true on the workflow
"The undo for 'charge payment' is 'refund payment'" Map each step to its compensation node: "compensationNodeId": "n-refund-payment"
"What about steps that don't need rollback?" Leave compensationNodeId absent — the engine skips those steps during compensation
"What happens after all the undos run?" Engine routes to globalOnFailureNodeId (if set) or faults the instance

Structural template:

{
  "id": "order-saga", "version": "1.0.0",
  "enableCompensation": true,
  "globalOnFailureNodeId": "n-saga-failed",
  "nodes": {
    "n-reserve-inventory": {
      "type": "integration",
      "compensationNodeId": "n-release-inventory",
      "config": { "clientRef": "inventory-api", ... },
      "edges": [{ "on": ["Match"], "nextNodeId": "n-charge-payment" },
                { "on": ["Error"], "nextNodeId": "n-saga-failed" }]
    },
    "n-charge-payment": {
      "type": "integration",
      "compensationNodeId": "n-refund-payment",
      "config": { "clientRef": "payment-api", ... },
      "edges": [{ "on": ["Match"], "nextNodeId": "n-ship-order" },
                { "on": ["Error"], "nextNodeId": "n-saga-failed" }]
    },
    "n-ship-order": {
      "type": "integration",
      "config": { "clientRef": "shipping-api", ... },
      "edges": [{ "on": ["Match"], "nextNodeId": "n-completed" }]
    },
    "n-release-inventory": { "type": "integration", "config": { ... } },
    "n-refund-payment":    { "type": "integration", "config": { ... } },
    "n-completed":         { "type": "output", ... },
    "n-saga-failed":       { "type": "output", ... }
  }
}

Rules:

  • globalOnFailureNodeId is required when enableCompensation: true — without it, the instance faults with no notification node
  • Compensation nodes should be idempotent — the engine may execute them more than once on crash recovery
  • Compensation nodes themselves do not have compensationNodeId — avoid compensation-of-compensation chains
  • parallel node: when errorBehavior: StopAll and enableCompensation: true, compensation runs for already-completed branches automatically

Workflow version lifecycle

For AI agents helping manage workflow definitions.

Status states

Status Can be started Can be edited Can be deleted Notes
Draft No Yes Yes Default on SaveAsync; safe to iterate
Active Yes No No Immutable once active — transition back to Draft to edit, or create a new version
Archived No No No Retired; no new instances may start. In-flight instances continue normally. Unarchive to Active if re-activation needed.

Allowed transitions: Draft ↔︎ Active, Active → Archived, Archived → Active. Draft → Archived is not permitted (publish first).

Updating a workflow in conversation

When a user asks to change a running workflow:

  1. "Update the workflow / change a rule / add a step"

    • Load existing JSON, change what's needed, save as a new version (e.g. 2.0.0)
    • Activate the new version with TransitionStatusAsync(id, "2.0.0", Active)
    • Transition the old version back to Draft after migrating or draining suspended instances — this prevents new starts without affecting in-flight ones
    • Never edit an Active definition — it is immutable; transition to Draft first

  2. "What about instances already running on the old version?"

    • In-flight instances are pinned to the version they started on — they complete unchanged
    • If the user wants to move suspended instances to the new version, use MigrateInstanceAsync
    • Before migrating, run CompatibilityAnalyzer.Analyze(v1, v2) to surface breaking changes (removed nodes, missing edge targets, entry node changes)
    • Use dryRun: true to validate the node remapping without persisting — safe to call on live instances
    • Only migrate when the new version is backward-compatible at the current suspension point

  3. "Delete the old version"

    • Only safe when no instances remain in Running or Suspended status on that version
    • DeleteWorkflowVersionAsync will throw if live instances exist

Node ID remapping during migration

If node IDs changed between versions, pass a nodeIdMap:

// Production migration
await engine.MigrateInstanceAsync(instanceId, "2.0.0",
    nodeIdMap: new Dictionary<string, string>
    {
        ["n-old-approval-step"] = "n-manager-approval"
    });

// Dry-run — validates remapping; history entry labeled "[dry-run]"; does NOT persist
await engine.MigrateInstanceAsync(instanceId, "2.0.0",
    nodeIdMap: new Dictionary<string, string>
    {
        ["n-old-approval-step"] = "n-manager-approval"
    },
    dryRun: true);

Unmapped node IDs are assumed identical between versions.

Pre-migration compatibility check

var report = CompatibilityAnalyzer.Analyze(v1Definition, v2Definition);
if (report.Findings.Any(f => f.Severity == FindingSeverity.Breaking))
{
    // Do not migrate — breaking changes detected
    foreach (var f in report.Findings)
        logger.LogWarning("[{severity}] {message}", f.Severity, f.Message);
}

Finding Severity
Node removed Breaking
Node type changed Breaking
Missing edge target Breaking
New contextRequirements key on an existing node Breaking
compensationNodeId references a node absent in the target Breaking
Entry node changed Warning
GlobalOnFailureNodeId changed Warning
StoreAs key renamed Warning

Common mistakes to avoid

Mistake Correct approach
No output node — instance never completes Every workflow must have at least one output node reachable from the entry node
Backward edge with no maxVisits adjustment Set maxVisits on nodes in cycles safely above the business limit
human node edges that don't cover all form responses Missing response branches leave the instance unrouted — add a Default catch-all edge
integration node without idempotencyKey on writes Any POST/PUT/DELETE call must have idempotencyKey to prevent double-execution on retry
when predicate on an edge with no on field when only evaluates after outcome matches — add "on": null for a when-only edge
Using $.context.* directly in a filter node config Set "target": "$.context.myObject" — don't reference context paths inside the filterSet itself
Parallel branches without explicit joinStrategy Default is All — explicitly set joinStrategy when you want FirstOf or Threshold
workflow node fireAndForget: true with storeAs FireAndForget parent never sees child output — storeAs will always be null
Missing intent field Always write intent on every node and the workflow definition
Credentials or connection strings in workflow JSON Use clientRef pointing to a registered IFlowClient — never embed secrets
query node for a yes/no check returning all results Use resultMode: any — translates to EXISTS, no data transfer, emits Match/NoMatch directly
filter node targeting a database table filter is in-memory only — use query first, then filter on the stored results
outputSchema set on a node without storeAs Schema validation only runs when storeAs is also set — the validator warns at registration time
outputSchema on agent node but only in config (AgentNodeConfig) AgentNodeConfig.outputSchema shapes the LLM prompt; NodeDefinition.outputSchema enforces the shape engine-side — set both
contextRequirements key names include $.context. prefix Use bare key names (e.g. "apiResult" not "$.context.apiResult") — same convention as storeAs
agent node with model/temperature config in workflow JSON Model config belongs on the registered IAgentClient, not in the workflow definition
agent node with contentFilterPolicy but no IContentFilter registered contentFilterPolicy names a registered filter — if the name can't be resolved, the node faults at execution time
compute node or when edge predicate on an engine with AllowComputeNodes = false or AllowWhenExpressions = false StartAsync throws ArgumentException — check the engine's security policy before authoring Roslyn expressions
message node deliveryMode: RequestReply without replyEventName RequestReply suspends waiting for a signal — replyEventName is required to match it
Migrating instances without running CompatibilityAnalyzer first Always call CompatibilityAnalyzer.Analyze(from, to) before bulk migration — breaking findings mean suspended instances would be stranded
Assuming MigrateInstanceAsync is safe without testing it Use dryRun: true first — it validates the remapping without persisting and records a [dry-run] history entry
wait node without a timeout Always set timeout — an indefinitely suspended instance is a resource leak and an ops nightmare
Using $.context._humanTaskResponse in a non-human node _humanTaskResponse is only written by the human node executor — not available after other node types
workflow node cross-engine without clientRef registered Pre-execution validation will throw MissingClientException — register the client before first invocation
query node with TestValueParam filters but no params mapping TestValueParam filters need their values resolved from context via the params dict
Signal payload fields accessed before checking _signal is set $.context._signal is only populated after a wait or message RequestReply resumes — guard with a null check or filter
loop node mode: Parallel with errorBehavior: StopOnError on high-volume collections Parallel + StopOnError cancels all in-flight children on first failure — use ContinueOnError if partial results are acceptable
Write operation (integration POST/PUT/DELETE, message) without idempotencyKey Crash recovery re-executes the chain — without idempotency keys you get double-charges, double-sends, duplicate records
Assuming state is saved after every node By default, state saves at async boundaries only (wait, human, output, checkpoint) — a crash mid-chain re-runs all nodes since the last save. Set persistAfterEveryNode: true on the WorkflowDefinition to opt in to per-node saves at the cost of extra store writes.
Checkpoint as a substitute for idempotency keys Checkpoint reduces re-execution window but a crash can still happen after the checkpoint and before the next save — write nodes must be idempotent regardless
Checkpoint between every node Every checkpoint is a state store round-trip — place at meaningful boundaries only (before expensive compute, before write chains, before loop/parallel spawning)

Engine operational notes

Host shutdown — graceful stop

The engine resolves IHostApplicationLifetime.ApplicationStopping from the DI container at construction time (via IServiceProvider). If the lifetime service is not registered (e.g. non-hosted unit-test scenarios), it falls back to CancellationToken.None.

All fire-and-forget Task.Run loops — StartBackgroundAsync, ResumeBackgroundAsync, ResumeByInstanceIdBackgroundAsync, and the child-signal flush after suspension — receive this token. When the host initiates shutdown, running loops honour the stopping token and terminate within the configured HostOptions.ShutdownTimeout (default 30 s). Instances left in Running state are reclaimed by the sweep service on next startup.

No special configuration is required; standard ASP.NET Core Generic Host wiring is sufficient:

builder.Services.AddFlowEngine()...;
// IHostApplicationLifetime is already registered by the Generic Host.

when edge guard — script timeout

when expressions are evaluated by Roslyn scripting. An expression with an infinite loop or blocked I/O would consume a thread-pool thread indefinitely. The engine bounds evaluation with FlowEngineOptions.ScriptTimeoutSeconds (default: 5, set to 0 to disable).

Internally the script is run on a thread-pool thread via Task.Run so Task.WhenAny can race it against Task.Delay. On timeout, a TimeoutException is thrown and logged as a node Error outcome. The abandoned thread eventually exits when Thread.Sleep-style blocks finish; spin-loops are not interruptible and persist until the process shuts down.

Configure in DI:

builder.Services.AddFlowEngine(o => o.ScriptTimeoutSeconds = 10);

Sweep service — bounded concurrency

ExecutionSweepService wakes on a configurable interval and processes up to SweepBatchSize (default: 100) resumable instances per tick. Each resumption is launched as a Task.Run call. To prevent spawning more concurrent tasks than the engine can handle, a SemaphoreSlim is acquired before each spawn and released in finally inside the task.

The semaphore capacity is MaxConcurrentExecutions when set in FlowEngineOptions, otherwise SweepBatchSize. This means the sweep never queues more live tasks than the engine is configured to handle simultaneously.

FilterBuilder integration points

filter nodes use FilterBuilder FilterSets as their condition language. Use the FilterBuilder SKILL to construct FilterSet JSON for any filter node.

Key integration patterns:

// Filter the primary entity
{ "target": "$.entity", "filterSet": { ... } }

// Filter a stored context object
{ "target": "$.context.enrichedCustomer", "filterSet": { ... } }

// Filter engine metadata (visit counts, etc.)
{ "target": "$.engine", "filterSet": { "operator": "AND", "filters": [
  { "propertyPath": "visits.n-review", "operation": "ge", "testValue": 3 }
]}}

// Multi-result cross-type query (produces IN clause)
// Use TestValueFilterExpressionMulti in a Filter node's filterSet
// to derive membership from another dataset at expression-build time

The entity structure passed to a filter node must match the C# entity type registered with FilterBuilder. Confirm the entity schema with the developer before constructing deep navigation path filters.

Decision guide — which node type?

Is the workflow making a data-based decision (yes/no/unknown)?
  → filter node (FilterBuilder against in-context data)

Does the workflow need to QUERY a database or data source?
  → query node (FilterBuilder against a registered IQueryClient)
  → resultMode: any/count if you only need yes/no (no filter node needed after)
  → resultMode: all/first if you need the data for downstream nodes

Is the workflow routing based on a context value?
  → decision node + edge when predicates

Does the workflow need data from an external REST API?
  → integration node (clientRef = registered IRequestResponseClient)

Does the workflow need to call an AI agent or LLM?
  → agent node (clientRef = registered IAgentClient)

Does the workflow need to publish a message or event?
  → message node (clientRef = registered IMessageClient)
  → FireAndForget if no reply needed
  → RequestReply if workflow should suspend until a reply arrives

Does the workflow need to compute a derived value?
  → compute node (Roslyn expression)

Does the workflow need a human to act?
  → human node (Internal task queue or External notification)

Does the workflow need to pause and wait for an external signal?
  → wait node (eventName + correlationKeyPath/Expression)
  → harness code calls engine.ResumeAsync(eventName, correlationKey, payload)

Does the workflow need a pure time delay with no external dependency?
  → timer node (delay = ISO 8601 or ICalendarProvider expression)
  → no harness code — sweep service resumes automatically with Match outcome
  → use "PT5M", "PT1H", "P2D" for standard delays (DefaultCalendarProvider)
  → use "3bd", "startDate+30d" for calendar-aware delays (custom ICalendarProvider)
  → timer always emits Match; wait timeout emits Error — intentionally different

Does the workflow need to iterate over a collection?
  → loop node + sub-workflow

Does the workflow need to run things concurrently?
  → parallel node

Does the workflow invoke another workflow?
  → workflow node
  → clientRef absent = local engine
  → clientRef set = remote IFlowEngineClient (different engine, deployment, or system)

Does the workflow end here (terminal state)?
  → output node (one per distinct terminal outcome)

Does the workflow just need to record or reshape something?
  → store node (write a value) or transform node (reshape multiple fields)

Is there expensive or write-heavy work where crash re-execution would be costly?
  → checkpoint node before the expensive/write chain
  → always combine with idempotencyKey on write nodes — checkpoint reduces re-execution
     window but does not replace idempotency

Workflow builder conversation guide

When a business user describes a process:

Step 1 — Identify the trigger and entity "What kicks this off?" → determines invocation pattern "What information does it start with?" → defines $.entity

Step 2 — Map the happy path Walk through what happens when everything goes right. One node per decision point, one node per external call, one node per human action.

Step 3 — Add the branching For each decision node: "What are the possible outcomes?" Map each to an edge.

Step 4 — Add error and rejection paths For each node: "What if this fails?" → onFailure edge or global handler. For each human node: "What if nobody responds?" → dueIn + escalation or timeout.

Step 5 — Identify rework cycles "Can anything be sent back?" → backward edge + visit count limit. "How many times?" → $.engine.visits.{nodeId} in when predicate.

Step 6 — Draft JSON and walk through it Present the workflow node by node using intent fields to explain in plain language. "After checking eligibility, if the customer qualifies we go to..."

Step 7 — Validate gaps Ask: "What happens if [edge case]?" for any paths not yet covered. Check: every node has at least one edge (except output nodes). Check: at least one output node is reachable on every path. Check: every backward edge has a visit limit. Check: every integration write has an idempotencyKey. Check: nodes with outputSchema also have storeAs (otherwise schema validation never runs). Check: contextRequirements key names use bare keys, not $.context.* prefixes.

Pre-registration validation: WorkflowDefinitionValidator.ValidateAndThrow(definition) is called automatically inside IWorkflowRegistry.SaveAsync. It catches broken node ID references, missing entry points, and self-loops at registration time. You can also call it manually before saving to surface errors early.
