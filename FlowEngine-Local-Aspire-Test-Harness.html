Architecture Overview

FlowEngine separates workflow definition from workflow execution. Definitions are stored in a registry (SQL, Redis, Cosmos, Azure Table, or File). Execution requires a running engine instance with the right external clients registered — databases, APIs, message buses, and so on.

Two deployment surfaces exist:

Dashboard UI

  • Blazor Server app for designing and managing workflows
  • Can also execute workflows (co-host mode)
  • Exposes the Admin API and Client Registry page
  • Needs the same clients registered so designers can reference them in node configs

Production Worker

  • Background service / Azure Function / Worker Service
  • Automatically processes triggered or scheduled workflows
  • Must register the same client vocabulary as the Dashboard
  • Points at production resources, not Aspire containers

Workflow node configs embed clientRef strings — e.g., "clientRef": "crm-api". The engine resolves clients by that name from IClientRegistry at runtime. If a client with that name isn't registered, the node faults. The client registry is therefore the shared vocabulary between workflow designers and the execution environment.

Key principle: Register clients once in code (startup). The vocabulary of available clientRef names is a developer responsibility, not a runtime configuration. The Dashboard UI makes those registrations visible to workflow designers so they know what names to use in node configs.

The Client Registry Contract

All external integrations implement one of the typed client interfaces:

InterfaceUsed by node typeImplementations
IRequestResponseClientfetch, integrationResilientHttpFlowClient, DirectHttpFlowClient
IQueryClientqueryEfQueryClient<TContext>, AdHocSqlQueryClient
IMessageClientmessageServiceBusMessageClient
IAgentClientagentCustom LLM/SK integrations

Each client is registered under a unique clientRef string:

csharp// Fluent builder on IServiceCollection
var flowEngineBuilder = builder.Services.AddFlowEngine();

flowEngineBuilder
    .AddResilientHttpClient("crm-api", namedClient: "CrmApi")
    .AddServiceBusClient("order-events", connectionString, queueOrTopic: "orders")
    .AddClient(sp => new EfQueryClient<CrmDbContext>(
        clientRef:   "crm-query",
        factory:     sp.GetRequiredService<IDbContextFactory<CrmDbContext>>(),
        typeMap:     CrmDbContext.EntityTypeMap,
        setResolver: (db, entity) => entity.ToLower() switch {
            "customer" => db.Customers,
            "order"    => db.Orders,
            _          => null
        }));

The Dashboard UI's Client Registry page (/clients) displays all registered clients. Clients registered at startup are shown as startup source and are read-only in the UI. Clients added via the UI form are shown as config source and can be deleted.

Note on EfQueryClient<TContext>: This client requires compile-time generic type parameters and must be registered in code. It cannot be created from the UI. Use it for typed EF Core queries against a known DbContext. For ad-hoc SQL access from the UI, use the AdHocSqlQueryClient type.

Running the Harness Locally

The EF.FlowEngine.Dashboard.AppHost project is a .NET Aspire AppHost that provisions SQL Server and Redis via Docker and wires their connection strings into EF.FlowEngine.Dashboard.UI.

Prerequisites

  • .NET 10 SDK
  • Docker Desktop (running)
  • .NET Aspire workload: dotnet workload install aspire

Start the harness

shelldotnet run --project EF.FlowEngine.Dashboard.AppHost

Aspire opens its dashboard at http://localhost:15888. From there you can watch all resources come up, view logs, and navigate to the Dashboard.UI.

  1. Aspire starts a SQL Server container and a Redis container with persistent data volumes.
  2. Connection strings are injected into Dashboard.UI as environment variables (ConnectionStrings__FlowEngineDb, ConnectionStrings__TaskFlowDb, ConnectionStrings__Redis).
  3. Dashboard.UI detects the SQL connection string and runs EF Core migrations automatically on startup (MigrationStartupTask).
  4. Sample workflows are seeded into the workflow registry (SampleWorkflowSeeder) if none exist.
  5. A taskflow-query EF Core client is registered against the TaskFlow demo database, which is migrated and seeded with representative data.
  6. The Dashboard.UI is available at its Aspire-assigned port.
Containers use WithLifetime(ContainerLifetime.Persistent) and named data volumes, so data survives across dotnet run restarts. On first run, migrations and seeders run; on subsequent runs they are idempotent.

What Aspire Provides

ResourceConnection nameUsed for
SQL Server containerFlowEngineDbFlowEngine state store, workflow registry, distributed locks — all backed by FlowEngineDashboardDbContext

Provider selection logic in Dashboard.UI

csharpif (!string.IsNullOrEmpty(flowEngineDbCs))
{
    // SQL preferred — persistent, supports rich instance queries
    flowEngineBuilder
        .UseStateStoreSql<FlowEngineDashboardDbContext>()
        .UseWorkflowRegistrySql<FlowEngineDashboardDbContext>()
        .UseLockProviderSql<FlowEngineDashboardDbContext>();
}
else if (!string.IsNullOrEmpty(redisCs))
{
    // Redis — lighter-weight alternative
    builder.AddRedisClient("Redis");   // registers IConnectionMultiplexer
    flowEngineBuilder
        .UseStateStoreRedis()
        .UseWorkflowRegistryRedis()
        .UseLockProviderRedis();
}
// else: in-memory defaults (no external services required)

This means Dashboard.UI works in three modes: full-SQL (Aspire or real SQL Server), Redis-only, or in-memory (no configuration required — useful for quick UI exploration).

UI-Registered Clients

The Client Registry page (/clients) lets developers add three types of clients at runtime without redeploying:

TypeFieldsImplementationPersisted?
HTTPBase URL, optional API key headerDirectHttpFlowClientYes — clientconfigs.json
Service BusConnection string, queue/topic nameServiceBusMessageClientYes — clientconfigs.json
SQL QueryConnection string, entity→table mapAdHocSqlQueryClientYes — clientconfigs.json

Persisted configs are stored in {FlowEngine:DataDirectory}/clientconfigs.json (default: AppData/clientconfigs.json relative to the app root) and reloaded on every startup by ClientRegistryStartupTask.

Dev convenience, not a production pattern. UI-registered clients store connection strings in plaintext on disk. They are intended for local development and prototyping. In production, register all clients in code using startup DI and source connection strings from Azure Key Vault, environment variables, or managed identity.

AdHocSqlQueryClient translates FilterSet predicates to parameterized SQL at runtime. It supports the common filter operations (eq, neq, gt, lt, gte, lte, contains→LIKE, startswith→LIKE, in→IN) and works against any SQL Server table. For more complex queries — joins, projections, stored procedures — register a typed EfQueryClient<TContext> in code instead.

Moving to Production

The Aspire AppHost is a development convenience. Moving to production means replacing Aspire-provisioned containers with real Azure services and switching from UI-registered clients to code-registered ones.

Step 1 — Replace connection strings

Remove the AppHost and configure connection strings in your production host's appsettings.json, environment variables, or Azure App Configuration:

json{
  "ConnectionStrings": {
    "FlowEngineDb": "Server=my-sql.database.windows.net;Database=FlowEngine;Authentication=Active Directory Default",
    "TaskFlowDb":   "Server=my-sql.database.windows.net;Database=TaskFlow;Authentication=Active Directory Default"
  }
}

The same conditional provider selection code in Program.cs works unchanged — it reads from ConnectionStrings:FlowEngineDb regardless of whether it was injected by Aspire or set directly.

Step 2 — Register typed clients in code

Replace the TaskFlow demo client with your application's real clients. In both the Dashboard.UI and the production worker service:

csharp// Your AppDbContext implements IFlowEngineStateDbContext and maps ApplyFlowEngineState()
// or be a separate DbContext (for data queries)

flowEngineBuilder
    // HTTP: use the resilience pipeline for production
    .AddResilientHttpClient("my-api", namedClient: "MyApi")

    // Azure Service Bus
    .AddServiceBusClient("order-events",
        connectionString: config["ServiceBus:ConnectionString"],
        queueOrTopic:     "orders")

    // Typed EF Core query client
    .AddClient(sp => new EfQueryClient<MyAppDbContext>(
        clientRef:   "app-query",
        factory:     sp.GetRequiredService<IDbContextFactory<MyAppDbContext>>(),
        typeMap:     MyAppDbContext.EntityTypeMap,
        setResolver: (db, entity) => entity.ToLowerInvariant() switch {
            "order"    => db.Orders,
            "customer" => db.Customers,
            _          => null
        }));

// Named HttpClient configured with base address and auth
builder.Services.AddHttpClient("MyApi", c =>
{
    c.BaseAddress = new Uri(config["MyApi:BaseUrl"]);
    c.DefaultRequestHeaders.Add("x-api-key", config["MyApi:ApiKey"]);
});

Step 3 — Remove UI-registered dev clients

Delete or ignore clientconfigs.json. In production, all clients should come from code. If you need runtime client configuration (e.g., tenant-specific endpoints), implement a custom IClientConfigStore backed by a database or Key Vault and wire it accordingly — but this is an application-level concern, not a FlowEngine responsibility.

Registering Clients in a Production Worker

A production worker runs the engine in the background, executing workflows triggered by events, timers, or the Admin API. It must register the same client vocabulary as the Dashboard so workflow definitions — which embed clientRef strings — resolve successfully.

csharp// Worker service Program.cs (Worker Service / Azure Functions host / etc.)
var builder = Host.CreateApplicationBuilder(args);

var flowEngineBuilder = builder.Services.AddFlowEngine()
    .UseStateStoreSql<WorkerDbContext>()
    .UseWorkflowRegistrySql<WorkerDbContext>()
    .UseLockProviderSql<WorkerDbContext>();

// Register EXACTLY the same clientRef names as the Dashboard
flowEngineBuilder
    .AddResilientHttpClient("my-api",      namedClient: "MyApi")
    .AddServiceBusClient("order-events",   connectionString, queueOrTopic: "orders")
    .AddClient(sp => new EfQueryClient<MyAppDbContext>(
        "app-query", factory, MyAppDbContext.EntityTypeMap, setResolver));

builder.Services.AddHostedService<FlowEngineWorker>();  // your polling/trigger loop
clientRef mismatch = runtime fault. If the worker registers "my-api" but a workflow definition uses "myApi", the fetch node will fault. Keep a shared constants file or configuration section that both the Dashboard and worker reference for clientRef names.

Shared client ref names

The simplest way to avoid drift is a shared constants class in a common library:

csharp// Shared library: MyApp.FlowEngine.Clients
public static class ClientRefs
{
    public const string MyApi        = "my-api";
    public const string OrderEvents  = "order-events";
    public const string AppQuery     = "app-query";
}

Reference this in both hosts and in any code that programmatically constructs workflow definitions.
