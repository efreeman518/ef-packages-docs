Admin API

Package: EF.FlowEngine.AdminApi

Exposes workflow engine operations over HTTP as a minimal-API extension. Designed to be mounted in your existing ASP.NET Core host — it does not require a dedicated service.

Registration

csharp// Program.cs — add policies and services
builder.Services.AddFlowEngineAdminPolicies();   // registers FlowEngine.Admin + FlowEngine.HumanTask policies
builder.Services.AddFlowEngine()                 // FlowEngineAdminService registered automatically
    .UseStateStoreSql<AppDbContext>()
    // ... other engine setup

// Map all admin endpoints under a prefix
app.MapFlowEngineAdmin(prefix: "/api/flowengine");

Authorization Policies

AddFlowEngineAdminPolicies() registers two named policies. Configure them to match your identity provider:

csharpbuilder.Services.AddAuthorization(o =>
{
    o.AddPolicy("FlowEngine.Admin", p =>
        p.RequireClaim("role", "flowengine-admin"));

    o.AddPolicy("FlowEngine.HumanTask", p =>
        p.RequireClaim("role", "task-worker"));
});

All admin endpoints require FlowEngine.Admin. Human-task endpoints accept either policy.

Ops Dashboard

Package: EF.FlowEngine.Dashboard (component library) + EF.FlowEngine.Dashboard.UI (ASP.NET Core host)

Blazor Server dashboard built on MudBlazor. Includes a workflow designer, client registry, and instance management UI. Consumes the Admin API via a Refit-generated typed HTTP client. The host app conditionally wires SQL Server or Redis state store, registry, and lock providers based on available connection strings — falling back to in-memory for zero-config development.

Registration

csharp// Program.cs
builder.Services.AddFlowEngineDashboard(
    adminApiBaseUrl: builder.Configuration["FlowEngine:AdminApiBaseUrl"]!
    // e.g. "https://your-api-host/api/flowengine"
);

// Blazor Server wiring (add alongside your existing Blazor registration)
builder.Services.AddServerSideBlazor();
app.MapBlazorHub();
app.MapFallbackToPage("/_Host");

IFlowEngineAdminClient

The dashboard uses a Refit-generated typed client. You can also use it directly in your own code to call the Admin API:

csharp// Registered by AddFlowEngineDashboard — or register manually:
builder.Services.AddRefitClient<IFlowEngineAdminClient>()
    .ConfigureHttpClient(c => c.BaseAddress = new Uri(adminApiBaseUrl));
Authentication: The dashboard does not configure authentication itself. Mount it behind your existing auth middleware and ensure the user's JWT or cookie includes the FlowEngine.Admin or FlowEngine.HumanTask claim required by the Admin API policies.

Transactional Outbox

Package: EF.FlowEngine.Outbox.Sql

The transactional outbox pattern guarantees at-least-once delivery for messages, integration calls, and agent invocations.

Availability: A SQL-backed transactional outbox is the only production implementation provided. Redis, Cosmos, Azure Table, and File state stores do not have a corresponding outbox implementation; if you use those stores without EF.FlowEngine.Outbox.Sql, outbox entries are not persisted and delivery is best-effort only.

How it works

  1. Node executors return outbox entries via NodeResult.PendingOutboxEntries; the engine writes them atomically with the workflow state in the same SaveChangesAsync call when both state store and outbox share the same DbContext
  2. Alternatively, executors may call IOutboxStore.EnqueueAsync directly — this is best-effort (separate transaction)
  3. OutboxDrainService (background IHostedService) polls for entries and publishes them to the registered client
  4. On successful publish the entry is marked published; on failure it is retried with exponential backoff

Registration

csharpbuilder.Services.AddFlowEngine()
    .UseStateStoreSql<AppDbContext>()
    .UseOutboxSql<AppDbContext>();     // EF.FlowEngine.Outbox.Sql

Both state store and outbox must share the same DbContext type for transactional enrollment to work.

Idempotency keys

Set idempotencyKey on any node that makes an outbox-enrolled call. The engine resolves the key as a context path or literal and forwards it to the client:

json{
  "type": "message",
  "config": {
    "clientRef":      "order-events",
    "subject":        "order.completed",
    "body":           { "orderId": "$.entity.OrderId" },
    "idempotencyKey": "$.entity.OrderId + '-order-complete'"
  }
}

{
  "type": "agent",
  "config": {
    "clientRef":       "gpt4o",
    "promptTemplate":  "Classify this order: {{$.context.orderData}}",
    "idempotencyKey":  "$.entity.OrderId + '-classification'"
  }
}

{
  "type": "integration",
  "config": {
    "clientRef":      "payment-api",
    "integration":    "charge-card",
    "idempotencyKey": "$.entity.OrderId + '-payment'"
  }
}
Validation warning: WorkflowDefinitionValidator emits a warning when idempotencyKey is absent from an agent/message/integration node. This does not block registration but surfaces in validation output — treat it as an at-least-once delivery risk.

Distributed Circuit Breaker

The default InMemoryCircuitBreakerStore is process-local — circuit state is not shared across replicas. For multi-replica deployments, replace it with a distributed backend:

PackageTypeBacking store
(built-in)InMemoryCircuitBreakerStoreIn-process only — single replica
EF.FlowEngine.CircuitBreaker.RedisRedisCircuitBreakerStoreRedis sorted sets — shared across all replicas
EF.FlowEngine.CircuitBreaker.SqlSqlCircuitBreakerStoreEF Core SQL table — shared across all replicas

Registration

csharp// Redis — requires IConnectionMultiplexer in DI
builder.Services.AddFlowEngine()
    .UseStateStoreSql<AppDbContext>()
    .UseCircuitBreakerRedis();

// SQL (EF Core) — requires IDbContextFactory<TContext> in DI
builder.Services.AddFlowEngine()
    .UseStateStoreSql<AppDbContext>()
    .UseCircuitBreakerSql<AppDbContext>();

ICircuitBreakerStore interface

csharppublic interface ICircuitBreakerStore
{
    Task<bool> IsOpenAsync(string key, CancellationToken ct = default);
    Task        RecordFailureAsync(string key, CircuitBreakerPolicy policy, CancellationToken ct = default);
    Task        RecordSuccessAsync(string key, CancellationToken ct = default);
}

Circuit behavior

ScenarioBehavior
Failures reach FailureThreshold within SamplingWindowCircuit opens — subsequent nodes skip execution
Node has a CircuitOpen edgeEngine takes that edge — workflow continues via degraded path
No CircuitOpen edgeInstance suspends with a timed wait equal to OpenDuration; sweep service resumes it after cool-down
RecordSuccessAsync calledCircuit closes immediately — failures counter reset
OpenDuration elapsesNext execution attempt allowed (half-open); success closes, failure re-opens
InMemoryCircuitBreakerStore in production: circuit state is not persisted — a process restart resets all circuits. If you restart a replica while circuits are open, instances may retry a still-degraded service. Use a distributed store for any multi-replica or container-based deployment.

Migration Tooling

CompatibilityAnalyzer

Always analyze compatibility before migrating suspended instances to a new workflow version:

csharpvar report = CompatibilityAnalyzer.Analyze(v1Definition, v2Definition);

foreach (var finding in report.Findings)
{
    // Severity: Warning | Breaking
    // Message:  human-readable description
    Console.WriteLine($"[{finding.Severity}] {finding.Message}");
}

if (report.Findings.Any(f => f.Severity == FindingSeverity.Breaking))
{
    // Do not proceed — suspended instances would be stranded
    return;
}

Finding categories:

CategorySeverityDescription
Removed nodeBreakingA node present in from was removed in to — suspended instances at that node would be stranded
Retyped nodeBreakingA node's type changed — executor mismatch at resume time
Missing edge targetBreakingAn edge references a nextNodeId that no longer exists in to
Entry node changedWarningNew instances start at a different node — in-flight instances unaffected but worth reviewing
GlobalOnFailureNodeId changedWarningFailure routing will change after migration
OutputSchema removedWarningA node's output schema was removed — downstream nodes that relied on the enforced shape may receive unexpected values
OutputSchema changedWarningA node's output schema changed — verify downstream consumers still handle the new shape
When guard may reference renamed StoreAs keyWarningAn edge When expression contains the old key name when the node's storeAs was renamed — heuristic string match; verify the expression manually

For the complete finding catalogue (including ContextRequirements, StoreAs rename, CompensationNodeId checks) and the full promotion checklist, see FlowEngine Design Doc → CompatibilityAnalyzer.

Via Admin API

httpGET /api/flowengine/workflows/{workflowId}/compatibility?from=1.0.0&to=2.0.0

Returns a WorkflowCompatibilityReport JSON object. Safe to call in automated pre-migration pipelines.

MigrateInstanceAsync with dry-run

csharp// Always dry-run first — validates remapping without persisting
// Adds a "[dry-run]" entry to instance history for audit
var result = await engine.MigrateInstanceAsync(
    instanceId:     instanceId,
    targetVersion:  "2.0.0",
    nodeIdMap:      new Dictionary<string, string>
    {
        ["n-old-approval"] = "n-manager-approval"
    },
    dryRun:         true,
    ct:             ct);

// If dry-run succeeded, apply the real migration
await engine.MigrateInstanceAsync(
    instanceId:    instanceId,
    targetVersion: "2.0.0",
    nodeIdMap:     new Dictionary<string, string>
    {
        ["n-old-approval"] = "n-manager-approval"
    },
    ct: ct);

Bulk migration pattern

csharp// 1. Analyze compatibility
var report = CompatibilityAnalyzer.Analyze(v1, v2);
if (report.Findings.Any(f => f.Severity == FindingSeverity.Breaking)) return;

// 2. Fetch all suspended instances on the old version
var queryResult = await adminApi.QueryInstancesAsync(new ExecutionQuery
{
    WorkflowId = "expense-approval",
    Version    = "1.0.0",
    Status     = ExecStatus.Suspended
});

// 3. Dry-run each instance
foreach (var inst in queryResult.Items)
{
    await engine.MigrateInstanceAsync(inst.InstanceId, "2.0.0", dryRun: true, ct: ct);
}

// 4. Apply migration to all (dry-runs all passed)
foreach (var inst in queryResult.Items)
{
    await engine.MigrateInstanceAsync(inst.InstanceId, "2.0.0", ct: ct);
}

Testing Failure Modes

The integration test suite (EF.Test.Integration.FlowEngine/FailureModeTests.cs) covers the following failure scenarios with InMemory stores — no Docker required:

Test classScenario verified
CircuitBreakerTripsTestsCircuit opens after FailureThreshold consecutive failures; subsequent runs return CircuitOpen outcome in history
CircuitBreakerResetTestsRecordSuccessAsync closes an open circuit (IsOpenAsync returns false)
RetryExhaustionTestsRetry exhaustion faults the instance with correct AttemptNumber on the final history record
IdempotencyKeyForwardingTestsStatic IdempotencyKey is forwarded verbatim to IAgentClient.InvokeAsync
FaultingStateStoreTestsState store SaveAsync exception propagates out of the engine (at-least-once guarantee)

Run with: dotnet test EF.Test.Integration.FlowEngine (no external infrastructure required for these tests).
