Admin API

Package: EF.FlowEngine.AdminApi

Exposes workflow engine operations over HTTP as a minimal-API extension. Designed to be mounted in your existing ASP.NET Core host — it does not require a dedicated service.

Registration

csharp// Program.cs — add policies and services
builder.Services.AddFlowEngineAdminPolicies();   // registers FlowEngine.Admin + FlowEngine.HumanTask policies
builder.Services.AddFlowEngine()                 // FlowEngineAdminService registered automatically
    .UseStateStoreSql<AppDbContext>()
    // ... other engine setup

// Map all admin endpoints under a prefix
app.MapFlowEngineAdmin(prefix: "/api/flowengine");

Authorization Policies

AddFlowEngineAdminPolicies() registers two named policies. Configure them to match your identity provider:

csharpbuilder.Services.AddAuthorization(o =>
{
    o.AddPolicy("FlowEngine.Admin", p =>
        p.RequireClaim("role", "flowengine-admin"));

    o.AddPolicy("FlowEngine.HumanTask", p =>
        p.RequireClaim("role", "task-worker"));
});

All admin endpoints require FlowEngine.Admin. Human-task endpoints accept either policy.

Ops Dashboard

Package: EF.FlowEngine.Dashboard (component library) + EF.FlowEngine.Dashboard.UI (ASP.NET Core host)

Blazor Server dashboard built on MudBlazor. Includes a workflow designer, client registry, and instance management UI. Consumes the Admin API via a Refit-generated typed HTTP client. The host app conditionally wires SQL Server or Redis state store, registry, and lock providers based on available connection strings — falling back to in-memory for zero-config development.

Registration

csharp// Program.cs
builder.Services.AddFlowEngineDashboard(

    // e.g. "https://your-api-host/api/flowengine"
);

// Blazor Server wiring (add alongside your existing Blazor registration)
builder.Services.AddServerSideBlazor();
app.MapBlazorHub();
app.MapFallbackToPage("/_Host");

Transactional Outbox

Package: EF.FlowEngine.Outbox.Sql

The transactional outbox pattern guarantees at-least-once delivery for messages, integration calls, and agent invocations.

Availability: A SQL-backed transactional outbox is the only production implementation provided. Redis, Cosmos, Azure Table, and File state stores do not have a corresponding outbox implementation; if you use those stores without EF.FlowEngine.Outbox.Sql, outbox entries are not persisted and delivery is best-effort only.

How it works

  1. Node executors return outbox entries via NodeResult.PendingOutboxEntries; the engine writes them atomically with the workflow state in the same SaveChangesAsync call when both state store and outbox share the same DbContext
  2. Alternatively, executors may call IOutboxStore.EnqueueAsync directly — this is best-effort (separate transaction)
  3. OutboxDrainService (background IHostedService) polls for entries and publishes them to the registered client
  4. On successful publish the entry is marked published; on failure it is retried with exponential backoff

Registration

csharpbuilder.Services.AddFlowEngine()
    .UseStateStoreSql<AppDbContext>()
    .UseOutboxSql<AppDbContext>();     // EF.FlowEngine.Outbox.Sql

Both state store and outbox must share the same DbContext type for transactional enrollment to work.

Idempotency keys

Set idempotencyKey on any node that makes an outbox-enrolled call. The engine resolves the key as a context path or literal and forwards it to the client:

json{
  "type": "message",
  "config": {
    "clientRef":      "order-events",
    "subject":        "order.completed",
    "body":           { "orderId": "$.entity.OrderId" },
    "idempotencyKey": "$.entity.OrderId + '-order-complete'"
  }
}

{
  "type": "agent",
  "config": {
    "clientRef":       "gpt4o",
    "promptTemplate":  "Classify this order: {{$.context.orderData}}",
    "idempotencyKey":  "$.entity.OrderId + '-classification'"
  }
}

{
  "type": "integration",
  "config": {
    "clientRef":      "payment-api",
    "integration":    "charge-card",
    "idempotencyKey": "$.entity.OrderId + '-payment'"
  }
}
Validation warning: WorkflowDefinitionValidator emits a warning when idempotencyKey is absent from an agent/message/integration node. This does not block registration but surfaces in validation output — treat it as an at-least-once delivery risk.

Distributed Circuit Breaker

The default InMemoryCircuitBreakerStore is process-local — circuit state is not shared across replicas. For multi-replica deployments, replace it with a distributed backend:

PackageTypeBacking store
(built-in)InMemoryCircuitBreakerStoreIn-process only — single replica
EF.FlowEngine.CircuitBreaker.RedisRedisCircuitBreakerStoreRedis sorted sets — shared across all replicas
EF.FlowEngine.CircuitBreaker.SqlSqlCircuitBreakerStoreEF Core SQL table — shared across all replicas

Registration

csharp// Redis — requires IConnectionMultiplexer in DI
builder.Services.AddFlowEngine()
    .UseStateStoreSql<AppDbContext>()
    .UseCircuitBreakerRedis();

// SQL (EF Core) — requires IDbContextFactory<TContext> in DI
builder.Services.AddFlowEngine()
    .UseStateStoreSql<AppDbContext>()
    .UseCircuitBreakerSql<AppDbContext>();

// Cosmos — requires CosmosClient in DI
builder.Services.AddFlowEngine()
    .UseCircuitBreakerCosmos(databaseId: "flowengine");

ICircuitBreakerStore interface

csharppublic interface ICircuitBreakerStore
{
    Task<bool> IsOpenAsync(string key, CancellationToken ct = default);
    Task        RecordFailureAsync(string key, CircuitBreakerPolicy policy, CancellationToken ct = default);
    Task        RecordSuccessAsync(string key, CancellationToken ct = default);
}

Circuit behavior

ScenarioBehavior
Failures reach FailureThreshold within SamplingWindowCircuit opens — subsequent nodes skip execution
Node has a CircuitOpen edgeEngine takes that edge — workflow continues via degraded path
No CircuitOpen edgeInstance suspends with a timed wait equal to OpenDuration; sweep service resumes it after cool-down
RecordSuccessAsync calledCircuit closes immediately — failures counter reset
OpenDuration elapsesCircuit transitions to HalfOpen — exactly one probe attempt is let through; all other callers are blocked during the probe window. Probe success → Closed (failures counter reset). Probe failure → re-Open with timer reset.

InMemoryCircuitBreakerStore — HalfOpen behavior: after OpenDuration elapses, the store transitions to HalfOpen state. Exactly one call is permitted as a probe; all concurrent callers are blocked. A successful probe result (via RecordSuccessAsync) transitions to Closed. A failed probe result (via RecordFailureAsync) transitions back to Open and resets the open timer. This is enforced by a semaphore in the in-memory implementation — no additional configuration is required.

InMemoryCircuitBreakerStore in production: circuit state is not persisted — a process restart resets all circuits. If you restart a replica while circuits are open, instances may retry a still-degraded service. Use a distributed store for any multi-replica or container-based deployment.

Migration Tooling

CompatibilityAnalyzer

Always analyze compatibility before migrating suspended instances to a new workflow version:

csharpvar report = CompatibilityAnalyzer.Analyze(v1Definition, v2Definition);

foreach (var finding in report.Findings)
{
    // Severity: Warning | Breaking
    // Message:  human-readable description
    Console.WriteLine($"[{finding.Severity}] {finding.Message}");
}

if (report.Findings.Any(f => f.Severity == FindingSeverity.Breaking))
{
    // Do not proceed — suspended instances would be stranded
    return;
}

Finding categories:

CategorySeverityDescription
Removed nodeBreakingA node present in from was removed in to — suspended instances at that node would be stranded
Retyped nodeBreakingA node's type changed — executor mismatch at resume time
Missing edge targetBreakingAn edge references a nextNodeId that no longer exists in to
Entry node changedWarningNew instances start at a different node — in-flight instances unaffected but worth reviewing
GlobalOnFailureNodeId changedWarningFailure routing will change after migration
OutputSchema removedWarningA node's output schema was removed — downstream nodes that relied on the enforced shape may receive unexpected values
OutputSchema changedWarningA node's output schema changed — verify downstream consumers still handle the new shape
When guard may reference renamed StoreAs keyWarningAn edge When expression contains the old key name when the node's storeAs was renamed — heuristic string match; verify the expression manually

For the complete finding catalogue (including ContextRequirements, StoreAs rename, CompensationNodeId checks) and the full promotion checklist, see FlowEngine Design Doc → CompatibilityAnalyzer.

Via Admin API

httpGET /api/flowengine/workflows/{workflowId}/compatibility?from=1.0.0&to=2.0.0

Returns a WorkflowCompatibilityReport JSON object. Safe to call in automated pre-migration pipelines.

MigrateInstanceAsync with dry-run

csharp// Always dry-run first — validates remapping without persisting
// Adds a "[dry-run]" entry to instance history for audit
var result = await engine.MigrateInstanceAsync(
    instanceId:     instanceId,
    targetVersion:  "2.0.0",
    nodeIdMap:      new Dictionary<string, string>
    {
        ["n-old-approval"] = "n-manager-approval"
    },
    dryRun:         true,
    ct:             ct);

// If dry-run succeeded, apply the real migration
await engine.MigrateInstanceAsync(
    instanceId:    instanceId,
    targetVersion: "2.0.0",
    nodeIdMap:     new Dictionary<string, string>
    {
        ["n-old-approval"] = "n-manager-approval"
    },
    ct: ct);

Bulk migration (MigrateInstancesAsync)

Move every non-terminal instance off a version in one call. Failures are collected per-instance in the returned BulkMigrationResult rather than aborting the batch; pass dryRun: true to preview feasibility first. Migration does not resume execution.

csharp// 1. Analyze compatibility
var report = CompatibilityAnalyzer.Analyze(v1, v2);
if (report.Findings.Any(f => f.Severity == FindingSeverity.Breaking)) return;

// 2. Dry-run the whole batch
var preview = await engine.MigrateInstancesAsync(
    workflowId:    "expense-approval",
    fromVersion:   "1.0.0",
    targetVersion: "2.0.0",
    nodeIdMap:     new Dictionary<string, string> { ["n-old-approval"] = "n-manager-approval" },
    dryRun:        true,
    ct:            ct);

// 3. Apply if the preview had no failures
if (preview.Failed.Count == 0)
{
    var result = await engine.MigrateInstancesAsync(
        "expense-approval", "1.0.0", "2.0.0",
        nodeIdMap: new Dictionary<string, string> { ["n-old-approval"] = "n-manager-approval" },
        ct: ct);

    // result.Migrated: instance ids moved to 2.0.0; result.Failed: id -> reason
}

Scheduled Workflows & Start Idempotency

Cron triggers (UseScheduler)

UseScheduler() registers a background service that fires WorkflowSchedule cron triggers. On each tick it evaluates enabled schedules and starts the workflow for any whose next occurrence is due. Standard 5-field cron expressions are evaluated in UTC.

csharpbuilder.Services.AddFlowEngine()
    .UseScheduler(tickInterval: TimeSpan.FromSeconds(30))
    .AddSchedule(new WorkflowSchedule
    {
        ScheduleId     = "nightly-report",
        WorkflowId     = "generate-report",
        CronExpression = "0 2 * * *",       // 02:00 UTC daily
        Params         = new() { ["scope"] = ContextValue.FromString("all") }
    });

Each firing starts the workflow with an idempotency key of {scheduleId}:{occurrence}. If the scheduler runs on multiple replicas, engine start idempotency (below) ensures each occurrence launches exactly one instance — so no shared schedule store or leader election is required. UseScheduler() registers an in-memory IWorkflowScheduleStore unless a durable one is registered first; schedules can also be managed at runtime by resolving IWorkflowScheduleStore.

Start idempotency

Set IdempotencyKey on a StartRequest to make starts safe to retry. When the key matches an instance that already exists, the engine returns that existing instance instead of creating a duplicate; the key is stored as the well-known __idempotency tag and looked up via a tag query. This gives exactly-once starts under client retries, at-least-once queue redelivery, and multi-replica schedulers.

csharpvar instance = await engine.StartAsync(new StartRequest
{
    WorkflowId     = "process-order",
    IdempotencyKey = $"order:{orderId}"
});

Copying a Workflow Definition

Use the copy endpoint to create a new, independent workflow definition from an existing one. The copy has a distinct ID and label, starts in Draft status, and shares no lifecycle relationship with the source. It can be promoted, versioned, and deleted independently.

Via Admin API

httpPOST /api/flowengine/workflows/{sourceWorkflowId}/copy
Content-Type: application/json

{
  "newWorkflowId": "expense-approval-v2",
  "newLabel":      "Expense Approval (Revised)",
  "newVersion":    "1.0.0",
  "sourceVersion": "2.1.0"   // omit to copy the latest version
}

Returns 201 Created with the new WorkflowDefinition in the response body. Returns 404 Not Found if the source workflow or version does not exist.

Via IFlowEngineAdminApi

csharpvar copy = await adminApi.CopyWorkflowAsync(
    sourceWorkflowId: "expense-approval",
    sourceVersion:    null,           // null = latest
    newWorkflowId:    "expense-approval-v2",
    newLabel:         "Expense Approval (Revised)",
    newVersion:       "1.0.0");

// copy.Status == DefinitionStatus.Draft
// Promote when ready:
await adminApi.TransitionWorkflowStatusAsync(copy.Id, copy.Version, DefinitionStatus.Active);

What is copied: all node definitions, edges, policies (retry, circuit breaker, lease duration), default tags, entry node, global failure/deadline handlers, compensation flag, persist-after-every-node flag, params schema, description, and intent. CreatedAt/UpdatedAt are reset to the time of copying.

Instance Retention & Dead-Letter

RetentionPolicy / UseRetentionPolicy

Register a background retention service that archives terminal instances older than a configured age. The service runs on a configurable interval and calls IExecutionStateStore.ArchiveAsync to bulk-delete matching instances.

csharpbuilder.Services.AddFlowEngine()
    .UseStateStoreSql<AppDbContext>()
    .UseRetentionPolicy(new RetentionPolicy
    {
        RetainFor  = TimeSpan.FromDays(90),           // keep instances for 90 days after terminal
        Statuses   = [ExecStatus.Completed,
                      ExecStatus.Cancelled],          // which terminal statuses to archive
        RunEvery   = TimeSpan.FromHours(6)            // how often InstanceRetentionService runs
    });

InstanceRetentionService is a background IHostedService registered automatically by UseRetentionPolicy. On each run it calls:

csharp// Called by InstanceRetentionService — not called directly in normal usage
await stateStore.ArchiveAsync(
    olderThan: DateTimeOffset.UtcNow - policy.RetainFor,
    statuses:  policy.Statuses,
    ct);

IDeadLetterStore / UseDeadLetterStore

When an instance reaches Faulted status and no recovery path (GlobalOnFailureNodeId, retry policy) is available, the engine automatically enqueues the instance to the dead-letter store if one is registered. Register a dead-letter store implementation:

csharpbuilder.Services.AddFlowEngine()
    .UseStateStoreSql<AppDbContext>()
    .UseDeadLetterStore<SqlDeadLetterStore>();   // or RedisDeadLetterStore, etc.

The engine resolves IDeadLetterStore optionally from DI (services.GetService<IDeadLetterStore>()). When present, after EmitFinalEvent for a Faulted instance the engine calls IDeadLetterStore.EnqueueAsync. Instances without a registered dead-letter store simply fault and stay in the state store.

ReplayFromDeadLetterAsync

To replay a faulted instance from the dead-letter store, call:

csharp// Resets instance to Running and re-enters the execution loop
await engine.ReplayFromDeadLetterAsync(instanceId, ct);

The engine loads the dead-letter entry, resets instance.Status = Running, clears instance.Error, saves state, removes the entry from the dead-letter store, and re-enters ExecuteLoopAsync from the last saved CurrentNodeId.

Metrics

UseMetrics() / MeterFlowEngineTelemetry

Call UseMetrics() on the builder to enable System.Diagnostics.Metrics instrumentation. This registers MeterFlowEngineTelemetry as the IFlowEngineTelemetry implementation and exposes 5 metrics under the meter name "EF.FlowEngine":

Metric nameTypeDescription
flowengine.instances.activeGauge (int)Count of instances currently in Running state on this process
flowengine.instances.completed_totalCounter (long)Cumulative count of instances that reached Completed
flowengine.instances.failed_totalCounter (long)Cumulative count of instances that reached Faulted, TimedOut, or CycleDetected
flowengine.instance.duration_msHistogram (double)End-to-end instance duration in milliseconds (recorded at terminal state)
flowengine.node.duration_msHistogram (double)Per-node execution duration in milliseconds (tagged with nodeType)

The counters and histograms carry low-cardinality dimensional tags — workflowId, tenantId (when set), and nodeType (node histogram only) — so dashboards can slice completions/failures/durations by workflow or tenant. Instance ids are deliberately not emitted as tags to keep series count bounded.

To emit metrics and distributed-trace spans from the same engine, call UseMetricsAndTracing() instead of UseMetrics(). It registers a composite telemetry sink over both MeterFlowEngineTelemetry and ActivitySourceFlowEngineTelemetry (the individual UseMetrics()/UseActivitySourceTelemetry() calls are otherwise mutually exclusive). Configure exporters for both the meter and the activity source named "EF.FlowEngine".

Registration

csharp// Enable FlowEngine metrics
builder.Services.AddFlowEngine()
    .UseStateStoreSql<AppDbContext>()
    .UseMetrics();

// Wire into OpenTelemetry (example — adjust to your OTel setup)
builder.Services.AddOpenTelemetry()
    .WithMetrics(metrics => metrics
        .AddFlowEngineInstrumentation()   // extension on MeterProviderBuilder
        .AddPrometheusExporter());

builder.Services.AddOpenTelemetry()
    .WithTracing(tracing => tracing
        .AddFlowEngineInstrumentation()   // extension on TracerProviderBuilder
        .AddOtlpExporter());

AddFlowEngineInstrumentation() is an extension method on both MeterProviderBuilder and TracerProviderBuilder that adds the "EF.FlowEngine" meter/activity source to the pipeline. Without calling UseMetrics(), the engine uses the default LoggerFlowEngineTelemetry and no metrics are emitted.
