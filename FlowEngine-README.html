FlowEngine

A declarative, serializable workflow orchestration engine for durable async business processes.

Define complex workflows as plain JSON — store them in a database, version them like data, edit them without deploying code — and execute them durably across any number of server instances with full state persistence, distributed locking, and automatic crash recovery.

Why FlowEngine?

Business workflows are hard to get right. Human approvals can take days. External APIs fail and need retries. Long-running processes span server restarts. Multiple team members need to act in sequence. Rules change frequently. And the whole thing needs to be auditable.

Most approaches force a choice between:

  • Code-based workflow (Temporal, Azure Durable Functions) — durable and powerful, but logic is locked in code. Changing a business rule means a code change and a deployment.
  • Visual workflow platforms (Power Automate, Zapier) — accessible to non-developers, but limited expressiveness and poor integration with your existing typed data model.

FlowEngine takes a different path. Workflows are serializable JSON definitions that live in your database alongside your data. Business rules can be changed through data operations. The compiled execution is typed, with deep integration into your existing .NET entity model via FilterBuilder. The execution engine is designed for durable operation — async steps persist state, release server resources, and can resume on another server instance.

WorkflowDefinition (JSON in database)
         │
         ▼
    FlowEngine
         │
         ├── Compiles FilterBuilder conditions → EF Core queries
         ├── Persists state to SQL / Redis / Cosmos / Azure Table
         ├── Coordinates across servers via distributed locking
         └── Resumes from webhooks / Service Bus / Event Grid
         │
         ▼
  ExecutionInstance
  (persisted, auditable, resumable)

Orchestration, Choreography & Hybrid Patterns

FlowEngine is primarily an orchestration engine: one central workflow definition controls the entire business process. Understanding when to use orchestration, choreography, or a hybrid combination is key to designing effective systems.

Orchestration

A single workflow definition governs the full process flow — every step, branch, retry, and compensation. The engine drives execution; services respond to instructions.

Strengths: visible end-to-end process, single retry/compensation strategy, easy debugging, full audit trail. Trade-off: services are coordinated by the engine; adding a step means updating the workflow definition.

Choreography

Each service knows what to do when it receives a domain event. There is no central coordinator — services react autonomously and emit their own events.

Strengths: loose coupling, independently deployable services, naturally event-driven. Trade-off: overall process flow is implicit, distributed failure handling is complex, observability requires event tracing across all participants.

Hybrid — FlowEngine's sweet spot for complex systems

FlowEngine orchestrates the business process core while allowing choreography at the edges via its message and wait node types:

  • A message node publishes a domain event (e.g., order.created) to a registered IMessageClient (Service Bus, Event Grid). Independent downstream services react autonomously — they have no knowledge of the workflow.
  • A wait node suspends the workflow until an external event arrives (e.g., order.fulfilled signaled via ResumeAsync(eventName, correlationKey)).

The workflow remains the authoritative record of process intent and state. External participants stay fully decoupled.

Agents in hybrid systems

agent nodes (IAgentClient — OpenAI, Azure AI Foundry, Semantic Kernel) embed LLM/AI reasoning directly inside an orchestrated flow. The agent may call tools, reason over context, or produce structured decisions — but the workflow graph controls sequencing, retries, and compensation, making AI-driven steps durable, observable, and auditable.

Typical hybrid pattern with agents:

  1. agent node reasons over data and produces a structured output (e.g., classification or risk score)
  2. decision node routes based on agent output
  3. message node publishes a domain event for downstream services to react independently
  4. wait node suspends until an external confirmation arrives via ResumeAsync
  5. human node handles low-confidence or escalation cases

When to use each pattern

Pattern Use when
Orchestration Process has a clear sequence, compensation requirements, audit needs, or human-in-the-loop steps
Choreography Independent bounded contexts that must remain fully decoupled with no shared process state

Quick Start

1. Register FlowEngine

builder.Services.AddDbContextFactory<AppDbContext>(opts =>
  opts.UseSqlServer(builder.Configuration.GetConnectionString("appdb")));

builder.Services.AddSingleton<IConnectionMultiplexer>(_ =>
  ConnectionMultiplexer.Connect(builder.Configuration.GetConnectionString("redis")!));

builder.Services.AddFlowEngine(options =>
{
    options.DefaultLeaseDuration   = TimeSpan.FromSeconds(30);
    options.LeaseRenewalInterval   = TimeSpan.FromSeconds(13);
    options.SweepInterval          = TimeSpan.FromSeconds(30);
})
.UseStateStoreSql<AppDbContext>()    // AppDbContext : DbContext, IFlowEngineStateDbContext
.UseLockProviderRedis()
// All 19 built-in node executors are registered automatically by AddFlowEngine().
// Use .AddNodeExecutor<T>() only to register custom executors.
// Register your external clients
.AddHttpClient("payment-api")                              // built-in IRequestResponseClient
.AddClient<EfCoreQueryClient<CrmContext>>()                // DI-resolved IQueryClient
.AddClient("order-events", new ServiceBusMessageClient(sbClient, "orders"));

3. Register and start a workflow

// Register the workflow definition
var registry = app.Services.GetRequiredService<IWorkflowRegistry>();
await registry.SaveAsync(workflowDefinition, ct);

// Start an execution
var engine   = app.Services.GetRequiredService<IFlowEngine>();
var instance = await engine.StartAsync(new StartRequest
{
    WorkflowId    = "expense-approval",
    Entity        = new JsonContextValue { Value = JsonSerializer.SerializeToElement(expenseReport) },
    CorrelationId = expenseReport.Id.ToString(),
    TenantId      = currentTenant.Id    // optional — propagated to ExecutionInstance, filterable in queries
});

Console.WriteLine($"Status: {instance.Status}");  // Suspended (waiting for manager)
Console.WriteLine($"Instance: {instance.InstanceId}");

Sync request-response pattern: StartAsync runs the entire workflow on the calling thread and returns only when the workflow reaches a terminal state (Completed, Faulted) or a suspension node (human, wait, timer, message RequestReply). For workflows composed entirely of non-suspending nodes — query, integration, fetch, compute, decision, etc. — StartAsync returns Completed with the full output context in a single await. No polling required.

var result = await engine.StartAsync(request, ct);
if (result.Status == ExecStatus.Completed)
    return result.Context["outputKey"];   // result available immediately

Use StartBackgroundAsync only when you explicitly want fire-and-forget behavior (event handlers, bulk launches, or when the workflow is expected to suspend).

Background variants: All mutating entry points have a *BackgroundAsync counterpart that persists state and fires execution on the thread pool, returning immediately with the instance in Running status. The caller can respond with the instanceId and the client polls for completion. StartManyAsync starts multiple instances concurrently; a failure on one does not abort the others.

// Start — fire and observe
var instance = await engine.StartBackgroundAsync(request, ct);

// Resume via event name + correlation key — fire and observe
var instance = await engine.ResumeBackgroundAsync(instanceId, "payment.confirmed", orderId, payload, ct);

// Resume by instance ID (admin / retry) — fire and observe
var instance = await engine.ResumeByInstanceIdBackgroundAsync(instanceId, signalPayload, ct);

// Bulk launch — returns list of started instances in request order
var instances = await engine.StartManyAsync(requests, ct);

4. Resume from an external signal

// Webhook handler — manager responded via internal UI
app.MapPost("/api/tasks/{taskId}/complete", async (
    string taskId, TaskResponsePayload payload,
    IHumanTaskStore taskStore, IFlowEngine engine) =>
{
    await taskStore.SubmitResponseAsync(taskId, payload.ResponseToken, payload.FormValues);
    // Engine resumes automatically
    return Results.Ok();
});

// Or resume from Service Bus
processor.ProcessMessageAsync += async args =>
{
    var body = args.Message.Body.ToObjectFromJson<dynamic>();
    var instanceId = (string)body.instanceId;  // for logging; lookup uses event+correlation

    // Synchronous — awaits until the next suspension point or completion
    await engine.ResumeAsync(
        instanceId:     instanceId,
        eventName:      args.Message.Subject,
        correlationKey: body.expenseReportId.ToString(),
        signalPayload:  JsonSerializer.SerializeToElement(body)
    );

    // Background — returns immediately with Status=Running; workflow continues on thread pool
    // await engine.ResumeBackgroundAsync(instanceId, args.Message.Subject,
    //     body.expenseReportId.ToString(), JsonSerializer.SerializeToElement(body), ct);

    await args.CompleteMessageAsync(args.Message);
};

Multi-tenancy

Pass TenantId on StartRequest to tag every execution instance with a tenant identifier. The value is stored on ExecutionInstance.TenantId and is propagated through the full execution lifetime.

var instance = await engine.StartAsync(new StartRequest
{
    WorkflowId = "expense-approval",
    Entity     = ...,
    TenantId   = currentUser.TenantId   // propagated to ExecutionInstance
});

Filter by tenant when querying instances:

var instances = await stateStore.QueryAsync(new ExecutionQuery
{
    TenantId   = "tenant-abc",           // only return instances for this tenant
    Status     = InstanceStatus.Suspended,
    WorkflowId = "expense-approval"
}, ct);

Important: TenantId is a contract-level field. Each state store implementation is responsible for filtering on it. The engine does not enforce tenant isolation — combine with application-layer authorization to prevent cross-tenant reads.

Throttle Providers

Throttle policies (ConcurrencyLimit, RateLimit) on IFlowClient are enforced via pluggable provider interfaces (IDistributedConcurrencyLimiter, IDistributedRateLimiter).

Backend Package Use when
InMemory (default) Built into EF.FlowEngine Single process, dev/test, or when cluster-wide throttling is not required
Redis Throttles.Redis Multi-node — atomic Lua scripts; sliding-window rate + INCR concurrency counter
SQL Throttles.Sql Multi-node without Redis — EF Core optimistic-concurrency; fixed-window rate

Important: The default InMemoryDistributedThrottleProvider is process-local. Each replica enforces limits independently — effective cluster limit is limit × node-count. For strict cluster-wide throttling in multi-replica deployments, replace it with RedisThrottleProvider or SqlThrottleProvider<TContext>.

State Store Resilience

// Wrap IExecutionStateStore with a Polly retry pipeline for transient I/O faults
builder.UseStoreResiliency();

// Custom options
builder.UseStoreResiliency(new StoreResilienceOptions
{
    MaxRetryAttempts   = 3,
    RetryDelay         = TimeSpan.FromMilliseconds(500),
    CircuitBreakerErrors = 5
});

ConcurrencyException is never retried — it represents a deliberate optimistic-concurrency conflict, not a transient fault. UseStoreResiliency() must be called after UseStateStore*() so it decorates the correct registration.

Security Policy

Two FlowEngineOptions flags let operators disable Roslyn execution for environments where workflow definitions come from untrusted authors:

Option Default Effect when false
AllowComputeNodes true StartAsync / StartBackgroundAsync rejects any workflow definition that contains a compute node
AllowWhenExpressions true StartAsync / StartBackgroundAsync rejects any workflow definition that has a when predicate on any edge

Set both to false to prohibit all Roslyn execution on that engine node.

builder.Services.AddFlowEngine(options =>
{
    options.AllowComputeNodes    = false;   // no Roslyn compute nodes
    options.AllowWhenExpressions = false;   // no Roslyn edge predicates
});

When a workflow is rejected, StartAsync throws ArgumentException with a message identifying the blocked construct. Workflows that were already started before the policy was applied are not affected — the policy is enforced per-invocation, not at registration time.

Note: This is an operator-level kill switch, not a sandbox. Expressions in workflows started before the flags were set will still run. For untrusted multi-tenant authoring, combine these flags with a separate IWorkflowRegistry tenant isolation layer.

Health Checks

FlowEngineHealthCheck implements IHealthCheck. It probes two core infrastructure components (hard Unhealthy on failure) plus optional operational signals reported only when their stores are registered. Optional signals compose to the worst reported status:

Lock provider FindResumableInstanceIdsAsync(...) Unhealthy

Per-Workflow Concurrency Caps

MaxConcurrentExecutions caps total in-process executions across all workflows. For finer isolation — preventing one high-volume workflow from starving others — set per-workflow limits:

builder.Services.AddFlowEngine(options =>
{
    options.MaxConcurrentExecutions = 500;          // global ceiling
    options.PerWorkflowConcurrencyLimits = new()
    {
        ["nightly-batch"]  = 5,   // batch job: max 5 concurrent
        ["ai-enrichment"]  = 10,  // LLM-heavy: isolate from other traffic
    };
    options.GlobalOverflowPolicy = AdmissionOverflowPolicy.Reject;
});

When the cap for a workflow is hit, StartAsync and StartBackgroundAsync throw WorkflowCapacityExceededException immediately (carrying WorkflowId and CurrentDepth). The per-workflow check runs before the global semaphore — a capped workflow cannot consume a global slot it cannot use.

GlobalOverflowPolicy also applies to the global semaphore: Block (default) waits for a slot; Reject throws immediately when the global cap is full.

Multi-Replica Sweep Partitioning

By default every replica's sweep service scans the same set of instances. With many replicas this creates contention. Assign each replica a disjoint partition of the instance namespace so each pod handles its own slice:

// Read the pod ordinal injected by Kubernetes StatefulSet
var index = int.Parse(Environment.GetEnvironmentVariable("INSTANCE_INDEX") ?? "0");
var count = int.Parse(Environment.GetEnvironmentVariable("REPLICA_COUNT") ?? "1");

builder.Services.AddFlowEngine(options =>
{
    options.SweepPartitionCount = count;
    options.SweepPartitionIndex = index;
});

The engine uses fixed UTF-8 FNV-1a hashing: fnv1a(instanceId) % partitionCount == partitionIndex. Partition 0 and partition 1 together cover every instance with no overlap across processes and deployments. Use SweepPartitionCount = 1 (default) for single-replica deployments.

Intake Queue

The intake queue decouples workflow submission from execution. Without an intake queue, StartAsync begins executing immediately — under burst load this saturates the thread pool. With an intake queue, submitted workflows enter a Queued state first; a drain service pulls from the queue within MaxConcurrentExecutions.

In-memory (default — no extra package)

builder.Services.AddFlowEngine()
    .UseInMemoryIntakeQueue(depth: 1000, overflow: AdmissionOverflowPolicy.Reject);

depth: 0 = unbounded. Reject throws WorkflowCapacityExceededException when the channel is full. Block waits for a slot.

When the intake queue is registered, StartAsync and StartBackgroundAsync return the instance in Queued status immediately instead of blocking until the first suspension point. The IntakeDrainService (registered automatically as an IHostedService) pulls instances from the queue and executes them within the concurrency cap.

On restart, IntakeDrainService re-hydrates any Queued instances from the state store so no submissions are lost.

SQL (EF.FlowEngine.IntakeQueue.Sql)

Durable — survives process restarts. Shared across replicas via a FlowEngineIntakeQueue table polled with SKIP LOCKED.

flowEngineBuilder.UseIntakeQueueSql<AppDbContext>();

Redis (EF.FlowEngine.IntakeQueue.Redis)

Durable via Redis Streams with consumer groups (XADD/XREADGROUP/XACK). Shared across replicas.

flowEngineBuilder.UseIntakeQueueRedis(
    streamKey:      "flowengine:intake",
    groupName:      "flowengine-drain",
    consumerName:   null,        // defaults to machine name
    blockMs:        2000,        // XREAD block timeout
    pendingClaimMs: 30_000);     // reclaim stalled messages after 30 s

Azure Service Bus (EF.FlowEngine.IntakeQueue.ServiceBus)

Durable via ASB PeekLock. Failed messages move to the Dead-Letter Queue after max delivery count.

flowEngineBuilder.UseIntakeQueueServiceBus(
    queueName:              "flowengine-intake",
    fullyQualifiedNamespace: "myns.servicebus.windows.net");

Requires ServiceBusClient in DI (e.g. via Microsoft.Extensions.Azure).

OpenTelemetry Trace Context

FlowEngine can propagate W3C traceparent across suspension/resume boundaries so every resume in Jaeger, Application Insights, or Grafana links back to the originating trace.

Register the ActivitySource-backed telemetry implementation and wire both tracing and metrics in one call:

builder.Services.AddFlowEngine()
    .UseActivitySourceTelemetry();     // or .UseMetrics() for System.Diagnostics.Metrics

builder.Services.AddOpenTelemetry()
    .WithTracing(t => t.AddFlowEngineInstrumentation())   // adds source "EF.FlowEngine"
    .WithMetrics(m => m.AddFlowEngineInstrumentation());  // adds meter  "EF.FlowEngine"

AddFlowEngineInstrumentation() is an extension method on both TracerProviderBuilder and MeterProviderBuilder (from the core EF.FlowEngine package — no separate instrumentation package needed).

If you only want one or the other, use the individual AddSource/AddMeter calls directly:

builder.Services.AddOpenTelemetry()
    .WithTracing(t => t.AddSource("EF.FlowEngine"));

How it works: when a workflow suspends, the engine captures Activity.Current?.Id into ExecutionInstance.TraceContext. On resume, it restores that context as the parent of the new Activity before calling any node executors — so the resumed span is a child of the original request span even across HTTP boundaries.

TraceContext is a nullable string on ExecutionInstance and serializes into the JSON state blob automatically. No state store migration is needed.

When UseActivitySourceTelemetry is not called, the default LoggerFlowEngineTelemetry writes events to ILogger<FlowEngine> at Debug level and no Activity spans are created.

Input Validation with paramsSchema

Declare a JSON Schema string on a workflow definition to validate StartRequest.Params before execution begins. Supported keywords: required, properties (with type, enum, minimum, maximum).

{
  "id": "loan-application",
  "version": "1.0.0",
  "paramsSchema": "{\"required\":[\"applicantId\",\"requestedAmount\"],\"properties\":{\"applicantId\":{\"type\":\"string\"},\"requestedAmount\":{\"type\":\"number\",\"minimum\":1000,\"maximum\":500000}}}",
  "entryNodeId": "n-start",
  "nodes": { ... }
}

Using the fluent builder:

var definition = WorkflowDefinitionBuilder.Create("loan-application")
    .WithParamsSchema("""
        {
          "required": ["applicantId", "requestedAmount"],
          "properties": {

Output and Context Value Validation

Beyond input param validation, nodes can declare schemas for their outputs and for the context values they depend on.

outputSchema — validate a node's output before storing

Set outputSchema (JSON Schema draft-07 subset) on any node alongside storeAs. The engine validates the output before writing it to $.context.{storeAs}. If validation fails, the node produces DecisionOutcome.Error and the invalid value is never stored.

// Fluent builder
.AddNode("call-api", "fetch", new FetchNodeConfig { ... })
    .WithStoreAs("apiResult")
    .WithOutputSchema("""
        {
          "type": "object",
          "required": ["orderId", "status"],
          "properties": {
            "orderId": { "type": "string" },
            "status":  { "type": "string", "enum": ["ok", "failed"] }
          }
        }
        """)
    .ThenOn("next-node", DecisionOutcome.Match)
    .ThenOn("schema-error-handler", DecisionOutcome.Error)
    .Done()
// JSON workflow definition
{
  "id": "call-api", "type": "fetch",
  "storeAs": "apiResult",
  "outputSchema": "{\"type\":\"object\",\"required\":[\"orderId\",\"status\"]}",
  "config": { ... },
  "edges": [
    { "on": ["Match"], "nextNodeId": "next-node" },
    { "on": ["Error"], "nextNodeId": "schema-error-handler" }
  ]
}

agent nodes: AgentNodeConfig.outputSchema (config-level) shapes the LLM prompt for structured output. NodeDefinition.outputSchema (definition-level) is the engine-side gate. Set both to the same schema when you want the LLM to produce the right shape and the engine to enforce it.

Error code: OUTPUT_SCHEMA_VALIDATION_FAILED — appears in NodeExecutionRecord.Error and routes through normal DecisionOutcome.Error edge evaluation.

contextRequirements — assert required context keys before execution

Declare keys that must be present in $.context.* before a node runs. Each key has an optional per-key JSON Schema.

// Fluent builder
.AddNode("process-result", "compute", new ComputeNodeConfig { ... })
    .WithContextRequirement("apiResult")                            // presence-only
    .WithContextRequirement("eligibilityData", """{"type":"object","required":["tier"]}""")
    .Done()
// JSON workflow definition
{
  "id": "process-result", "type": "compute",
  "contextRequirements": {
    "apiResult": null,
    "eligibilityData": "{\"type\":\"object\",\"required\":[\"tier\"]}"
  },
  "config": { ... }
}

If a required key is missing or fails its schema, the executor is never called and the node produces DecisionOutcome.Error with code CONTEXT_REQUIREMENTS_FAILED.

Supported schema keywords: full JSON Schema draft-07 — type, required, properties, enum, minimum, maximum, anyOf, oneOf, $ref (internal), pattern, minLength, maxLength, minItems, maxItems, and more — backed by NJsonSchema.

Registration-time checks: WorkflowDefinitionValidator (called by IWorkflowRegistry.SaveAsync) catches outputSchema set without storeAs, and malformed schema JSON in either field, at registration time rather than at runtime.

Workflow Authoring Lifecycle

Definitions follow a three-status lifecycle. Only Active definitions can be started.

Draft ◄──► Active ──► Archived
               ◄──────────────
Status New instances Editable Deletable
Draft No Yes Yes
Active Yes No No (auto-demoted on delete)
Archived No No No (unarchive first)

Archiving only gates new instance creation — any in-flight instances continue to completion normally.

// Save a new definition (saved as Draft by default)
await registry.SaveAsync(definition, ct);

// Activate a draft (makes it startable and immutable)
await registry.TransitionStatusAsync("expense-approval", "1.0.0", DefinitionStatus.Active, ct);

// List active definitions
var defs = await registry.ListAsync(status: DefinitionStatus.Active, ct: ct);

// Move back to Draft to edit (stops new instances from starting)
await registry.TransitionStatusAsync("expense-approval", "1.0.0", DefinitionStatus.Draft, ct);

// Retire a workflow — prevents new starts, keeps definition for audit/history
await registry.TransitionStatusAsync("expense-approval", "1.0.0", DefinitionStatus.Archived, ct);

// Unarchive if needed
await registry.TransitionStatusAsync("expense-approval", "1.0.0", DefinitionStatus.Active, ct);

Running instances are pinned to the version they started on. Updating or archiving a definition never affects in-flight instances.

Compatibility Analysis

Before migrating instances, run CompatibilityAnalyzer.Analyze(from, to) to surface breaking changes between two workflow versions:

var report = CompatibilityAnalyzer.Analyze(v1Definition, v2Definition);

    Console.WriteLine($"[{finding.Severity}] {finding.Message}");

Entry node changed Warning New instances start at a different node
GlobalOnFailureNodeId changed Warning Error routing differs between versions

Migrating instances

When a workflow definition needs to change while instances are still running or suspended, use MigrateInstanceAsync to move them to the new version without replaying history:

// Load the suspended instance
var instance = await stateStore.LoadAsync(instanceId, ct);

// Build the updated definition (v2)
var v2 = WorkflowDefinitionBuilder.FromJson(existingJson)
    .WithVersion("2.0.0")
    // ... apply changes
    .Build();
await registry.SaveAsync(v2, ct);
await registry.TransitionStatusAsync("expense-approval", "2.0.0", DefinitionStatus.Active, ct);

// Migrate the suspended instance — nodeIdMap is optional; only needed if node IDs changed
await engine.MigrateInstanceAsync(
    instanceId,
    targetVersion: "2.0.0",
    nodeIdMap: new Dictionary<string, string>
    {
        ["n-old-approval"] = "n-manager-approval"   // renamed node
    },
    ct);

// Dry-run — validates remapping without persisting; history entry labeled "[dry-run]"
await engine.MigrateInstanceAsync(
    instanceId,
    targetVersion: "2.0.0",
    nodeIdMap: new Dictionary<string, string> { ["n-old-approval"] = "n-manager-approval" },
    dryRun: true,
    ct: ct);

// Instance is now pinned to v2.0.0 — resume it normally
await engine.ResumeByInstanceIdAsync(instanceId, ct: ct);
// or return immediately and let execution continue on the thread pool
await engine.ResumeByInstanceIdBackgroundAsync(instanceId, ct: ct);

Delete an old version only when no running or suspended instances reference it:

await engine.DeleteWorkflowVersionAsync("expense-approval", "1.0.0", ct);

Circuit Breaker

When a node executor's backing service is repeatedly unresponsive, the circuit breaker prevents every workflow instance from hammering it and burning through retries. Once the failure threshold is reached the circuit opens: subsequent instances skip the executor entirely and either follow a CircuitOpen edge (graceful degradation) or auto-suspend at the failing node until the cool-down period expires, at which point the sweep service resumes them transparently.

Policy inheritance mirrors RetryPolicy: set defaultCircuitBreakerPolicy on the workflow definition as a workflow-wide default; override with circuitBreakerPolicy on individual nodes.

{
  "id": "order-processing",
  "version": "1.0.0",
  "defaultCircuitBreakerPolicy": {
    "key": "external-apis",
    "failureThreshold": 5,
    "samplingWindow": "00:01:00",
    "openDuration": "00:00:30"
  },
  "nodes": {
    "n-call-payment": {
      "id": "n-call-payment",
      "type": "fetch",
      "circuitBreakerPolicy": {
        "key": "payment-svc",
        "failureThreshold": 3,
        "openDuration": "00:01:00"
      },
      "edges": [
        { "on": ["Match"],       "nextNodeId": "n-process-payment" },
        { "on": ["CircuitOpen"], "nextNodeId": "n-use-cached-result" },
        { "on": ["Error"],       "nextNodeId": "n-payment-failed" }
      ]
    }
  }
}

CircuitBreakerPolicy properties:

Property Default Description
key node type Groups nodes that share a backing service under one circuit. Omit to scope per node type.
failureThreshold 5 Number of failures within samplingWindow that trips the circuit
samplingWindow 00:01:00 Rolling window over which failures are counted
openDuration 00:00:30 How long the circuit stays open before the next attempt is allowed

Behaviors when the circuit is open:

Scenario Behavior
Node has a CircuitOpen edge Engine takes that edge — workflow continues via the alternate path
No CircuitOpen edge Instance suspends at the failing node with a timed wait equal to openDuration; the sweep service resumes it automatically after cool-down

Half-open recovery: After openDuration elapses, the circuit enters a HalfOpen state and allows exactly one probe request through. If the probe succeeds, the circuit closes. If it fails, the circuit re-opens for another full openDuration. All other concurrent callers remain blocked during the probe window. This behavior is built into InMemoryCircuitBreakerStore and should be implemented by custom ICircuitBreakerStore implementations for consistency.

Circuit state scope: InMemoryCircuitBreakerStore (the default) is a singleton — circuit state is shared across all workflow instances on the same process replica, so one instance discovering a failure protects the rest. Circuit state is per-replica (not distributed across replicas), but workflow instance state is always durable — suspended instances are picked up by the sweep service after a server restart, regardless of which replica holds the circuit state.

Distributed circuit breaker: For multi-replica deployments, replace the in-process store with a shared backend:

// Redis — requires IConnectionMultiplexer in DI
builder.UseCircuitBreakerRedis();

// SQL — requires IDbContextFactory<TContext> in DI
builder.UseCircuitBreakerSql<AppDbContext>();

Or swap manually:

builder.Services.AddSingleton<ICircuitBreakerStore, RedisCircuitBreakerStore>();

Prevent a single node type from monopolising the thread pool across all concurrent workflow instances. Set maxConcurrentNodeExecutions on any node definition:

{

// Fluent builder

Dead-Letter Store

When a workflow instance faults and has no remaining recovery path — retries exhausted, no GlobalOnFailureNode, compensation completed — it transitions to Faulted. Registering an IDeadLetterStore causes the engine to automatically enqueue a DeadLetterEntry for every such instance, making failed workflows inspectable and replayable without manual state store queries.

// Register — InMemoryDeadLetterStore from EF.FlowEngine.Testing (dev/test only)
builder.Services.AddFlowEngine()
    .UseDeadLetterStore<InMemoryDeadLetterStore>();

// Or with a factory (custom SQL/Redis implementation):
builder.Services.AddFlowEngine()
    .UseDeadLetterStore(sp => new MyRedisDeadLetterStore(sp.GetRequiredService<IConnectionMultiplexer>()));

Inspect and replay dead-lettered instances:

var dlStore  = services.GetRequiredService<IDeadLetterStore>();
var entries  = await dlStore.ListAsync(ct);

foreach (var entry in entries)
{
    Console.WriteLine($"{entry.InstanceId} — {entry.Reason} — {entry.EnqueuedAt:u}");
    Console.WriteLine($"  Last error: {entry.LastError?.Code}: {entry.LastError?.Message}");
}

// Replay one instance (resets status to Running, removes from dead-letter, re-enters execution loop)
var replayed = await engine.ReplayFromDeadLetterAsync(entries[0].InstanceId, ct);
Console.WriteLine($"Replayed: {replayed.Status}");   // Completed, Suspended, or Faulted

ReplayFromDeadLetterAsync throws InvalidOperationException when no IDeadLetterStore is registered. The replay re-enters ExecuteLoopAsync from CurrentNodeId — the instance resumes exactly where it faulted, with the original context intact.

The default implementation treats all ISO 8601 durations as calendar durations without business-day awareness.

// Option A — OpenTelemetry ActivitySource (traces)

public async Task ComputeNode_CalculatesTotal()

        .WithEntity(new { Price = 100m, Quantity = 3 })

        .Build();

    {

        Type   = NodeTypes.Compute,

        }),

    };

    var executor = new ComputeNodeExecutor();
    var result   = await executor.ExecuteAsync(node, ctx.Instance, ctx, CancellationToken.None);

    Assert.Equal(DecisionOutcome.Match, result.Outcome);
    // Verify stored value via ctx.Instance.Context
}

Chaos Testing — Fault Injection

Wrap any IExecutionStateStore with FaultableExecutionStateStore to simulate infrastructure failures:

var inner    = new InMemoryExecutionStateStore();
var faultable = new FaultableExecutionStateStore(inner);

// Inject into DI
services.AddSingleton<IExecutionStateStore>(faultable);

// In a test — fault the next save to verify crash recovery

var instance = await engine.StartAsync(request, ct);

// Engine should recover on next sweep and re-execute from last checkpoint

Suppressing the Engine in WebApplicationFactory Tests

When a consuming service uses WebApplicationFactory<TProgram>, the test host runs the real Program.cs, which calls AddFlowEngine(). For test scenarios that don't exercise workflow execution — API audits, controller tests, category tests — this triggers unnecessary engine initialization, background hosted services, and potentially DB schema creation, which can fail when the test environment doesn't have the required backend infrastructure.

Call AddFlowEngineTesting() inside ConfigureServices to replace the engine with a no-op stub and remove all four background services:

protected override void ConfigureWebHost(IWebHostBuilder builder)
{
    builder.ConfigureServices(services =>
    {
        // Replaces IFlowEngine with NullFlowEngine and removes
        // FlowEngineInitializationService, ExecutionSweepService,
        // LeaseRenewalService, and FlowEngineShutdownService.
        services.AddFlowEngineTesting();
    });
}

NullFlowEngine satisfies IFlowEngine — all methods return a stub ExecutionInstance with ExecStatus.Completed immediately. Registries, stores, and lock providers are left intact since they have no external dependencies by default (InMemory).

If you need the real engine but want to suppress the background loops (e.g. you control init and sweep explicitly in tests), use the narrower helper:

services.RemoveFlowEngineHostedServices();

Both methods are in the EF.FlowEngine.Testing package (FlowEngineWebHostTestingExtensions).

Transactional Outbox

The transactional outbox pattern guarantees at-least-once delivery for messages, integration calls, and agent invocations by writing outbox entries atomically with the workflow state save. A background drain service then publishes and removes entries.

SQL outbox (EF.FlowEngine.Outbox.Sql)

State row and outbox rows are written in the same SaveChangesAsync call — truly atomic within a single SQL transaction.

// AppDbContext must implement IFlowEngineStateDbContext + IFlowEngineOutboxDbContext
// and call mb.ApplyFlowEngineState() + mb.ApplyFlowEngineOutbox() in OnModelCreating.
builder.Services.AddFlowEngine()
    .UseStateStoreSql<AppDbContext>()
    .UseOutboxSql<AppDbContext>();

Redis outbox (EF.FlowEngine.StateStore.Redis)

RedisExecutionStateStore overrides SaveWithOutboxAsync to batch the instance SET and outbox LPUSH entries in a single Redis transaction — no separate outbox package needed.

builder.Services.AddFlowEngine()
    .UseStateStoreRedis()
    .UseOutboxRedis();    // registers RedisOutboxStore + OutboxDrainService

Cosmos outbox (EF.FlowEngine.StateStore.Cosmos)

CosmosExecutionStateStore uses TransactionalBatch (same partition key = instanceId) to upsert the instance document and create outbox documents atomically.

builder.Services.AddFlowEngine()
    .UseStateStoreCosmos(databaseId: "flowengine")
    .UseOutboxCosmos(databaseId: "flowengine");

Azure Table outbox (EF.FlowEngine.StateStore.AzureTable)

AzureTableExecutionStateStore uses Azure Table entity group transactions (SubmitTransactionAsync, same PartitionKey) to update the instance entity and insert outbox entities atomically.

builder.Services.AddFlowEngine()
    .UseStateStoreAzureTable()
    .UseOutboxAzureTable();

Idempotency keys ensure duplicate-safe re-delivery. Set IdempotencyKey on any message, agent, or integration node:

{
  "type": "message",
  "config": {
    "clientRef": "order-events",
    "subject":   "order.completed",
    "body":      { "orderId": "$.entity.OrderId" },
    "idempotencyKey": "$.entity.OrderId + '-order-complete'"
  }
}
{
  "type": "agent",
  "config": {
    "clientRef":       "gpt4o",
    "promptTemplate":  "Classify this order...",
    "idempotencyKey":  "$.entity.OrderId + '-classification'"
  }
}

WorkflowDefinitionValidator emits a warning when idempotencyKey is absent from any agent/message/integration node — it does not block registration, but the warning surfaces at save time.

Monitoring drain health — IOutboxStore.GetMetricsAsync returns aggregate stats:

var metrics = await outboxStore.GetMetricsAsync(ct);
Console.WriteLine($"Pending: {metrics.PendingCount}, Failed: {metrics.FailedCount}, " +
                  $"Oldest: {metrics.OldestPendingAge?.TotalMinutes:F1} min");

FailedCount is the number of entries currently in exponential back-off (next retry in the future). The drain service uses capped exponential back-off: min(2^n × 5 s, 300 s). FlowEngineHealthCheck uses OldestPendingAge to report Degraded when the drain falls behind.

See FlowEngine-Operations.html for detailed configuration and drain service options.

AI agent — IChatClient (EF.FlowEngine.Clients.AI)

Default connector for new workflows. Binds an agent-node clientRef to a DI-resolved Microsoft.Extensions.AI.IChatClient, so the same workflow JSON runs against any OpenAI-compatible endpoint (Foundry Local, Azure AI Foundry, OpenAI, Ollama, …) - only the host registration differs. No Azure SDK dependency. When a node declares an outputSchema, it is sent to the model as a JSON-schema response format. A node may also declare an optional instructions (system prompt) sent as a distinct system message ahead of the user promptTemplate.

// Host registers an IChatClient (e.g. Aspire's Aspire.Azure.AI.Inference).
// .UseFunctionInvocation() is required only if agent nodes are registered with tools.
builder.AddAzureAIInferenceChatClient("chat").UseFunctionInvocation().AsIChatClient();

builder.Services.AddFlowEngine()
    .AddChatClientAgentClient("ai-agent", sp => sp.GetRequiredService<IChatClient>());
// Keyed hosts: .AddChatClientAgentClient("ai-agent", serviceKey: "chat");
// With tools:  .AddChatClientAgentClient("ai-agent", sp => sp.GetRequiredService<IChatClient>(),
//                  tools: [ AIFunctionFactory.Create(GetWeather) ]);

Foundry lifecycle (local model via RunAsFoundryLocal() vs. an Azure deployment) is a host concern: FlowEngine consumes whichever IChatClient the host registers and stays model/transport agnostic. Foundry server-hosted / project agents (AIProjectClient.AsAIAgent(...)) are an Azure-only path; if you need them, register such an agent's IChatClient at the host and bind it the same way - no separate FlowEngine connector is required.

OpenAI / Azure OpenAI (EF.FlowEngine.Clients.OpenAI)

// OpenAIAgentClient backed by Microsoft.Extensions.AI IChatClient

builder.Services.AddFlowEngine()

Agent Governance

Content Filtering

Register a named IContentFilter and reference it by name in AgentNodeConfig.ContentFilterPolicy:

// Register a custom content filter
builder.Services.AddSingleton<IContentFilter, MyAzureContentSafetyFilter>();
{
  "type": "agent",
  "config": {
    "clientRef":           "gpt4o",
    "promptTemplate":      "Summarise the document: {{$.context.documentText}}",
    "contentFilterPolicy": "azure-content-safety",
    "promptVersion":       "v2.1-summarise"
  }
}

FilterInputAsync runs before the LLM call; FilterOutputAsync runs after. If either returns IsAllowed: false, the node short-circuits with DecisionOutcome.Error and ReplacementContent (if set) is stored as the output.

Prompt Versioning

Set AgentNodeConfig.PromptVersion to a label string. It is recorded in NodeExecutionRecord.Metadata["promptVersion"] for every execution — enabling A/B analysis and rollback tracking without changing the workflow definition ID.

Telemetry & Cost Tracking

AgentNodeExecutor emits a flow.agent.completed event via IFlowEngineTelemetry with:

builder.Services.AddFlowEngine(options =>
