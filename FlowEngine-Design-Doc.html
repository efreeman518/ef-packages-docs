Why FlowEngine?

Business workflows are hard to get right. Human approvals take days. External APIs fail and need retries. Long-running processes span server restarts. Multiple team members act in sequence. Rules change frequently. The whole thing needs to be auditable.

Most approaches force a choice:

ApproachTrade-off
Code-based — Temporal, Azure Durable FunctionsDurable and powerful, but logic is embedded in code. Changing a business rule means a code change and a deployment.
Visual platforms — Power Automate, ZapierAccessible to non-developers, but limited expressiveness and poor integration with your typed data model.
FlowEngineWorkflows as serializable JSON definitions. Business rules changed through data operations. Fully typed .NET execution with deep FilterBuilder integration. Durable by design.
WorkflowDefinition (JSON in database — versioned, changeable without redeploying code) │ ▼ FlowEngine │ ├── Compiles FilterBuilder conditions → EF Core queries ├── Persists state to SQL / Redis / CosmosDB / Azure Table ├── Coordinates across servers via distributed locking └── Resumes from webhooks / Service Bus / Event Grid │ ▼ ExecutionInstance (persisted · auditable · resumable)

Orchestration, Choreography & Hybrid Patterns

FlowEngine is primarily an orchestration engine: one central workflow definition controls the entire business process. Understanding when to use orchestration, choreography, or a hybrid combination is key to designing effective systems.

Orchestration

A single workflow definition governs the full process flow — every step, branch, retry, and compensation. The engine drives execution; services respond to instructions.

Strengths: visible end-to-end process, single retry/compensation strategy, easy debugging, full audit trail.
Trade-off: services are coordinated by the engine; adding a step means updating the workflow definition.

Choreography

Each service knows what to do when it receives a domain event. There is no central coordinator — services react autonomously and emit their own events.

Strengths: loose coupling, independently deployable services, naturally event-driven.
Trade-off: overall process flow is implicit, distributed failure handling is complex, observability requires tracing events across all participants.

Hybrid — FlowEngine's sweet spot for complex systems

FlowEngine orchestrates the business process core while allowing choreography at the edges via its message and wait node types:

  • A message node publishes a domain event (e.g., order.created) to a registered IMessageClient (Service Bus, Event Grid). Independent downstream services react autonomously — they have no knowledge of the workflow.
  • A wait node suspends the workflow until an external event arrives (e.g., order.fulfilled signaled via ResumeAsync(eventName, correlationKey)).

The workflow remains the authoritative record of process intent and state. External participants stay fully decoupled.

Workflow (orchestrates the core process) │ ├── message node → publishes domain event → external services react independently (choreography) ├── wait node ← suspends until external event arrives via ResumeAsync └── agent node ↔ LLM/AI reasoning (durable, observable, compensatable) │ ▼ ExecutionInstance (single source of truth for process state)

Agents in hybrid systems

agent nodes (IAgentClient — OpenAI, Microsoft Foundry, Semantic Kernel, Microsoft Agent Framework) embed LLM/AI reasoning directly inside an orchestrated flow. The agent may call tools, reason over context, or produce structured decisions — but the workflow graph controls sequencing, retries, and compensation, making AI-driven steps durable, observable, and auditable.

Typical hybrid pattern with agents:

  1. agent node reasons over data and produces a structured output (e.g., classification or risk score)
  2. decision node routes based on agent output
  3. message node publishes a domain event for downstream services to react independently
  4. wait node suspends until an external confirmation arrives via ResumeAsync
  5. human node handles low-confidence or escalation cases

Console.WriteLine($"Status: {instance.Status}");    // Suspended (waiting for manager)
Console.WriteLine($"Instance: {instance.InstanceId}");

4. Resume from an external signal

csharp// Task response via internal UI — background variant returns immediately; workflow continues on thread pool
app.MapPost("/api/tasks/{taskId}/complete", async (
    string taskId, TaskResponsePayload payload, IHumanTaskStore taskStore) =>
{

// Use SubmitResponseAsync if you need to wait for the workflow to reach its next suspension point.

// Or resume from Service Bus — background keeps the message handler fast
processor.ProcessMessageAsync += async args =>
{
    var body = args.Message.Body.ToObjectFromJson<dynamic>();
    await engine.ResumeBackgroundAsync(

        eventName:      args.Message.Subject,
        correlationKey: body.expenseReportId.ToString(),
        signalPayload:  JsonSerializer.SerializeToElement(body));
    await args.CompleteMessageAsync(args.Message);
};

Architecture

FlowEngine separates the workflow blueprint (a versioned JSON definition) from the execution state (a persisted instance). The engine loop mediates: acquire claim → load state → execute node → handle retry → advance edge → save state → release or suspend.

WorkflowDefinition (JSON — stored once, executed many times, versioned) entryNodeId where all new instances begin nodes keyed dictionary of NodeDefinition each: type · config · edges · storeAs · intent · maxVisits intent plain-language description for agents + humans ExecutionInstance (persisted to state store at every async boundary) instanceId · workflowId · workflowVersion · correlationId status Running | Suspended | Completed | Faulted | TimedOut | CycleDetected currentNodeId executing now, or where execution is suspended context $.entity · $.params · $.context (grows as nodes execute) history immutable append-only audit trail, one record per node pendingWait what event + correlationKey will resume this instance nodeVisitCounts visits per node — rework limits and cycle detection claimedBy / claimExpiresAt distributed lock fields Engine Loop (one iteration per node) TryAcquire → Load → Execute → Retry? → StoreAs → Edge eval → Advance → Save → Release Save fires at: wait/human (Suspended) · output (Completed) · fault · checkpoint (mid-chain)

Core Concepts

WorkflowDefinition

The static, versioned blueprint. Serializes to/from JSON. Stored once, executed many times. In-flight instances are pinned to the version they started on — updating a definition never affects running instances.

csharppublic sealed class WorkflowDefinition
{
    // Identity
    public string  Id          { get; init; }  // stable across versions
    public string  Version     { get; init; }  // semver
    public string  Label       { get; init; }  // human-readable display name
    public string? Description { get; init; }  // prose description
    public string? Intent      { get; init; }  // AI-routing hint
    public string? CreatedBy   { get; init; }

    // Status
    public DefinitionStatus Status { get; set; }  // Draft | Active | Archived  (transitions: Draft ↔ Active, Active ↔ Archived)

    // Graph
    public string EntryNodeId { get; init; }
    public Dictionary<string, NodeDefinition> Nodes { get; init; }

    // Failure / deadline handlers
    public string? GlobalOnFailureNodeId  { get; init; }  // reroutes unhandled Error
    public string? GlobalOnDeadlineNodeId { get; init; }  // reroutes instance deadline exceeded

    // Defaults applied to all instances
    public RetryPolicy?              DefaultRetryPolicy          { get; init; }
    public CircuitBreakerPolicy?     DefaultCircuitBreakerPolicy { get; init; }  // null = no circuit breaking by default
    public TimeSpan?                 DefaultLeaseDuration { get; init; }
    public Dictionary<string,string> DefaultTags         { get; init; }

    // Saga compensation
    public bool EnableCompensation { get; init; }  // default false

    // Input validation (JSON Schema draft-07 subset)
    public string? ParamsSchema { get; init; }
}

ExecutionInstance

Each run of a workflow is an ExecutionInstance — isolated from definition changes, persistently saved at every async boundary, and fully auditable.

Every edge specifies which DecisionOutcome values it handles and an optional when predicate. Edges are evaluated in order — first match wins. Backward edges (referencing earlier nodes) are fully supported for rework and retry patterns.

Workflow Execution Model

This section describes how the definition types wire together at execution time — from the static blueprint down to the moment the engine decides where to go next.

Type hierarchy

├── EntryNodeId: string                    → first node to execute
├── GlobalOnFailureNodeId: string?         → fallback on unhandled Error outcome
├── GlobalOnDeadlineNodeId: string?        → fallback when instance.Deadline exceeded
├── EnableCompensation: bool               → true: saga rollback via CompensationNodeId (default false)
├── ParamsSchema: string?                  → JSON Schema validated against StartRequest.Params before any node runs

Per-node execution sequence

Fig — Per-node execution decision tree

Step 1 — Validate + StoreAs. If node.StoreAs is set and result.Output is not null, the engine first runs schema validation (if node.OutputSchema is set), then writes the output into $.context.{StoreAs} before edge evaluation.

Output schema validation: when node.OutputSchema is non-null, the output JsonElement is validated against the JSON Schema (draft-07 subset: type, required, properties, enum, minimum, maximum). If validation fails, the node result is rewritten to DecisionOutcome.Error with error code OUTPUT_SCHEMA_VALIDATION_FAILED and the invalid value is not stored. This lets the same Error edges that handle runtime failures also handle schema contract violations without any additional routing logic. Validation is skipped for DocumentContextValue and NullContextValue outputs; those pass through unchanged.

When validation passes (or no schema is set), output is written to context. Because this happens before edges are tested, a node's own when guards can read the value the node just produced — a single fetch, integration, or compute node can store its result and branch on it without a separate decision node.

storeAs writes to a plain dictionary key — each write overwrites the previous value. If a node is revisited (e.g. inside a loop or rework cycle), $.context.{storeAs} holds only the value from the most recent visit. Every visit does record an OutputSnapshot in instance.History (alongside the node ID, outcome, branch taken, and timestamps), providing a full audit trail — but that history is not addressable by when expressions or any node at runtime. To accumulate outputs across revisits, use a compute node to append the current value to an array in context before the next iteration can overwrite the key.

Context requirements validation runs before the executor is called (before Step 0 — Execute in the diagram). If node.ContextRequirements is non-null, each declared key is checked for presence in $.context.*; if a schema is provided for that key, it is validated against ValidateOutput. Missing or schema-invalid keys produce DecisionOutcome.Error with code CONTEXT_REQUIREMENTS_FAILED and the executor is never invoked. Key names use the bare context key convention (no $.context. prefix), matching storeAs.

Step 2 — Check for suspension. If result.PendingWait != null, the instance status transitions to Suspended, state is saved, and the distributed lock is released. Edge evaluation is skipped — edges fire after the wait resolves, with DecisionOutcome.Match as the outcome.

Step 3 — Evaluate edges. Edges in node.Edges are tested left-to-right; the first that passes both filters wins:

text① Outcome filter:  edge.On is null/empty  OR  edge.On.Contains(result.Outcome)
② When guard:      edge.When is null       OR  WhenEvaluator(edge.When) is truthy
→ Both pass → follow this edge (CurrentNodeId = edge.NextNodeId)
→ Either fails → try next edge

When expressions are Roslyn C# booleans. Four read-only globals are injected:

GlobalContents
Context$.context.* items as Dictionary<string, object?>
Entity$.entity fields as Dictionary<string, object?>
Params$.params.* items as Dictionary<string, object?>
EngineMetadata: instanceId, workflowId, currentNodeId, status, visits (per-node map), totalVisits

"(decimal)Context[\"riskScore\"] > 750"

Expression compilation and caching. WhenEvaluator compiles each distinct expression string to a delegate on first use via Roslyn and caches the result in a bounded LRU cache (size and execution timeout are configurable). Compilation is not on the hot path for steady-state workflows, but workflows with a large number of distinct When expressions — or those that generate expression strings dynamically — should be aware of the cold-compile cost and cache eviction behaviour.

Step 4 — Handle no matching edge:

node.Edges is emptyTerminal — Status = Completed, instance.Output = result.Output
result.Outcome == Error and GlobalOnFailureNodeId is setRoute to GlobalOnFailureNodeId, continue loop
No edge matched (any other case)Status = Faulted, error code NO_MATCHING_EDGE

Step 5 — Checkpoint. If result.ForceCheckpoint == true, state is saved mid-loop before the next node. This bounds the crash re-execution window. checkpoint nodes always set this.

Persistence Model

The engine saves state at async boundaries only, not after every node. A synchronous chain runs entirely in memory with one save at the end.

1SAVE  Instance created — bare state before any execution
2filter → compute → store → transform → decision  — all in memory
3SAVE  checkpoint — mid-loop save; CurrentNodeId advanced past checkpoint
4integration → query  — in memory
5SAVE  wait / human / timer — status = Suspended; claim released
… workflow dormant, zero resources consumed …
6Resume: wait/message → engine.ResumeAsync · human → taskStore.SubmitResponseAsync · timer → sweep service
7More nodes execute in memory
8SAVE  output — status = Completed; claim released
All node executors must be idempotent. Crash recovery re-runs from the last save point. Read-only nodes (filter, query, compute, transform, store) are naturally idempotent. Write operations (integration POST/PUT/DELETE, message publish) require idempotencyKey.

Suspend & Resume

When an instance reaches a suspending node (wait, human, timer, or message RequestReply), state is saved, the claim is released, and no resources are consumed. Each node type has its own resume path:

Node typeHow it resumes
wait, message (RequestReply)External caller invokes engine.ResumeAsync or engine.ResumeBackgroundAsync with the matching eventName and correlationKey. The harness does not need to know the instanceId — lookup is by event name + correlation key.
humanA user submits a response via IHumanTaskStore.SubmitResponseAsync / SubmitResponseBackgroundAsync. The task store validates the response, checks quorum, and calls engine.ResumeByInstanceIdAsync internally — you never call ResumeAsync directly for a human node.
timerAutomatic — ExecutionSweepService detects the elapsed delay and resumes the instance. No caller code required.

Idempotency Key

IdempotencyKey is an optional string forwarded to external systems so they can deduplicate repeated calls. FlowEngine itself does not use it for deduplication — it is a hint carried through to clients and brokers.

Why it matters

When ExecutionSweepService recovers a crashed instance it re-executes the node from CurrentNodeId. If the external system was already called before the crash, the re-execution sends a second call. Without an idempotency key the external system has no way to detect the duplicate.

Validator warning. WorkflowDefinitionValidator.GetWarnings emits a warning for every message, integration, and agent node that does not set IdempotencyKey. Treat this warning as an error for any node that performs a write operation.

Where to set it

integrationIntegrationNodeConfig.IdempotencyKeyClientRequest.IdempotencyKey → request-response client

When an IOutboxStore is enabled the key is also persisted on OutboxEntry.IdempotencyKey and forwarded by the drain service at dispatch time.

Value format

The value is either a JSONPath expression resolved against the execution context at runtime, or a plain literal string.

json// JSONPath — resolved from the execution context

// Literal — forwarded as-is

Resolution logic: if the template starts with $., ctx.Resolve(template) is called and the resulting JsonContextValue string is extracted. If resolution throws (e.g. the value is a plain literal, not a path), the template string is used verbatim.

Responsibility boundary

FlowEngine resolves and forwards the key. Honoring it — deduplicating the operation — is the responsibility of the external system (broker, HTTP endpoint, agent provider). Choose a value that is stable across retries: a business entity ID from the workflow context is the most reliable choice.

Client concurrency limits

All clients are registered as singletons — the same instance is called by every parallel loop branch and parallel node. Clients backed by thread-safe resources (HttpClient, IDbContextFactory<T>, pooled SDK clients) handle this naturally. Clients backed by non-thread-safe resources need additional protection.

Override ConcurrencyLimit on IFlowClient to declare a process-local cap. ClientRegistry auto-wraps the client in a SemaphoreSlim — callers acquire a slot before calling through and release it on completion or exception.

csharppublic class MyApiClient : IRequestResponseClient
{
    public string ClientRef        => "rate-limited-api";
    public int?   ConcurrencyLimit => 5;   // at most 5 concurrent calls in this process
    // ...
}
Process-local only. The semaphore is per-process. In a multi-node deployment each host enforces its own limit independently — total cluster concurrency is limit × node-count. For strict cluster-wide throttling a future IDistributedConcurrencyLimiter extension point (Redis counter or similar) will replace or supplement this mechanism. See Connectors — Client Concurrency Limits for full guidance.

Any event calls IFlowEngine.StartAsync or StartBackgroundAsync. The engine resolves the latest Active definition, creates an ExecutionInstance, and runs the node graph.

Phase 4 — What the engine does

On StartAsync the engine: resolves the latest Active definition via IWorkflowRegistry.GetAsync → validates params and clients → creates a new ExecutionInstance → acquires a distributed lock → executes nodes in sequence → persists state at every async boundary → releases the lock → returns the instance (completed or suspended).

See Persistence Model and Crash Recovery for internals.

Common Patterns

Fetch data and branch on the result (StoreAs + When)

storeAs is applied before edge evaluation, so a single node can store its own output and route on it in the same step:

json{
  "id": "n-get-score", "type": "fetch",
  "config": { "url": "https://api.credit.com/score/{{$.entity.customerId}}", "method": "GET" },
  "storeAs": "creditScore",
  "edges": [
    { "label": "approved", "on": ["Match"],           "when": "(int)((System.Text.Json.JsonElement)Context[\"creditScore\"]).GetProperty(\"score\").GetInt32() >= 700", "nextNodeId": "n-approve" },
    { "label": "review",   "on": ["Match"],           "when": "(int)((System.Text.Json.JsonElement)Context[\"creditScore\"]).GetProperty(\"score\").GetInt32() >= 500", "nextNodeId": "n-review"  },
    { "label": "denied",   "on": ["Match","NoMatch"],                                                                                                                   "nextNodeId": "n-deny"    },
    { "label": "error",    "on": ["Error"],                                                                                                                            "nextNodeId": "n-error"   }
  ]
}

The same approach applies to integration, compute, query, and transform — any node with storeAs. When you prefer to keep HTTP outcome edges (2xx / 4xx / error) separate from value-branching edges, use a subsequent decision node instead:

json[
  { "id": "n-get-score", "type": "fetch",
    "config": { "url": "https://api.credit.com/score/{{$.entity.customerId}}", "method": "GET" },
    "storeAs": "creditScore",
    "edges": [
      { "on": ["Match"],            "nextNodeId": "n-check-score" },
      { "on": ["NoMatch", "Error"], "nextNodeId": "n-error"       }
    ]
  },
  { "id": "n-check-score", "type": "decision",
    "config": { "valuePath": "$.context.creditScore" },
    "edges": [
      { "on": ["Match"], "when": "(int)((System.Text.Json.JsonElement)Context[\"creditScore\"]).GetProperty(\"score\").GetInt32() >= 700", "nextNodeId": "n-approve" },
      { "on": ["Match"], "when": "(int)((System.Text.Json.JsonElement)Context[\"creditScore\"]).GetProperty(\"score\").GetInt32() >= 500", "nextNodeId": "n-review"  },
      { "on": ["Match"],                                                                                                                   "nextNodeId": "n-deny"    },
      { "on": ["Unknown"],                                                                                                                 "nextNodeId": "n-error"   }

]

Saga Compensation

FlowEngine supports the saga pattern for distributed transactions. When a mid-saga node faults and enableCompensation: true is set on the workflow, the engine automatically executes compensating (undo) nodes for all previously completed steps in reverse order before routing to the failure handler.

How rollback works

  1. The engine walks ExecutionInstance.History in reverse order.
  2. Entries that already faulted or are already compensation records (compensatingFor != null) are skipped.
  3. Each completed forward step with a compensationNodeId is executed via the normal ExecuteWithRetryAsync path.
  4. A history record is appended with compensatingFor: "<originalNodeId>" — prevents double-compensation on engine retry.
  5. After all compensation runs, the engine routes to GlobalOnFailureNodeId (if defined) or transitions to Faulted.

Definition

json{
  "id": "order-saga", "version": "1.0.0",
  "enableCompensation": true,
  "globalOnFailureNodeId": "saga-failed",
  "nodes": {
    "reserve-inventory": { "type": "integration", "compensationNodeId": "release-inventory", ... },
    "charge-payment":    { "type": "integration", "compensationNodeId": "refund-payment",    ... },
    "ship-order":        { "type": "integration" },
    "release-inventory": { "type": "integration", ... },
    "refund-payment":    { "type": "integration", ... },
    "saga-failed":       { "type": "output",      ... }
  }
}

Rollback example

When ship-order returns HTTP 500:

textreserve-inventory → charge-payment → ship-order  ✗ (500)
                                          ↓ compensation (reverse)
                         refund-payment ← charge-payment
               release-inventory ← reserve-inventory
                                          ↓
                          saga-failed (GlobalOnFailureNodeId)

Circuit Breaker

The circuit breaker prevents repeated hammering of a failing service. When a node's failure count within a rolling window reaches the threshold, the circuit opens. While open, the executor is skipped entirely and each affected instance either routes to a CircuitOpen edge (graceful degradation) or auto-suspends at the failing node until the cool-down period expires, after which the sweep service resumes it for a retry.

Policy inheritance

Mirrors RetryPolicy: set defaultCircuitBreakerPolicy on the workflow as a workflow-wide default; override with circuitBreakerPolicy on individual nodes. Nodes with neither policy have no circuit breaker.

json{
  "id": "order-processing", "version": "1.0.0",
  "defaultCircuitBreakerPolicy": {
    "key": "external-apis", "failureThreshold": 5,
    "samplingWindow": "00:01:00", "openDuration": "00:00:30"
  },
  "nodes": {
    "n-call-payment": {
      "type": "fetch",
      "circuitBreakerPolicy": { "key": "payment-svc", "failureThreshold": 3, "openDuration": "00:01:00" },
      "edges": [
        { "on": ["Match"],       "nextNodeId": "n-process-payment" },
        { "on": ["CircuitOpen"], "nextNodeId": "n-use-cached-result" },
        { "on": ["Error"],       "nextNodeId": "n-payment-failed" }
      ]
    }
  }
}

CircuitBreakerPolicy properties

PropertyDefaultDescription
keynode typeGroups nodes that share a backing service under one circuit. Omit to scope the breaker per node type.
failureThreshold5Failures within samplingWindow required to trip the circuit.
samplingWindow00:01:00Rolling window over which failures are counted.
openDuration00:00:30How long the circuit stays open before the next attempt is allowed.

Engine behaviour when circuit is open

  1. ExecuteWithRetryAsync checks the circuit before invoking the executor. If open, it immediately returns Outcome = CircuitOpen (no execution, no retry).
  2. The engine evaluates edges for CircuitOpen as normal.
  3. If a CircuitOpen edge exists → workflow advances to the alternate node.
  4. If no CircuitOpen edge → the instance suspends at the current node with PendingWait.TimeoutAt = now + openDuration. The circuit-open event is recorded in ExecutionInstance.History (BranchTaken = "circuit-open"). After cool-down, the sweep service resumes the instance; the node is retried and the circuit is checked again.

Failure and success recording

After all retries are exhausted (not per attempt): an Error outcome calls RecordFailureAsync; any non-error outcome calls RecordSuccessAsync which resets the circuit to closed.

Circuit state scope and crash recovery

The default InMemoryCircuitBreakerStore is a process-local singleton — one store is shared across all workflow instances on a replica, so one instance discovering a failure protects the others on that replica. Circuit state is not preserved across process restarts, but workflow instance state is always durable. After a restart, suspended instances are found by the sweep service and resumed; if the service is still down they will re-trip the circuit on the new replica.

For fleet-wide circuit state, replace ICircuitBreakerStore in DI with a distributed implementation:

csharpservices.AddSingleton<ICircuitBreakerStore, RedisCircuitBreakerStore>();
