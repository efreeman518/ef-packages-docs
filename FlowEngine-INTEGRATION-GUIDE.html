FlowEngine Integration Guide

Use this guide when you want to add FlowEngine, the Admin API, and the Dashboard to an existing .NET solution.

What to install

Add these packages to the solution projects that actually need them:

Need Package
Core workflow engine EF.FlowEngine
Admin HTTP endpoints EF.FlowEngine.AdminApi
Blazor dashboard UI EF.FlowEngine.Dashboard

Add provider packages that match your infrastructure:

Concern Choose one
State store EF.FlowEngine.StateStore.Sql, Redis, Cosmos, AzureTable, or File
Lock provider EF.FlowEngine.Locks.Sql, Redis, Cosmos, AzureBlob, AzureTable, or InMemory
Workflow registry EF.FlowEngine.WorkflowRegistry.Sql, Redis, or Cosmos

Optional circuit breaker store EF.FlowEngine.CircuitBreaker.Sql or Redis

Choosing your database layout

The FlowEngine state-store tables can live in the same database as your application data or in a dedicated database. This is the most important architectural decision in the integration, because it determines whether outbox writes remain atomic with state writes.

Variant Atomic outbox Resource isolation Cross-DB joins Ops cost Best for
A. Same DB, application tables + FlowEngine tables together ✅ kept (single SaveChangesAsync) shared instance / pool; per-context separation via AddPooledDbContextFactory n/a — single DB lowest — one resource, one backup window, one connection string Monoliths, demos, small teams; anywhere message / agent / integration nodes rely on FlowEngine's outbox
B. Separate DB on the same server/instance ❌ lost — different DbContext, different connection full buffer pool / IO isolation; shared compute possible via 3-part names medium — second DB, second migration history Connection-pool / buffer-cache isolation without paying for a second SQL instance
C. Separate DB on a separate server ❌ lost full IO + compute isolation not practical highest — second instance, separate failure domain, separate PITR coordination Platform-team-owned FlowEngine serving many apps; SaaS pattern; aggressive blast-radius / compliance

Hinge: the atomic-outbox guarantee. SqlOutboxStore writes outbox rows in the same SaveChangesAsync as the execution instance — but only if both entity sets are mapped on the same DbContext. The moment FlowEngine tables live in a different DbContext (Variants B or C), this guarantee disappears. Use B/C only if your app already has an at-least-once publisher (Service Bus + transactional outbox, MassTransit) and you route FlowEngine message sends through it via DelegatingMessageClient.

Migration coordination (B/C): two migration histories, two deploy steps. Recommend the table name __EFMigrationsHistory_FlowEngine to make grep / audit trivial.

PITR drift (B/C): workflow Entity JSON snapshots reference business-data IDs by value. Point-in-time-restoring one database without the other surfaces dangling references in suspended-instance context. Co-located backup windows mitigate but do not eliminate.

Once data exists, moving between variants requires data migration. Decide upfront.

Composing FlowEngine into your DbContext

FlowEngine SQL providers consume any DbContext that exposes the right DbSet properties and applies the right entity configurations. There is no abstract base class to inherit from.

using EF.FlowEngine.Sql;
using EF.FlowEngine.Outbox.Sql;
using EF.FlowEngine.CircuitBreaker.Sql;

public class AppDbContext(DbContextOptions<AppDbContext> options)
    : DbContext(options),
      IFlowEngineStateDbContext,
      IFlowEngineOutboxDbContext,
      IFlowEngineCircuitBreakerDbContext
{
    // Your own DbSets ...
    public DbSet<Order>    Orders    => Set<Order>();
    public DbSet<Customer> Customers => Set<Customer>();

    // FlowEngine state
    public DbSet<FlowEngineWorkflowRow>    Workflows    => Set<FlowEngineWorkflowRow>();
    public DbSet<FlowEngineExecutionRow>   Executions   => Set<FlowEngineExecutionRow>();
    public DbSet<FlowEngineHumanTaskRow>   HumanTasks   => Set<FlowEngineHumanTaskRow>();
    public DbSet<FlowEngineChildSignalRow> ChildSignals => Set<FlowEngineChildSignalRow>();

    // Outbox (optional)
    public DbSet<FlowEngineOutboxRow> Outbox => Set<FlowEngineOutboxRow>();
    public void StageOutboxEntry(EF.FlowEngine.Model.OutboxEntry entry)
        => OutboxDbContextHelpers.StageOutboxEntry(this, entry);

    // Circuit-breaker store (optional)
    public DbSet<FlowEngineCircuitBreakerRow> CircuitBreakers => Set<FlowEngineCircuitBreakerRow>();

    protected override void OnModelCreating(ModelBuilder mb)
    {
        base.OnModelCreating(mb);
        // Your own configuration ...
        mb.ApplyFlowEngineState();
        mb.ApplyFlowEngineOutbox();
        mb.ApplyFlowEngineCircuitBreaker();
    }
}

Because the FlowEngine concerns are mixin extensions on ModelBuilder, your app's DbContext can still inherit from your own audit / multi-tenant base class — no diamond-inheritance forced choice.

Configure FlowEngine

Select the backing stores first, then register your workflow clients.

var flowEngineBuilder = builder.Services.AddFlowEngine();

flowEngineBuilder
    .UseStateStoreSql<AppDbContext>()
    .UseWorkflowRegistrySql<AppDbContext>()
    .UseLockProviderSql<AppDbContext>()
    .UseHumanTaskStoreSql<AppDbContext>()
    .UseOutboxSql<AppDbContext>()             // requires IFlowEngineOutboxDbContext
    .UseCircuitBreakerSql<AppDbContext>();    // requires IFlowEngineCircuitBreakerDbContext

For Redis deployments, swap to the Redis provider extensions. For local development, you can use the file or in-memory defaults, but those are not production choices.

All 19 built-in node executors are registered automatically by AddFlowEngine(). If you're composing FlowEngine into a custom service collection that does not call AddFlowEngine(), use:

services.AddBuiltInNodeExecutors();

Add SQL migration support

If you use SQL-backed providers, register the DbContext factory and the migration hosted service before the app starts serving traffic.

builder.Services.AddDbContextFactory<AppDbContext>(opts =>
    opts.UseSqlServer(builder.Configuration.GetConnectionString("FlowEngineDb")));

builder.Services.AddHostedService<MigrationStartupTask>();

If you also have a demo or sample database, register that separately. Keep production workflow storage and demo data migrations distinct.

Register required clients

FlowEngine does not own your business integrations. Register the clients your workflows reference by name.

flowEngineBuilder.AddHttpClient("payment-api");

// Service Bus — connection string variant
flowEngineBuilder.AddServiceBusClient("order-events", connectionString: cs, queueOrTopic: "orders");

// Service Bus — factory variant (typical for Microsoft.Extensions.Azure callers)
flowEngineBuilder.AddServiceBusClient(
    "order-events",
    sp => sp.GetRequiredService<IAzureClientFactory<ServiceBusClient>>().CreateClient("my-bus"),
    queueOrTopic: "orders");

// Azure OpenAI — factory variant that bridges AzureOpenAIClient to IChatClient
flowEngineBuilder.AddAzureOpenAIAgentClient(
    "gpt4o",
    sp => sp.GetRequiredService<AzureOpenAIClient>(),
    deploymentName: "gpt-4o-prod",
    modelName: "gpt-4o");

If your app already has an IIntegrationEventPublisher (or MassTransit, or a custom bus) and you want FlowEngine message nodes to delegate to it (preserving tenant headers, correlation IDs, OTel baggage), wrap it with DelegatingMessageClient:

flowEngineBuilder.Services.AddSingleton<IFlowClient>(sp =>
{
    var publisher = sp.GetRequiredService<IIntegrationEventPublisher>();
    return new DelegatingMessageClient(
        clientRef: "domain-events",
        sendAsync: async (req, ct) =>
        {
            await publisher.PublishAsync(req.Subject, req.Body, req.Properties, ct);
            return new MessageResult { Sent = true, Outcome = DecisionOutcome.Match };
        });
});

Seed workflow definitions from JSON files

Ship workflow JSON files in a Workflows/ directory and have FlowEngine seed them on startup:

flowEngineBuilder.AddWorkflowJsonSeeding(opts =>
{
    opts.Directory                = "Workflows";
    opts.SearchPattern            = "*.json";
    opts.ActivateOnSeed           = true;   // saves as Draft, then transitions → Active
    opts.OverwriteExistingVersion = false;  // skip on duplicates
});

The seeder reads each file with WorkflowDefinitionJsonOptions.Default (camelCase, string-named enums with integer fallback). If you build your own seeder, use that same options instance — never raw JsonSerializerOptions():

var def = JsonSerializer.Deserialize<WorkflowDefinition>(
    json, WorkflowDefinitionJsonOptions.Default)!;

Equivalently, WorkflowDefinitionBuilder.FromJson(json).Build() uses the same options internally and fails fast with a clear message if the JSON shape didn't match.

Add the Admin API

The dashboard talks to the Admin API, so the API must be exposed somewhere in your solution.

builder.Services.AddFlowEngineAdminPolicies();
app.MapFlowEngineAdmin();                              // default prefix /api/flowengine
app.MapFlowEngineAdmin(prefix: "/admin/flowengine");   // or override

The Admin API requires the engine services to already be registered. It exposes instance management, workflow registry operations, circuit-breaker operations, compatibility analysis, and human-task endpoints.

Multi-tenancy: end-to-end

StartRequest.TenantId is propagated to ExecutionInstance.TenantId. The engine does not enforce tenant isolation — each store implementation filters on it. Enable Admin-API tenant scoping by calling AddFlowEngineAdminTenantPolicy alongside AddFlowEngineAdminPolicies:

builder.Services
    .AddFlowEngineAdminPolicies()
    .AddFlowEngineAdminTenantPolicy(opts =>
    {
        opts.TenantClaimType = "tid";      // OIDC claim
        opts.FallbackHeader  = "X-Tenant"; // optional, off by default
        opts.RequireTenant   = true;       // 403 when neither resolves
    });

When enabled, an endpoint filter resolves the tenant for every Admin API request and populates a request-scoped FlowEngineTenantContext. Endpoints honor it in two ways:

  • GET /instances injects tenant.TenantId into ExecutionQuery.TenantId.
  • GET /instances/{id} returns 404 if the instance's TenantId doesn't match the caller's tenant.

For asynchronous trigger handlers (Service Bus consumers, hosted services) that call IFlowEngine.StartAsync outside an HTTP request, capture the tenant on the inbound message and pass it explicitly:

public async Task HandleAsync(OrderCreatedEvent evt, CancellationToken ct)
{
    await engine.StartAsync(new StartRequest
    {
        WorkflowId = "order-flow",
        TenantId   = evt.TenantId,
        Entity     = JsonSerializer.SerializeToElement(evt)
    }, ct);
}

Dashboard: the Dashboard does not currently filter by tenant — host one Dashboard per tenant, or wrap the Admin API call inside a DelegatingHandler that forces the caller's tenant claim onto the upstream request.

Add the Dashboard UI

If you want the UI inside the same ASP.NET Core app, register the dashboard.

builder.Services.AddFlowEngineDashboard(
    adminApiBaseUrl: builder.Configuration["FlowEngine:AdminApiBaseUrl"]!);

AddFlowEngineDashboard registers a startup-time validator (DashboardStartupValidator) that throws a clear exception if MudBlazor services (IDialogService, ISnackbar) are missing — surfacing host-misconfiguration before the user hits a Dashboard route.

.NET 8+ Razor Components host

The Dashboard's pages use @page routing. In a MapRazorComponents<App>() host, the Dashboard assembly must be added to Router.AdditionalAssemblies for those routes to be discovered. Without this, navigation to /workflows/registry, /workflows/new, etc. returns 404 with no startup error.

In App.razor:

<Router AppAssembly="@typeof(App).Assembly"
        AdditionalAssemblies="new[] { typeof(EF.FlowEngine.Dashboard.DashboardServiceExtensions).Assembly }">
    <Found Context="routeData">
        <RouteView RouteData="@routeData" DefaultLayout="@typeof(MainLayout)" />
    </Found>
</Router>

In _Imports.razor:

@using EF.FlowEngine.Dashboard
@using EF.FlowEngine.Dashboard.Pages

Required MudBlazor providers in the host's root component (typically MainLayout.razor):

<MudThemeProvider />
<MudPopoverProvider />
<MudDialogProvider />
<MudSnackbarProvider />

The package itself does NOT render these — the host's layout owns them. Missing providers fail silently when the user navigates to a page that opens a dialog or snackbar.

MudBlazor version window: the Dashboard targets MudBlazor 9.x. Verify your host pins a compatible major version.

Forwarding user authentication to the Admin API

When the Dashboard sits in the same app as the Admin API (or talks to a remote API behind the same identity provider), forward the inbound user's bearer token to the Admin API call so per-tenant / per-scope authorization is enforced upstream:

public sealed class BearerForwardingHandler(IHttpContextAccessor accessor) : DelegatingHandler
{
    protected override Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
    {
        var token = accessor.HttpContext?.Request.Headers.Authorization.ToString();
        if (!string.IsNullOrEmpty(token))
            request.Headers.TryAddWithoutValidation("Authorization", token);
        return base.SendAsync(request, ct);
    }
}

builder.Services.AddHttpContextAccessor();
builder.Services.AddTransient<BearerForwardingHandler>();

builder.Services
    .AddFlowEngineDashboard(adminApiBaseUrl)
    .AddHttpMessageHandler<BearerForwardingHandler>();

Dashboard package dependencies

EF.FlowEngine.Dashboard transitively pulls EF.FlowEngine.Clients.Sql — the in-Dashboard "Add SQL Query Client" feature constructs AdHocSqlQueryClient. If you do not use that feature, the package payload still includes it; treat it as part of the Dashboard's surface area.

Suggested composition order

  1. Add the FlowEngine package.
  2. Pick the state store, lock provider, workflow registry, and human-task store.
  3. Compose them into your DbContext (IFlowEngineStateDbContext + ApplyFlowEngineState(), plus optional outbox / circuit-breaker mixins).
  4. Add SQL migration startup tasks if the selected providers need them.
  5. Register all workflow clients that the solution uses.
  6. Add AddWorkflowJsonSeeding if you ship JSON workflow files.
  7. Add the Admin API and policies, plus the tenant policy if multi-tenant.
  8. Add the dashboard package and Razor Components hosting (Router.AdditionalAssemblies + MudBlazor providers).

Testing Workflows

Unit Tests

Unit tests validate individual node execution logic without database setup. Use EF.FlowEngine.Testing to build test contexts:

var testContext = TestExecutionContext.Create()
    .WithEntity(new { OrderId = "ORD-001", Amount = 5000 })
    .WithContext("approvalThreshold", 3000)
    .Build();

var executor = new FilterNodeExecutor(/* ... */);
var result = await executor.ExecuteAsync(nodeConfig, testContext);
Assert.AreEqual(DecisionOutcome.Match, result.Outcome);

For transient failures or store resilience, wrap the state store with FaultableExecutionStateStore to inject single-fault scenarios:

var faultable = new FaultableExecutionStateStore(realStateStore);
faultable.FaultOnNextSave = true;  // Next save throws; auto-clears

Integration Tests

Integration tests run complete workflows against real infrastructure (SQL, Redis, Cosmos). Use TestContainers to manage ephemeral databases per test assembly:

[TestClass]
[ClassInitialize]
public static async Task AssemblyInit(TestContext _)
{
    var sqlContainer = new MsSqlBuilder("mcr.microsoft.com/mssql/server:2025-latest").Build();
    await sqlContainer.StartAsync();
    _connectionString = sqlContainer.GetConnectionString();
}

Build a fresh DI container per test with SQL providers:

[TestInitialize]
public void TestInit()
{
    var services = new ServiceCollection();
    services.AddDbContextFactory<MyDbContext>(o => o.UseSqlServer(_connectionString));
    services.AddFlowEngine()
        .UseStateStoreSql<MyDbContext>()
        .UseLockProviderSql<MyDbContext>()
        .UseWorkflowRegistrySql<MyDbContext>()
        .AddHttpClient("api");

    _provider = services.BuildServiceProvider();
    _engine = _provider.GetRequiredService<IFlowEngine>();
}

All 19 built-in node executors are registered by AddFlowEngine() — you do not need to enumerate them.

Testing human workflows

var instance = await _engine.StartAsync(new StartRequest { WorkflowId = "approval-flow", Entity = order });
Assert.AreEqual(ExecStatus.Suspended, instance.Status);

await _humanTasks.RespondAsync(humanTaskId, new HumanTaskResponse
{
    FormValues  = new { decision = "approved" },
    RespondedBy = "manager@company.com"
});

instance = await _engine.ResumeAsync(instance.InstanceId, eventName: "human.response", correlationKey: humanTaskId);
Assert.AreEqual(ExecStatus.Completed, instance.Status);

Reference implementation: the source repository includes 9 realistic end-to-end use cases covering healthcare, loans, e-commerce, AI, compliance, scheduling, and orchestration patterns.

In-Memory Testing for Local Development

For fast local unit/integration tests without containers:

services.AddFlowEngine().UseAllInMemoryProviders();

Important: in-memory providers are not distributed — use only for single-instance local development and unit tests. For multi-instance or production, use SQL / Redis / Cosmos providers.

Known issues

Roslyn version conflict with Microsoft.EntityFrameworkCore.Design

EF.FlowEngine depends on Microsoft.CodeAnalysis.CSharp.Scripting 5.3.0 (for the workflow expression evaluator used by compute, wait, and edge-guard nodes). EF Core Design 10.x pulls in older Microsoft.CodeAnalysis.Workspaces 5.0.0. Pinning only Microsoft.CodeAnalysis.Common lets restore succeed but dotnet ef migrations add then crashes with TypeLoadException: Method 'ReduceExtensionMember' ... not have an implementation. Pin all four Roslyn packages to 5.3.0:

<PackageVersion Include="Microsoft.CodeAnalysis.Common"            Version="5.3.0" />
<PackageVersion Include="Microsoft.CodeAnalysis.CSharp"            Version="5.3.0" />
<PackageVersion Include="Microsoft.CodeAnalysis.Workspaces.Common" Version="5.3.0" />
<PackageVersion Include="Microsoft.CodeAnalysis.CSharp.Workspaces" Version="5.3.0" />

Plus an explicit <PackageReference> to all four in the project that runs dotnet ef. The error is misleading because dotnet restore succeeds with only two pins.
