Quick start — minimal executor

csharpusing System.Text.Json;
using EF.FlowEngine.Abstractions;
using EF.FlowEngine.Definition;
using EF.FlowEngine.Model;

public sealed class MyCustomNodeExecutor : INodeExecutor
{
    // Must match the "type" field in workflow JSON
    public string NodeType => "my-custom";

    public async Task<NodeResult> ExecuteAsync(
        NodeDefinition    node,
        ExecutionInstance instance,
        IExecutionContext  ctx,
        CancellationToken ct)
    {
        // 1. Deserialize config. Built-in executors read config keys case-insensitively
        //    (JsonSerializerDefaults.Web), so camelCase workflow JSON binds; pass
        //    new JsonSerializerOptions(JsonSerializerDefaults.Web) to do the same here.
        var config = node.Config.Deserialize<MyCustomNodeConfig>()
            ?? throw new InvalidOperationException("Missing config");

        // 2. Read from context
        var entityId = ctx.ResolveAs<string>("$.entity.Id");
        var someValue = ctx.ResolveAs<int>("$.context.someValue");

        // 3. Do work
        var result = entityId + "-" + someValue;

        // 4. Return outcome (store result via storeAs if configured)
        return new NodeResult
        {
            Outcome = DecisionOutcome.Match,
            Output  = new JsonContextValue
                { Value = JsonSerializer.SerializeToElement(result) }
        };
    }
}

// Config class — one per node type
public sealed class MyCustomNodeConfig
{
    public string  SomeField   { get; init; }
    public string? OptionalRef { get; init; }
    public int     ThresholdMs { get; init; } = 5000;
}

Register at startup:

csharpservices.AddFlowEngine()
    .AddNodeExecutor<MyCustomNodeExecutor>();

The five rules every executor must follow

Rule 1 — Be idempotent

The engine re-executes nodes on crash recovery. If the server crashes after
your node runs but before the next SaveAsync, your node re-runs with the
same inputs. Your executor must produce the same effect regardless of how
many times it is called.

Node category Idempotency approach
Pure computation (filter, compute, transform, store) Naturally idempotent — no action needed
Read operations (GET, query, agent with same prompt) Naturally idempotent
Write operations via integration (POST/PUT/PATCH/DELETE) Set idempotencyKeyHeader; the engine sends one generated key per node execution (same across retries and lease recovery) and the server deduplicates on that header. IdempotencyKey alone is client metadata only
Write operations via fetch with clientRef FetchNodeConfig has no idempotency key: use an integration node with idempotencyKeyHeader for writes, or deduplicate on the server
Write operations via fetch without clientRef (raw HttpClient) Implement deduplication in the executor directly — no client registry to help
Message publish Use message deduplication on the broker, or IdempotencyKey
Record creation (human task, child workflow spawn) Check if record already exists by (InstanceId, NodeId) before creating
timer Naturally idempotent — re-execution rebuilds the WaitDescriptor from the same Delay expression. TimeoutAt may shift slightly after a crash but the delay restarts, which is acceptable.
checkpoint The only node that triggers a mid-loop save; always returns Match

Pattern for write-idempotent custom nodes:

csharp// Bad — creates a duplicate payment on re-execution
await _paymentClient.ChargeAsync(amount, orderId);

// Good — client deduplicates on idempotency key
var idempotencyKey = $"{instance.InstanceId}-{node.Id}";
await _paymentClient.ChargeAsync(amount, orderId, idempotencyKey);

Rule 2 — Use NodeResult correctly

NodeResult carries everything the engine needs to continue:

csharp// Successful, synchronous result
return new NodeResult { Outcome = DecisionOutcome.Match, Output = myValue };

// Failure — engine evaluates retry policy, then emits Error outcome
return new NodeResult
{
    Outcome = DecisionOutcome.Error,
    Error   = new ExecutionError
    {
        Code       = "MY_NODE_FAILED",
        Message    = "The thing failed because: " + ex.Message,
        NodeId     = node.Id,
        Detail     = ex.ToString(),
        OccurredAt = DateTimeOffset.UtcNow
    }
};

// Suspend — node is waiting for an external signal
// Engine saves state, releases lock, and resumes when signal arrives
return new NodeResult
{
    Outcome     = DecisionOutcome.Match,   // always Match for suspension
    PendingWait = new WaitDescriptor
    {
        EventName      = "my-event.arrived",
        CorrelationKey = ctx.ResolveAs<string>("$.entity.Id")!,
        TimeoutAt      = DateTimeOffset.UtcNow.AddDays(7),
        MinSignalCount = 1
    }
};
// EventName and CorrelationKey are limited to 256 UTF-16 code units each; a custom executor's
// outbox entries are limited to InstanceId/NodeId 64, ClientRef 127 and IdempotencyKey 512. A longer value fails the node with Error code
// RUNTIME_KEY_TOO_LONG instead of failing the save.

// Force mid-loop checkpoint save (only for checkpoint node type)
return new NodeResult
{
    Outcome         = DecisionOutcome.Match,
    ForceCheckpoint = true
};

// HTTP executors — log HTTP status in execution history; used by RetryPolicy
return new NodeResult
{
    Outcome        = DecisionOutcome.NoMatch,
    HttpStatusCode = 404
};

Rule 3 — Use IExecutionContext, not ExecutionInstance directly

IExecutionContext is the safe API for nodes. It handles namespace routing,
null safety, and synthesizes the read-only $.engine.* namespace at resolve time.

csharp// Good — use ctx
var orderId    = ctx.ResolveAs<string>("$.entity.OrderId");
var riskScore  = ctx.ResolveAs<int>("$.context.riskScore");
var visitCount = ctx.GetVisitCount("n-review");
ctx.Store("myResult", new JsonContextValue { Value = ... });

// Bad — bypass ctx and touch instance directly
var orderId = instance.Context.Entity; // bypasses type safety + null handling

// Pointless: Store does not throw, but it writes $.context["engine.visits.myNode"];
// $.engine.* paths are computed by the engine and never read stored keys
ctx.Store("engine.visits.myNode", ...);

Rule 4 - Map expected failures to NodeResult

An exception thrown by your executor does not fault the instance: the engine converts it to an
Error result with code NODE_EXECUTOR_EXCEPTION (message and detail from the exception),
which goes through the retry policy and then Error edge and failure routing like any other error.
A node that exceeds its executionTimeout becomes Error code NODE_EXECUTION_TIMEOUT.
Only cancellation of the engine's own token propagates. Catch the failures you understand anyway, so
each gets a specific error code that edges and operators can tell apart.

csharppublic async Task<NodeResult> ExecuteAsync(...)
{
    try
    {
        // ... your logic
        return new NodeResult { Outcome = DecisionOutcome.Match, ... };
    }
    catch (OperationCanceledException)
    {
        throw; // let cancellation propagate — engine handles it
    }
    catch (MyTransientException ex)
    {
        // Return Error — retry policy fires, then edge evaluation
        return new NodeResult
        {
            Outcome = DecisionOutcome.Error,
            Error   = new ExecutionError
            {
                Code = "MY_TRANSIENT_ERROR", Message = ex.Message,
                NodeId = node.Id, OccurredAt = DateTimeOffset.UtcNow
            }
        };
    }
    catch (Exception ex)
    {
        ctx.Logger.LogError(ex, "Unexpected error in {NodeType} {NodeId}",
            NodeType, node.Id);
        return new NodeResult
        {
            Outcome = DecisionOutcome.Error,
            Error   = new ExecutionError
            {
                Code = "UNEXPECTED_ERROR", Message = ex.Message,
                NodeId = node.Id, Detail = ex.ToString(),
                OccurredAt = DateTimeOffset.UtcNow
            }
        };
    }
}

Suspension pattern — async wait nodes

Nodes that need to suspend (wait for external signal) follow this pattern.
The timer node is a special case of this — it suspends with a synthetic
event name that only the sweep service triggers (no external harness needed).

csharp// wait node — suspends until external ResumeAsync call
return new NodeResult
{
    Outcome     = DecisionOutcome.Match,
    PendingWait = new WaitDescriptor
    {
        EventName        = config.EventName,       // external signal name
        CorrelationKey   = resolvedCorrelationKey,
        TimeoutAt        = resolvedTimeout,        // null = wait forever
        OnTimeoutNodeId  = config.OnTimeoutNodeId, // null = instance → TimedOut status
        MinSignalCount   = config.MinSignalCount   // default 1; increase for N-of-M approval
    }
};

// timer node — suspends until sweep detects TimeoutAt elapsed
// Synthetic event name ensures only the sweep triggers this
return new NodeResult
{
    Outcome     = DecisionOutcome.Match,
    PendingWait = new WaitDescriptor
    {
        EventName      = $"timer.{instance.InstanceId}.{node.Id}",
        CorrelationKey = instance.InstanceId,
        TimeoutAt      = await _calendar.ResolveAsync(config.Delay, DateTimeOffset.UtcNow, ct),
        MinSignalCount = 1
    }
};

WaitDescriptor fields:

FieldTypeNotes
EventNamestringLogical event name matched against the eventName parameter of ResumeAsync
CorrelationKeystringScopes the wait within the event type; typically the entity ID or an external reference
TimeoutAtDateTimeOffset?Optional deadline evaluated by the sweep service; null = wait forever
OnTimeoutNodeIdstring?Node to jump to when timeout fires; null = transition instance to TimedOut status
MinSignalCountintMinimum signal count before resuming; enables N-of-M approvals (default: 1)
ReceivedSignalsList<JsonElement>Accumulated signal payloads written by the engine on each ResumeAsync call; readable by the node after resume

Key distinction — what happens on sweep resume:
- timer node + TimeoutAt elapsed -> the node's Match edges are followed
- any other node (wait, human, your custom node) + TimeoutAt elapsed -> no outcome edge is evaluated. The instance jumps to OnTimeoutNodeId; if that is null, to the definition's globalOnDeadlineNodeId (only if the deadline handler has not run yet); otherwise the instance ends TimedOut with error code WAIT_TIMEOUT (a saga with enableCompensation unwinds first).

The sweep checks only whether the current node's type is timer. A custom suspension node gets
the timeout routing above; set OnTimeoutNodeId to route a timeout to a handler node. A wait that would
outlast an unhandled instance Deadline is capped at it, and then the deadline handling applies instead.

csharppublic async Task<NodeResult> ExecuteAsync(...)
{
    var config = node.Config.Deserialize<MyWaitNodeConfig>()!;

    // 1. Do whatever triggers the external work
    await _externalService.StartAsync(ctx.ResolveAs<string>("$.entity.Id")!, ct);

    // 2. Build the wait descriptor — engine saves this and suspends
    var correlationKey = config.CorrelationKeyExpression != null
        ? await _when.EvaluateAsStringAsync(config.CorrelationKeyExpression, ctx, ct) ?? instance.InstanceId
        : ctx.ResolveAs<string>(config.CorrelationKeyPath!)!;
    // _when is the WhenEvaluator instance (registered by AddFlowEngine) taken through the constructor.
    // The resolved key must be at most 256 UTF-16 code units (RUNTIME_KEY_TOO_LONG otherwise).

    return new NodeResult
    {
        Outcome     = DecisionOutcome.Match,
        PendingWait = new WaitDescriptor
        {
            EventName      = config.EventName,
            CorrelationKey = correlationKey,
            TimeoutAt      = config.Timeout != null
                ? await ctx.ResolveDateTimeAsync(config.Timeout, ct)
                : null,
            MinSignalCount = config.MinSignalCount
        }
    };
    // The engine saves state, releases the lock, and returns.
    // When ResumeAsync(eventName, correlationKey) is called, the engine
    // re-enters the loop. Your node is NOT re-executed — the engine
    // reads NodeResult.PendingWait == null on the resumed instance
    // (the engine cleared it) and evaluates edges normally.
}

What happens on resume: The engine detects PendingWait != null after
your node returns, saves the instance as Suspended, and stops. When
ResumeAsync is called, the engine loads the instance (now with
PendingWait = null cleared by the engine) and advances to edge evaluation
— your node does NOT run again.

Human task pattern

Nodes that create human tasks must handle crash-recovery idempotency
(never create a duplicate task):

csharppublic async Task<NodeResult> ExecuteAsync(...)
{
    // Check for existing task first — handles crash + re-execution
    var existing = (await _taskStore.GetByInstanceAsync(instance.InstanceId, ct))
        .FirstOrDefault(t => t.NodeId == node.Id);

    if (existing != null)
    {
        // Task already exists — check if it's done
        if (existing.Status == HumanTaskStatus.Completed
            && existing.Responses.Count >= existing.Quorum)
        {
            // Quorum reached — write response and return Match
            WriteResponseToContext(existing, instance);
            return new NodeResult { Outcome = DecisionOutcome.Match };
        }
        // Still waiting — re-suspend
        return new NodeResult
        {
            Outcome     = DecisionOutcome.Match,
            PendingWait = BuildWaitDescriptor(existing, instance)
        };
    }

    // Create new task
    var task = new HumanTask { TaskId = Guid.NewGuid().ToString("N"), ... };
    await _taskStore.SaveAsync(task, ct);

    return new NodeResult
    {
        Outcome     = DecisionOutcome.Match,
        PendingWait = BuildWaitDescriptor(task, instance),
        HumanTaskId = task.TaskId
    };
}

Emitting different DecisionOutcome values

Your executor controls the outcome. The engine uses it to select which edge(s)
to evaluate:

csharp// Match — condition met, operation succeeded
return new NodeResult { Outcome = DecisionOutcome.Match };

// NoMatch — condition explicitly not met (e.g. query returned 0 results)
return new NodeResult { Outcome = DecisionOutcome.NoMatch };

// Unknown — couldn't determine (e.g. required context key was null)
if (ctx.Resolve("$.context.someRequired") == null)
    return new NodeResult { Outcome = DecisionOutcome.Unknown };

// Error — something failed
return new NodeResult { Outcome = DecisionOutcome.Error, Error = ... };

// Note: Default is emitted by the EDGE EVALUATOR, not the node executor,
// when no other edge matches. Your executor never returns Default.

// CircuitOpen is emitted by the ENGINE when a CircuitBreakerPolicy is configured and the
// circuit is open: your executor is not called. Add an edge with On: ["CircuitOpen"] to route
// to a fallback node; if no such edge exists, the engine suspends the instance until the
// circuit cools down (or closes).
// Your executor may also return CircuitOpen itself (its dependency's own breaker is open).
// It then counts as a circuit failure (not for compensation steps or the global failure
// and deadline handler nodes, which never record on circuits), and it asserts NO side
// effects happened: such a visit is never compensated. Return Error after partial work.

Accessing external clients

Use IClientRegistry (via ctx.Services) to resolve named clients. A non-blank clientRef key (any case) in a node's config is also checked when the definition is saved to the workflow registry: an unregistered one is rejected with WorkflowDefinitionValidationException code CLIENT_NOT_REGISTERED. For the built-in client node types, a registered client of the wrong kind is rejected with code CLIENT_TYPE_MISMATCH (integration/fetch need IRequestResponseClient, message IMessageClient, query IQueryClient, agent IAgentClient, workflow IFlowEngineClient).

csharp// In constructor — inject IClientRegistry
private readonly IClientRegistry _clients;

// In ExecuteAsync
var config = node.Config.Deserialize<MyNodeConfig>()!;
var client = _clients.GetAs<IRequestResponseClient>(config.ClientRef)
    ?? throw new InvalidOperationException(
        $"Client '{config.ClientRef}' not registered or not IRequestResponseClient. " +
        $"Register via builder.AddClient().");

var response = await client.ExecuteAsync(new ClientRequest
{
    Method = "POST",
    Url    = config.Url,
    Body   = JsonSerializer.SerializeToElement(requestBody)
}, ct);

Custom node config best practices

csharppublic sealed class MyNodeConfig
{
    // Reference external clients by name — never embed connection strings
    public string  ClientRef     { get; init; }

    // Reference credentials by name — never embed secrets
    public string? CredentialRef { get; init; }

    // JSONPath expressions for input values — resolved at execution time
    public string  InputPath     { get; init; }

    // Timeout — always provide a sensible default
    public int TimeoutMs { get; init; } = 10_000;

    // Never: connection strings, API keys, base URLs
    // Always: clientRef + IClientRegistry lookup
}

fetch node exception: FetchNodeConfig.ClientRef is optional. When set, the fetch executor routes through the registered IRequestResponseClient. A clientRef that names no registered IRequestResponseClient fails the node; it never falls back. When absent, the executor sends on the HttpClient registered in DI if there is one, else on one shared HttpClient (never one per request), with the timeout applied per request. If that client has a BaseAddress, BaseAddressBoundary.Resolve holds the URL to it (same scheme, host, port and user info, under the base path prefix, no encoded . / \ ; % and no ..; segment); a credentialRef on a client without one requires the scheme and host to be written literally in the URL template. Responses map 2xx to Match, any 4xx to NoMatch, and everything else (5xx, transport failure, refused URL) to Error. This is the only node config where a clientRef is not required; all other async node types (integration, query, agent, message, workflow cross-engine) require one. Use the clientRef form for production; the raw form is for one-off calls to legacy or non-registerable endpoints.

Registration and DI

services.AddFlowEngine()
    .AddNodeExecutor<MyCustomNodeExecutor>();

    .AddNodeExecutor(new MyCustomNodeExecutor());

// Executor with dependencies
services.AddFlowEngine()
    .AddNodeExecutor<MyCustomNodeExecutor>();

// MyCustomNodeExecutor receives IMyDependency via constructor injection

services.AddFlowEngine()
    .AddNodeExecutor<MyCustomNodeExecutor>()
    .AddNodeExecutor<MyOtherNodeExecutor>()
    .AddNodeExecutor<MyThirdNodeExecutor>();

AddFlowEngine() registers every built-in executor (filter, compute, human, wait, etc.) as an
INodeExecutor singleton; do not add them again. There is no distinction between built-in and
custom node types at the engine level. The only requirement is that NodeType matches the "type"
field in the workflow JSON.

Roslyn expression security

The compute node and edge when predicates execute C# expressions at runtime via Roslyn scripting. This is a trusted-authors-only feature. The following applies to any deployment using these node types:

Trust model: Workflow authors are trusted. Expressions run in the same process as the engine, with full access to the .NET BCL. There is no sandbox — an expression can call File.Delete, open sockets, or access environment variables. This is by design for performance and expressiveness.

Implications for multi-tenant or externally-authored workflows:
- If workflow definitions can be created by untrusted parties (e.g. end users of a SaaS product), compute nodes and when predicates represent a code injection vector.
- In those scenarios, either disable compute/when support for untrusted definitions, or run the engine in a sandboxed process (separate container, gVisor, etc.) with restricted filesystem and network access.
- You can enforce this at the registry level: reject definitions containing compute nodes or non-trivial when predicates during SaveAsync validation.

Expression compilation caching: Roslyn compiles each unique expression on first use and caches the result. Expressions are keyed by their string content — two nodes with identical expressions share one compiled delegate. The cache is bounded to FlowEngineOptions.ScriptCacheSize entries (default 1000). When that limit is reached, the oldest 10% of entries are evicted to make room — so the cache does not grow unboundedly, but high-churn deployments (many distinct expression strings across workflow versions) will pay recompilation cost on evicted entries. For such deployments, raise ScriptCacheSize or monitor recompile frequency via IFlowEngineTelemetry.

Allowed assemblies: By default, Roslyn scripting has access to mscorlib, System.Core, System.Linq, and the assemblies loaded into the current AppDomain. If your engine process loads application assemblies, those are accessible too. Restrict the reference list in ComputeNodeExecutor's script options if your threat model requires it.

In-memory stack - zero-infrastructure integration tests

AddFlowEngine() registers in-memory implementations of the state store, lock provider and workflow registry, and every built-in executor. UseAllInMemoryProviders() (from EF.FlowEngine.Testing) sets the in-memory state store, lock provider and human task store explicitly; UseInMemoryLockProvider() (from EF.FlowEngine.Locks.InMemory) sets only the lock provider.

Custom state store implementations must correctly implement the child-signal members EnqueueChildSignalAsync, DequeueChildSignalsAsync, FindInstancesWithChildSignalsAsync and PeekChildSignalsAsync. The engine first tries to resume the parent immediately on child completion (fast path), and enqueues a durable signal when the parent's lease is held or the host is stopping. A run drains the queue on entry (DequeueChildSignalsAsync), the engine reads it without removing to decide whether a suspended parent should run (PeekChildSignalsAsync; the default implementation dequeues and re-enqueues, which can lose signals if the process stops in between, so override it), and the sweep pages through parents with queued signals (FindInstancesWithChildSignalsAsync). A store that stubs these silently drops signals under contention. See FlowEngine Design Doc -> IExecutionStateStore for the full contract.

csharp// Integration test: run a full workflow end-to-end
var services = new ServiceCollection();
services.AddLogging();
services.AddFlowEngine()
    .UseAllInMemoryProviders();
    // .AddNodeExecutor<MyCustomNodeExecutor>() for custom node types only

var provider = services.BuildServiceProvider();
var engine   = provider.GetRequiredService<IFlowEngine>();
var registry = provider.GetRequiredService<IWorkflowRegistry>();
var ct       = CancellationToken.None;

await registry.SaveAsync(MyWorkflows.ExpenseApproval, ct);
var instance = await engine.StartAsync(new StartRequest { WorkflowId = "expense-approval", Entity = entityValue }, ct);

Assert.Equal(ExecStatus.Suspended, instance.Status);   // waiting at human node

// Simulate the human response. The in-memory task store resumes the instance itself once the
// quorum is reached (responseToken is only checked for the External channel).
var taskStore = provider.GetRequiredService<IHumanTaskStore>();
