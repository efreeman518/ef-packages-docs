FlowEngine — Use-Case Examples

Nine representative business workflows illustrating the node and engine surface described in these docs.

This document uses nine business workflows to illustrate the FlowEngine
schema surface across multiple industries. Together they reference all 19
node types and the main engine behaviors: durable suspension, rework cycles,
parallel execution, child instances, cross-engine invocation, signal accumulation, crash recovery, and saga compensation.

UC1 — Healthcare Prior Authorization

Scenario: Patient needs a specialty medication. Insurance must approve
before the pharmacy dispenses. Possible outcomes: auto-approved, manually
approved, denied, or expired after clinical info timeout.

Rework pattern: Clinical information can be requested up to 2 times
before the case is auto-denied.

Start: { patient, prescription, prescriber, insurancePlan }
  │
  ├── filter: patient eligible under plan?
  ├── filter: medication on formulary?
  ├── integration: "eligibility-api" → get coverage details
  ├── filter: auto-approve criteria met? (diagnosis code + formulary tier)
  │     ├── Match → output: AUTO_APPROVED
  │     └── NoMatch → continue
  │
  ├── human[Internal]: "Medical Director Review"
  │     ├── "approved"      → integration: "auth-number-api" → output: APPROVED
  │     ├── "denied"        → output: DENIED
  │     └── "needs-clinical"→ check rework limit via $.engine.visits
  │           ├── visits < 2 → wait: "clinical-info.received" (P7D timeout)
  │           │   └── resume → loop back to human
  │           └── visits >= 2→ output: DENIED_INSUFFICIENT_INFO
  │
  └── wait: "clinical-info.received"
        ├── Match → (loop back to human[Medical Director])
        └── Error (timeout) → output: EXPIRED

Patterns shown:

filter targeting $.entity with nested navigation paths
(Patient.InsurancePlan.Tier) — FilterBuilder null-safe path handles this

integration with storeAs — eligibility-api stores coverage details,
downstream filter reads $.context.coverage.formularyTier

filter targeting $.context for auto-approve criteria check

human node Internal channel, with dueIn and escalation

wait node with timeout: "P7D" — sweep service handles expiry

Rework pattern — $.engine.visits.n-medical-review < 2 on edge when,
backward edge to n-medical-review

Multiple output nodes: AUTO_APPROVED, APPROVED, DENIED, DENIED_INSUFFICIENT_INFO, EXPIRED

integration for auth number generation after approval

Design note: The wait for clinical info uses a correlationKeyPath
of $.entity.AuthRequestId. The external EHR system that posts clinical
data needs to include that ID. This is a system integration concern, not
a schema concern — the harness pattern covers it.

UC2 — Loan Origination

Scenario: Small business loan application. Multi-stage underwriting with
parallel bureau pulls, risk scoring, committee approval (2-of-3 quorum),
and adverse action notice generation.

Start: { application, applicant, business }
  │
  ├── parallel: ["credit-bureau", "fraud-check", "business-score"]
  │     joinStrategy: All, errorBehavior: ContinueWithPartial
  │
  ├── compute: composite risk score from bureau results
  ├── compute: debt-to-income ratio
  ├── store: riskTier = (score > 750 ? "low" : score > 600 ? "medium" : "high")
  │           NOTE: decision node + when predicates is cleaner for this
  │
  ├── decision: route on riskTier
  │     ├── "low"  → output: AUTO_APPROVED (with terms)
  │     ├── "medium"→ human[Internal]: "Underwriter Review" (quorum: 1)
  │     ├── "high" → human[Internal]: "Credit Committee" (quorum: 2, role: committee)
  │     └── Default → output: AUTO_DENIED
  │
  ├── human[quorum]: credit committee responds
  │     ├── unanimous "approved" → integration: "loan-booking-api"
  │     │                        → output: APPROVED
  │     ├── any "denied"         → output: DENIED_WITH_ADVERSE_ACTION
  │     └── rework (up to 2x)   → backward edge to decision
  │
  └── output nodes: AUTO_APPROVED, APPROVED, DENIED, AUTO_DENIED

Patterns shown:

parallel with joinStrategy: All and errorBehavior: ContinueWithPartial
— partial bureau result is acceptable, engine proceeds with what it has

compute nodes for score and DTI — Roslyn expression with Context["bureauScore"]

decision node — valuePath: "$.context.riskTier" with edge when predicates

human node with quorum: 2 and assignedTo: "role:credit-committee"
— IHumanTaskStore.SubmitResponseAsync tracks quorum, resumes when 2 respond

Multi-response handling — $.context._humanTaskResponses accumulates all responses when quorum > 1. $.context._humanTaskConsensus is set automatically: "unanimous", "majority", "any-denied", or "split". Edges use simple string comparison: "$.context._humanTaskConsensus == 'unanimous'".

Rework with $.engine.visits.n-underwrite < 2 on backward edge

integration for loan booking after approval

Multiple terminal output nodes

UC3 — E-commerce Order Fulfillment

Scenario: Order placed. Check inventory per line item, calculate shipping
and tax, charge payment, allocate warehouse stock, notify customer.
Customer can request to wait for backordered items (up to 3 times before
forced cancellation).

Start: { order, customer }
  │
  ├── loop[Parallel]: over order.LineItems → "check-stock" sub-workflow
  │     aggregate: { reservedItems: collect, backorderedItems: collect }
  │
  ├── query: "crm-db" / Customer / any / filter: loyalty tier
  ├── filter: any backorderedItems?
  │     ├── NoMatch → continue
  │     └── Match → human[External]: customer backorder decision (up to 3x)
  │           ├── "ship-partial" → continue
  │           ├── "wait" + visits < 3 → wait: "inventory.restocked" (P14D)
  │           │   → loop back to loop[check-stock]
  │           ├── "wait" + visits >= 3 → output: CANCELLED
  │           └── "cancel" → output: CANCELLED
  │
  ├── checkpoint: before payment chain
  │
  ├── integration: "shipping-calculator-api"
  ├── integration: "tax-service-api"
  ├── compute: orderTotal = subtotal + shipping + tax
  │
  ├── integration: "payment-api" (idempotencyKey: orderId + "-charge")
  │     ├── Match → continue
  │     ├── NoMatch (declined) → human[External]: customer update payment
  │     └── Error → output: PAYMENT_ERROR
  │
  ├── loop[Sequential]: over reservedItems → "allocate-stock" sub-workflow
  │
  ├── message[FireAndForget]: "order-events" / "order.completed"
  ├── integration: "notification-api" → send confirmation
  └── output: FULFILLED

Patterns shown:

loop[Parallel] with aggregate: collect — child instances run concurrently,
results collected into $.context.reservedItems and $.context.backorderedItems

query node — resultMode: any for loyalty tier (does customer have VIP status?)
This exercises the cross-type dataset query: CRM Customer entity queried
while processing an Order entity

filter on $.context.backorderedItems — checks length > 0

human[External] with channel: External, notification config,
dueIn: "P3D", external customer email as assignee

Rework pattern with $.engine.visits.n-backorder-decision < 3 and backward
edge to the loop node (re-checks stock after waiting for restock)

wait node for restock signal with timeout: "P14D" — timeout takes
Error edge to cancellation output

checkpoint node before payment chain — correctly placed between the
expensive loop and the write operations

integration nodes with idempotencyKey on payment (prevents double-charge
on crash recovery re-execution)

compute for order total — straightforward Roslyn arithmetic

loop[Sequential] for stock allocation — order matters here

message[FireAndForget] for downstream event notification

integration for customer email notification

Multiple output nodes: FULFILLED, CANCELLED, PAYMENT_ERROR

Design note: The checkpoint placement matters — without it, a crash after the shipping/tax calculations but before payment would re-run those integrations. With the checkpoint, only the payment-forward path needs to be idempotent.

UC4 — AI-Assisted Document Review

Scenario: Research lab submits a sample document for review. An AI agent analyses
the content and, if acceptable, a legal team member provides sign-off. A digital
signature is then required before the document is marked approved.

Start: { sampleId, documentId, submittedBy }
  │
  ├── fetch: retrieve document from storage API
  ├── transform: map raw fetch response to standardised document fields
  ├── agent: "uc-agent-client" → review document content
  │     ├── Match → store: save AI recommendation
  │     └── Error → output: AI_REVIEW_ERROR
  │
  ├── human[Internal]: legal-team review
  │     └── Match → wait: "signature.received"
  │
  ├── wait: "signature.received" (correlationKey: instanceId)
  │     └── Match → output: APPROVED
  └── output: AI_REVIEW_ERROR (error path terminal)

Patterns shown:

fetch — document retrieval via registered IRequestResponseClient

transform — maps raw response fields to standardised shape for AI prompt input

agent with Error routing — IAgentClient returns Error outcome; routes
directly to error output without creating a human task

store — records AI recommendation in context for human reviewer visibility

human[Internal] with channel: Internal and assignedTo: "legal-team"

wait for digital signature — uses instanceId as correlation key;
harness calls engine.ResumeAsync("signature.received", instance.InstanceId)

Multiple output nodes — APPROVED, AI_REVIEW_ERROR

document node (when AzuriteContainerFixture is available) — uploads/downloads
document content via IDocumentStore backed by Azure Blob Azurite

UC5 — Scheduled Batch Processing

Scenario: A scheduled job (timer-triggered) extracts a batch payload from a sub-workflow, loops over each item in the batch, processes it, stores the result, and sends an ops notification when complete. An empty-batch case runs 0 loop iterations and still sends the notification.

Start: no entity (scheduled invocation)
  │
  ├── timer: 2-second delay (sweep service fires)
  ├── workflow[local]: "uc5-extract" sub-workflow → $.context.batchItems
  ├── loop[Sequential]: over $.context.batchItems
  │     sub-workflow: "uc5-item-processor"
  │       └── store: itemResult
  │
  ├── store: batchComplete = true
  ├── message[FireAndForget]: "Batch Processing Complete" to msg-client
  └── output: BATCH_DONE { batchStatus }

Node types exercised in UC5: timer, workflow, loop, store, message, output

Patterns shown:

timer — sweep service resumes the instance after the delay elapses. No harness code required. The scheduled host (Functions/Hangfire/Quartz) calls StartAsync; the timer handles the durable delay before execution continues.

workflow[local] for data extraction — the extract sub-workflow stores its result via storeAs; the parent reads it from $.context.batchItems

loop[Sequential] over the extracted array — each item processed in order by a lightweight item-processor sub-workflow

store node — records batch metadata (completion flag) into context

message[FireAndForget] — ops notification after batch completes; parent continues without waiting for consumer acknowledgement

Empty-batch case — when batchItems is empty the loop runs 0 iterations and the workflow still reaches the output node via the normal path

Single output node — BATCH_DONE (this workflow has one terminal outcome)

UC6 — Regulatory Compliance Check

Scenario: A manufacturing batch is submitted for regulatory compliance review. Invalid batches are immediately denied via a filter node. High-risk batches call a lab integration for measurements, compute a compliance score, loop through individual findings (each in a sub-workflow), then use a fetch node to call a legacy ERP API for batch release. Low-risk batches skip the lab and go direct to release.

Start: { batchId, riskLevel }
  │
  ├── filter: batchId present?
  │     ├── NoMatch → output: DENIED_INVALID
  │     └── Match → continue
  │
  ├── decision: route on riskLevel
  │     ├── "high" → integration: "lab-instrument-api" → store: labResults
  │     │             compute: complianceScore = f(labResults)
  │     │             loop[Parallel]: over findings
  │     │               sub-workflow: "uc6-finding"
  │     │                 └── fetch: "erp-api" / finding record
  │     └── other → continue direct
  │
  ├── compute: passed = complianceScore >= threshold (or default pass for low-risk)
  ├── integration: "erp-api" / batch-release
  └── output: RELEASED { batchId, complianceScore }

Node types exercised in UC6: filter, decision, integration, compute, loop, fetch, output

Patterns shown:

filter on $.entity — early-exit guard for invalid input; NoMatch routes directly to denial output without touching any external system

decision on riskLevel — branches to the lab path (high-risk) or the direct-release path (low-risk). Unknown/NoMatch (null riskLevel) takes the direct path — safe default rather than failure

integration for lab instrument — typed client call storing raw measurements as $.context.labResults

compute for compliance score — Roslyn expression over the lab result fields

loop[Parallel] over findings — each finding processed concurrently by a sub-workflow that calls the ERP via fetch

fetch node — legacy ERP API has no typed integration definition; raw HTTP escape hatch. Illustrates when fetch is appropriate over integration.

Multiple output nodes — RELEASED (happy path), DENIED_INVALID (bad input)

UC7 — Product Launch Coordination

Scenario: A new product is readied for market. Metadata is normalised, parallel
tracks run simultaneously (marketing prep, logistics readiness), a decision
routes high-confidence products through regulatory approval, and a launch
announcement is sent once all steps complete.

Start: { productId, name, sku, confidence }
  │
  ├── transform: normalise raw product fields → $.context.normalised
  ├── parallel: ["uc7-marketing-sub", "uc7-logistics-sub"]
  │     joinStrategy: All, errorBehavior: StopAll
  │
  ├── decision: route on $.entity.confidence
  │     ├── Match (non-null confidence) → workflow: "uc7-regulatory-sub"
  │     └── NoMatch/Unknown (null confidence) → output: BLOCKED
  │
  ├── workflow[local]: "uc7-regulatory-sub" (parallel approvals, loops)
  ├── store: save regulatory outcome
  ├── compute: derive launch readiness score
  ├── message[FireAndForget]: "Product Launch Announcement" to order-events
  └── output: LAUNCHED

Node types exercised in UC7: transform, parallel, decision, workflow, store, compute, message, timer, output

Patterns shown:

transform — normalises raw entity fields. Stored result available as $.context.normalised
for downstream nodes without re-reading $.entity

parallel with JoinStrategy.All and ErrorBehavior.StopAll — both tracks
(marketing + logistics sub-workflows) must complete; one faulting branch stops all

decision — null confidence test using JSONPath resolution; NoMatch/Unknown
directs cleanly to BLOCKED output; Match (non-null) continues to regulatory

workflow[local] for regulatory sub-workflow — FireAndForget: false; parent suspends
until regulatory sub-workflow completes

store / compute — standard context accumulation; compute builds launch score
from aggregated parallel branch outputs

message[FireAndForget] — launch announcement published to message bus;
parent continues without waiting for consumer

timer — used inside regulatory sub-workflow for a brief compliance delay;
exercises the ISO 8601 delay path end-to-end in a UC context

Multiple output nodes — LAUNCHED (success), BLOCKED (null confidence)

UC8 — Scheduled Fleet Service Batch

Scenario: An external scheduler (Azure Functions / Hangfire / Quartz) calls StartAsync with no entity. The entry query node uses FilterBuilder over real SQL seed data to discover vehicles with Status IN (Warning, Critical). A loop node runs a per-vehicle analysis sub-workflow: an agent node returns structured JSON { severity, recommendedTeam, reason }; downstream filter nodes branch to integration (team queue API) + message (manager email) for Critical, integration only for Routine, or no-op for NoAction. An ops batch-complete message is sent after the loop.

Start: no entity (scheduler-triggered)
  │
  ├── query: "uc-query-client" / Vehicle / all
  │     filterSet: Status IN ["Warning", "Critical"]
  │     storeAs: vehiclesNeedingService
  │     ├── Match  → loop-vehicles
  │     └── NoMatch/Error → notify-empty → output: BATCH_EMPTY
  │
  ├── loop[Sequential]: over $.context.vehiclesNeedingService
  │     itemAs: currentVehicle (→ $.params.currentVehicle in sub-workflow)
  │     sub-workflow: "uc8-vehicle-analysis"
  │       ├── agent: analyse vehicle → { severity, recommendedTeam, reason }
  │       │     storeAs: analysis   ($.params.currentVehicle embedded in prompt)
  │       ├── filter: severity == "Critical"?
  │       │     └── Match → parallel[All]: enqueue-team + email-manager
  │       ├── filter: severity == "Routine"?
  │       │     └── Match → integration: POST /service-teams/queue
  │       └── output: { vehicleId, severity, routing }
  │
  ├── message[FireAndForget]: "Fleet Batch Complete" to msg-client
  └── output: BATCH_DONE { batchStatus }

Node types exercised in UC8: query, loop, agent, filter, parallel, integration, message, output

Patterns shown:

query node with FilterBuilder over real SQL — resultMode: All returns a flat JSON array; no entity input required (scheduled invocation). The in operator with array testValue survives JSON round-trip correctly (scalar eq does not when TestValue is deserialized as JsonElement).

loop passes each item as @params to the child workflow (accessible as $.params.currentVehicle, NOT $.context.currentVehicle). This is the critical path distinction for loop-scoped sub-workflows.

agent node with per-item-varying response — promptTemplate embeds {{$.params.currentVehicle}} which the executor resolves via InterpolateTemplate before passing to the IAgentClient. The stub's ResponseFactory reads the resolved prompt to determine severity from the embedded vehicle JSON.

filter nodes on agent output — target: "$.context.analysis" checks the severity string returned by the agent. Each branch is a separate filter node (Critical → parallel, Routine → single integration, NoAction → skip).

parallel[All] for Critical vehicles — enqueue-team (integration POST) and email-manager (message) run concurrently; both must complete before the sub-workflow's output node is reached.

message for manager email — subject "Critical Vehicle Service Required"; testable via MessageSpy.SentMessages in the test harness.

Empty result-set branch — when the query returns 0 vehicles, NoMatch routes to a notify-empty message node and then to a terminal output. No per-vehicle traffic is produced.

NoAction branch — when the agent returns severity: "NoAction" the sub-workflow skips both integration and message nodes and falls through to the output directly.

Design note: Scheduling is out-of-scope for the engine. Production hosts (Azure Functions timer trigger, Hangfire, Quartz) own the cron trigger and call StartAsync directly. The query node performs the discovery that a scheduled batch job would normally do in application code — keeping the working-set logic declarative and version-controlled alongside the rest of the workflow.

UC9 — Inventory-Payment-Shipping Saga

Scenario: An order flows through three sequential integration steps — reserve inventory, charge payment, ship order. Each forward step declares a compensation node. If any step fails, the engine runs compensation nodes in reverse order (refund-payment, then release-inventory) and routes to a GlobalOnFailureNodeId terminal output rather than faulting the instance.

Start: { orderId, customerId, items }
  │
  ├── integration: POST /uc9/reserve
  │     compensationNode: release-inventory
  │     ├── Match → charge-payment
  │     └── Error → [compensation chain]
  │
  ├── integration: POST /uc9/charge
  │     compensationNode: refund-payment
  │     ├── Match → ship-order
  │     └── Error → [compensation chain]
  │
  ├── integration: POST /uc9/ship
  │     (no compensator — idempotent / read-only-ish)
  │     ├── Match → saga-success (output: result=shipped)
  │     └── Error → [compensation chain]
  │
  Compensation chain (runs in reverse on failure):
  ├── store: refund-payment      → paymentRefunded=true
  ├── store: release-inventory   → inventoryReleased=true
  └── GlobalOnFailureNodeId → saga-failed (output: result=saga-compensated)

Node types exercised in UC9: integration, store, output

Patterns shown:

EnableCompensation: true — activates the saga compensation engine. Without this flag a failing node faults the instance with no rollback (tested separately as the opt-out variant).

compensationNode per forward step — each integration node declares the rollback node to execute if it (or any later step) fails. The engine walks the executed-node stack in reverse and runs only the compensation nodes whose forward step completed with Match.

GlobalOnFailureNodeId: "saga-failed" — after compensation completes the engine routes to this terminal output node, so the instance Completes rather than Faults. The compensation path is fully auditable in ExecutionInstance.History.

store nodes as compensation actions — lightweight context writes represent the rollback side-effects. In production these would be integration calls to undo the forward action (refund charge, release reservation).

Partial compensation — when payment fails (step 2), only the inventory compensation runs; charge-payment never completed so its compensator is skipped. The engine tracks completed nodes, not declared nodes.

Compensation opt-out — EnableCompensation: false (default): no rollback, no GlobalOnFailureNodeId; a failing step leaves the instance Faulted.
